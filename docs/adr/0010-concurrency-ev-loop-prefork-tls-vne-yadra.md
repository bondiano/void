# ADR-0010: Concurrency — ev loop + fiber на запрос; multi-core через prefork; TLS вне ядра

- Статус: accepted
- Дата: 2026-08-25
- Связанные разделы SPEC: §1 (ограничения платформы), §8.1, §8.5

## Контекст и постановка проблемы

Janet — bytecode-интерпретатор без JIT (класс CPython/Ruby по CPU), с stop-the-world GC и потоками, не разделяющими heap. HTTP-серверу нужно решить: модель конкурентности внутри процесса, утилизация ядер CPU, и кто отвечает за TLS (в stdlib его нет).

## Драйверы решения

- Профиль нагрузки фреймворка — I/O-bound; tail latency решается архитектурой, а не скоростью интерпретатора.
- GC-паузы одного воркера не должны трогать остальных.
- `dyn` per-fiber даёт request context бесплатно — модель «fiber = запрос» естественна для платформы.
- Простота deploy story (single binary за reverse proxy).

## Рассмотренные варианты

1. **ev loop + fiber на запрос; multi-core = prefork (N процессов × SO_REUSEPORT); TLS — на reverse proxy.**
2. **Thread-pool внутри процесса** — потоки Janet не шарят heap, cross-thread только через channels; shared route table/пулы невозможны без сериализации — модель ломается о платформу.
3. **Один процесс, один loop** — не утилизирует ядра; оставлен как вырожденный случай prefork (N=1).
4. **TLS в ядре через ffi к openssl/bearssl** — тяжёлая поверхность атаки и сопровождения; отложено в опциональный plugin `void/tls` (low priority).

## Решение

Вариант 1.

- **Внутри процесса**: всё на `ev` — fiber на запрос, неблокирующие драйверы (см. ADR-0011), `dyn` для request/trace context. Блокирующие вызовы (FFI, CPU-bound) — только явно через `ev/thread`.
- **Multi-core**: prefork — N воркеров × SO_REUSEPORT (Linux сам раздаёт accept); никакого shared state между воркерами кроме БД/Redis. `void/http` умеет `:workers :auto`. Это же изолирует GC-паузы по воркерам.
- **TLS**: за TLS отвечает reverse proxy (nginx/Caddy/Cloudflare) — часть deploy story; ffi-plugin `void/tls` возможен позже. Исключение: TLS к Postgres бесплатен — его делает сам libpq.
- **GC-дисциплина**: короткие request lifetimes, переиспользование буферов (`buffer/clear`), `gcsetinterval` как ручка trade-off; бюджет — max pause < 10 ms, суммарно < 2% времени.
- **Правила для авторов plugins** (в CONTRIBUTING): никаких синхронных syscalls/FFI на loop; аллокации на hot path бюджетируются; всё, что можно посчитать на build-этапе, считается там.
- Health-индикатор №1 — **ev loop lag** (p99 < 1 ms), меряется из коробки в void/obs.

Честные пределы фиксируются в позиционировании: тысячи RPS на воркер, десятки тысяч на машину префорком; выше — другой язык или CDN/proxy впереди.

## Последствия

Плюсы:

- Модель совпадает с сильными сторонами платформы (ev, dyn per-fiber) и не борется с её ограничениями.
- Prefork — проверенная десятилетиями модель (unicorn, gunicorn); изоляция сбоев и GC-пауз бесплатно.
- Отказ от TLS в ядре убирает самый опасный класс кода из проекта.

Минусы / цена:

- Один синхронный вызов на loop портит latency всем запросам воркера — нужна культура + линт + метрика loop lag.
- In-process shared state между воркерами невозможен: кэши/сессии/rate-limit при N>1 обязаны жить в Redis/БД — это надо явно писать в docs каждого такого plugin.
- «TLS через proxy» усложняет минимальный деплой на голой VM — компенсируется документированной deploy story.
