# ADR-0020: Дистрибуция — монорепо как один jpm-bundle, граф пакетов как данные

- Статус: proposed
- Дата: 2026-08-28
- Связанные разделы SPEC: §5.17, §7 (п. 4), §9; часть I §1.2
- Референс: [janet-lang/jpm](https://github.com/janet-lang/jpm) — `pm.janet` (`resolve-bundle`, `bundle-install`), `declare.janet` (`declare-source`, `declare-binscript`)

## Контекст и постановка проблемы

README обещает Quick start из четырёх строк — `void new guestbook && cd guestbook && void dev`. На чистой машине не работает ни одна: `void` не устанавливается ничем, а сгенерированный `void new` проект не собирается — вместо зависимости в его `project.janet` стоит комментарий «until the packages are published, jpm install them from a void checkout». Установка — единственная часть системы, которую никто не проверял, включая CI: он гоняет `jpm test` по подкаталогам монорепо, то есть по живым исходникам, и путь пользователя не трогает вовсе.

Причина не в недоделке, а в инструменте. jpm-зависимость — это **git-репозиторий с `project.janet` в корне**: `resolve-bundle` знает типы `:git` и `:tar`, `bundle-install` клонирует репо, делает `cd` в его корень и требует там проект. Подкаталога в этой модели нет. Монорепо из пятнадцати scoped-пакетов через `:dependencies` не описывается в принципе, и строка README «each installable on its own via jpm» не соответствует тому, что jpm умеет.

Второй симптом того же корня: **граф зависимостей пакетов уже существует, записан трижды и ни разу машиночитаемо**. Он живёт в шестнадцати копиях `*/test-support/paths.janet` (по одной на пакет и на пример), дублируется прозой в комментариях каждого `project.janet` («void-core (../core) and void-http (../http) must be on the module path as well») и ещё раз — порядком шагов в CI. Ни один `project.janet` не объявляет зависимость от другого void-пакета. Расхождение этих трёх списков не ловит ничто.

Наконец, два дефекта в самом бинаре: установленный `void` получает двойной shebang (jpm дописывает свой поверх уже имеющегося в `cli/bin/void`), и `void` не видит локальное `jpm_tree/lib` проекта — схема «дерево на приложение», штатная для jpm, не работает.

## Драйверы решения

- Quick start обязан работать на чистой машине: позиционирование §9 (batteries included, стоимость владения) иначе не проверяет никто, кроме автора.
- void релизится **одной версией по волнам** (v0.1 → v0.4). Независимое версионирование пятнадцати пакетов было бы фикцией, а `:requires {:void/http ">=0.0.1"}` в манифестах плагинов — проверкой самой себя.
- Контрибьюторский цикл не должен требовать установки: тесты гоняются по живым исходникам, иначе dogfooding через netrepl превращается в цикл «поправил → переустановил».
- Граф пакетов — данные, всё остальное (пути тестов, порядок установки, матрица CI, dry-run) — его проекции (§2, ADR-0004).
- Опциональные нативные зависимости сообщают о себе на `:start`, а не на install — линия, уже выбранная для libpq (ADR-0011).

## Рассмотренные варианты

1. **N репозиториев — subtree-мирроры** (`core/` → `bondiano/void-core`, …), которые CI выталкивает из монорепо. Идиоматично для jpm: зависимости объявляются честно, приложение тянет только нужные пакеты. Цена — пятнадцать репозиториев и их синхронизация на одном разработчике (риск §«Риски»: длинный хвост plugins), плюс независимые версии, которых на самом деле не существует. Контрибьюторский цикл не улучшается вовсе.
2. **Свой инсталлятор** (`void install <пакет>`, CLI как пакетный менеджер собственных частей). Решает всё, но заводит второй пакетный менеджер рядом с jpm — ровно та сложность, которую void в остальном отказывается вносить.
3. **Native `bundle/` Janet ≥1.36** — `bundle/install` принимает **локальный каталог**, то есть монорепо-проблемы не существует, а порядок установки даёт `bundle/topolist`. Но spork и janet-lang/sqlite3 живут в jpm-мире, и экосистема туда пока не переехала: ставка преждевременна. Вернуться к вопросу к v0.4.
4. **Один корневой `project.janet` — один bundle `void`** (выбран).

## Решение

Вариант 4, четырьмя частями.

**1. `scripts/packages.janet` — граф как данные.** Одна декларация вида `{:void/core {:dir "core" :deps []} :void/http {:dir "http" :deps [:void/core]} …}`, из которой выводятся: `test-support/paths.janet` (становятся двухстрочными шимами вместо шестнадцати копий), топологический порядок установки, матрица шагов CI и список деревьев в `scripts/dry-run.janet`. Забытое ребро графа перестаёт быть тихой ошибкой.

**2. Корневой `project.janet` — bundle `void`.** `declare-source :source ["core/void" "http/void" …]` — деревья сливаются в один `<modpath>/void/`; `declare-native` для `fdwait`; `declare-binscript :main "cli/bin/void"`. Проверено на прототипе: после `jpm deps && jpm install` в изолированное дерево `void new demo && cd demo && void routes` отрабатывает из пустого каталога без единой ручной настройки путей.

Возражение «HTMX-приложение платит за C-компилятор ради нативного модуля» не проходит: `void/core` зависит от spork, а spork собирает девять нативных модулей (`json`, `base64`, `rawterm`, …). Компилятор в baseline уже есть, и `fdwait` (~60 строк) новых требований не добавляет — но требование cc становится явным и попадает в docs.

`janet-lang/sqlite3` зависимостью bundle **не** объявляется. Плагины грузятся по списку `:plugins`; приложение, не включившее `:void/db-sqlite`, драйвер не импортирует, а отсутствие библиотеки — ошибка на `:start` с внятным текстом, как у libpq.

**3. Дерево на приложение; глобальный `void` — тонкий лаунчер.** `bin/void` подхватывает `./jpm_tree/lib` **до** `(import void/cli)`:

```janet
(when (os/stat "jpm_tree/lib" :mode)
  (put root-env :syspath (string (os/cwd) "/jpm_tree/lib")))
(import void/cli :as cli)
```

Порядок здесь и есть решение: если подменить syspath после импорта, сам CLI останется из глобального дерева, а `void/http` придёт из проектного — и `void/core` окажется в процессе в двух экземплярах. Приложение делает `jpm --local deps` и пиннит свою версию фреймворка; глобальный бинарь только находит её. Заодно снимается лишний shebang из `cli/bin/void` — его дописывает jpm.

**4. `void new` генерирует настоящую зависимость** (`:dependencies ["https://github.com/bondiano/void.git"]`) вместо комментария, а Quick start в README становится исполняемым — и проверяется в CI на чистом дереве, а не только `jpm test` по подкаталогам.

## Последствия

Плюсы:

- Quick start становится проверяемым утверждением: путь пользователя — шаг CI, а не абзац документации.
- Шестнадцать копий `paths.janet` схлопываются в шимы, CI перестаёт перечислять пакеты руками, рассинхрон графа ловится сборкой.
- Контрибьютор получает `void` без установки (repo-relative дев-шим), автор приложения — пиннутую версию фреймворка в своём `jpm_tree`.
- Обещание «single binary» (§9) получает основу: bundle с бинарём — вход для `jpm quickbin` (ROADMAP 4.5).

Минусы / цена:

- `bundle-install` кэширует по URL, поэтому все void-пакеты обновляются вместе: приложение не сможет взять `void/http` новее, чем `void/cache`. Для волновых релизов это свойство, а не дефект, но **per-package pinning исключается** — если он понадобится, это новый ADR и возврат к варианту 1.
- Bundle кладёт на диск исходники всех пакетов, включая ненужные приложению. В процесс попадает только перечисленное в `:plugins`, но гранулярность `bundle/list` и manifest'ов теряется: установлен «void», а не «void-http 0.0.1».
- Утверждение README «each installable on its own via jpm» снимается как неверное; отдельная установка пакета из монорепо остаётся возможной только из чекаута (`cd http && jpm install`), и это путь контрибьютора, а не пользователя.
- Пока `void/core` тянет spork целиком, установка тянет и девять его нативных модулей — вопрос не этого ADR, но в бюджет времени установки он входит.
