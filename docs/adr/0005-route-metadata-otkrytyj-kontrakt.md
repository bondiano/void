# ADR-0005: Route metadata — открытая namespaced-map как интеграционный контракт

- Статус: accepted
- Дата: 2026-08-25
- Связанные разделы SPEC: §5.1, Часть II §2

## Контекст и постановка проблемы

Сквозные политики (authz, validation, OpenAPI, rate limit, txn, cache, tracing) должны цепляться к endpoint'у так, чтобы plugins не знали друг о друге. В Spring это аннотации на контроллерах; нам нужен аналог — данные, инспектируемые и расширяемые. Это второй из двух контрактов, которые дороже всего менять после релиза (первый — plugin API, ADR-0003), поэтому проектируется и замораживается рано.

## Драйверы решения

- Децентрализация: любой plugin добавляет свой ключ, не трогая ядро и другие plugins.
- Безопасность по построению: опечатка в ключе или невалидное значение — ошибка старта, не тихо проигнорированная политика.
- Ноль работы на hot path: merge и валидация — на построении таблицы.
- Переиспользуемость за пределами HTTP: те же метаданные на gRPC-методах и Kafka-handlers.

## Рассмотренные варианты

1. **Открытая map с namespaced-ключами, декларируемыми через extension point** `:void.http/route-meta-key`, + merge-семантика по слоям.
2. **Фиксированный struct route entry** — набор полей задаёт ядро; расширение требует изменения ядра.
3. **Регистрация политик отдельно от routes** (таблицы «route → policy» в каждом plugin) — расползание правды по plugins, `explain-route` невозможен.

## Решение

Вариант 1. Route metadata — открытая map; все ключи, кроме `:name`, **namespaced** (`:void.<plugin>/<key>`, `:app/<key>`). Каждый plugin декларирует свои ключи (schema, doc, merge-стратегия); ключ с опечаткой — ошибка старта с did-you-mean.

- **Merge-слои**: global → group → route; стратегии `:replace` / `:concat` / `:deep-merge` / `:restrict`. `:restrict` — специфичный слой может только ужесточать (timeout, rate limit, csrf) — ключевая гарантия для security-ключей.
- `:name` обязателен и глобально уникален → reverse routing, метрики, `explain-route`.
- Route table — immutable значение, пересборка атомарна (var swap).
- Merge прекомпилирован при билде таблицы; middleware с `:when`-предикатом по metadata вообще не входит в цепочку route, если предикат false.
- Reserved-ключи ядра v1 (таблица в SPEC Часть II §2.5) замораживаются; изменения — только через deprecation-процедуру.
- Контракт живёт в `void/core/meta`, не в void/http: non-HTTP протоколы (Connect-RPC, Kafka) используют тот же механизм.

## Последствия

Плюсы:

- Один endpoint-декларация интегрирует полдюжины plugins без связывания их между собой.
- `explain-route` показывает итог и происхождение каждого значения по слоям.
- Вся документация metadata генерируется из деклараций (`void routes --keys`).

Минусы / цена:

- Замороженный контракт: ошибка в дизайне reserved-ключей v1 живёт вечно (или через болезненный deprecation) — поэтому SPEC требует спроектировать до волны 1.
- Merge-семантика четырёх видов — когнитивная нагрузка; смягчается тем, что стратегия задаётся один раз при декларации ключа, а не автором route.
- Исключение для `:void.authz/policy` (semantically concat при merge-типе replace) — задокументированная неровность контракта.
