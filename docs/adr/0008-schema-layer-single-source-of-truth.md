# ADR-0008: Schema layer — один формат, много проекций; db-аннотации опциональны

- Статус: accepted
- Дата: 2026-08-25
- Связанные разделы SPEC: §3.3, §5.9 (entity), §5.3 (openapi), §5.21 (admin)

## Контекст и постановка проблемы

Одни и те же описания данных нужны валидации запросов, coercion query params, OpenAPI, protobuf, HTML-формам, генераторам тестовых данных, админке и миграциям. Если каждый потребитель описывает данные по-своему, правда расползается и рассинхронизируется (классика: OpenAPI врёт о реальном API).

## Драйверы решения

- Single source of truth: одна декларация питает все проекции.
- Расширяемость: plugins добавляют свои типы и свои проекции без изменения ядра.
- Человекочитаемые ошибки с path, локализация.
- Отделение «что такое данные» (валидация) от «как они хранятся» (db) — DTO и entity не должны быть разными мирами.

## Рассмотренные варианты

1. **Расширение spork/schema до Malli-уровня**: schemas как данные, проекции как функции, registry по имени.
2. **Взять spork/schema как есть** — недостаточно: нет композиции, coercion, проекций, registry.
3. **Отдельные декларации на потребителя** (валидация отдельно, OpenAPI отдельно, ORM отдельно) — статус-кво большинства фреймворков, источник рассинхрона.

## Решение

Вариант 1. `void/core/schema` — расширение spork/schema до Malli-уровня. Один формат → много проекций.

- Композиция: `merge`, `select`, `optional`, `union`, рекурсивные схемы; refinements предикатами; PEG-паттерны для строк.
- Coercion-режим (string→int для query params и форм).
- Ошибки с path (`[:tags 3]`), локализуемые (интеграция с void/i18n).
- **Проекции — отдельные функции**, plugins добавляют свои через `:void.core/schema-projection`: validator, JSON Schema/OpenAPI, protobuf descriptor, HTML form hints, генератор для property-based тестов, docs.
- Кастомные типы (`:money`, `:uuid`) — через `:void.core/schema-type`.
- Registry схем по имени → OpenAPI `$ref` и переиспользование.
- **Опциональные db-аннотации** (`:db/table`, `:db/pk`, `:db/fk`, `:db/rel`, `:db/index`, `:db/type`): не участвуют в валидации, но питают entity layer, void/admin и migrations-diff. Schema без них — обычный DTO; с ними — entity. DTO — проекция entity: `(schema/select User [:email :brand-id])`.

## Последствия

Плюсы:

- OpenAPI, формы, админка и фабрики тестов «бесплатны» и не могут рассинхронизироваться с валидацией.
- Плагинная расширяемость типов и проекций — тем же механизмом extension points (ADR-0003).
- Плавный градиент DTO → entity без смены формата.

Минусы / цена:

- Malli-уровень — большая работа ядра (композиция + coercion + пути ошибок + registry); недооценка сложности здесь бьёт по всем волнам.
- Каждая проекция должна осмысленно обрабатывать все конструкции схемы (или явно отклонять) — контрактная дисциплина.
- db-аннотации внутри schema смешивают слои намеренно; граница «не участвуют в валидации» должна жёстко соблюдаться.
