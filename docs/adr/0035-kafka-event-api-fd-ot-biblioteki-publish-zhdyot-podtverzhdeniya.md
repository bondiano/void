# ADR-0035: Kafka — event API вместо callbacks, fd от библиотеки вместо потоков; `publish!` ждёт подтверждения

- Статус: accepted (подтверждено работающим backend'ом и интеграционной сюитой)
- Дата: 2026-08-31
- Связанные разделы SPEC: §5.11, §5.22, §7 (прил.)
- Связанные ADR: [0010](0010-concurrency-ev-loop-prefork-tls-vne-yadra.md) (ни одного блокирующего syscall на loop), [0011](0011-async-libpq-cherez-c-shim.md) (`void/fdwait` — общий примитив «усыпи fiber до readiness чужого fd»), [0012](0012-jobs-i-bus-razdelnye-plaginy-outbox.md) (контракт `:void.bus/backend` и гарантии, которые читает router), [0033](0033-mysql-potok-na-soedinenie-i-tekstovyj-protokol.md) (противоположное решение для библиотеки, которой ждать нечего и негде)

## Контекст и постановка проблемы

`void/kafka` — последний backend из списка ADR-0012 и единственный, за которым стоит чужая инфраструктура, а не процесс или его база. Клиент — librdkafka: C-библиотека, которая сама держит пул потоков (по одному на брокера плюс внутренние), сама переподключается, сама батчит и сама разруливает ребалансировку групп. Интеграционный вопрос волны 5 — не «как говорить с Kafka», это librdkafka умеет лучше, чем мы напишем, — а **как её события попадают в Janet**, не нарушая двух правил: ни одного блокирующего вызова на ev loop (ADR-0010) и ни одного чужого потока внутри Janet VM.

SPEC (§5.11) записал набросок «callbacks → ev channels» — до чтения API. Наброском он и был: канонический интерфейс librdkafka действительно колбэчный (`dr_msg_cb`, `rebalance_cb`), но колбэк — это C-функция, которую библиотека вызовет на **своём** стеке, и путь к нему из Janet лежит через native-модуль с трамплином и через вопрос «в какой VM мы сейчас», на который у чужого потока нет хорошего ответа.

Второй вопрос — семантика `publish!` для контракта шины. Kafka — единственный наш транспорт, где «отдал сообщение» и «сообщение сохранено» разделены сетевым путём: `rd_kafka_produce*` кладёт сообщение во внутреннюю очередь и возвращается немедленно, а подтверждение брокера приезжает позже, delivery report'ом. Backend, который объявит `:durable true` (а без этого его не примет outbox — `require-durable!`), обязан решить, в какой момент публикация становится фактом.

## Драйверы решения

- Ни одного блокирующего syscall на loop — правило, а не предпочтение (ADR-0010). У librdkafka блокирует и `rd_kafka_consumer_poll`, и `rd_kafka_flush`, и `rd_kafka_metadata` — пользоваться нельзя ничем из этого списка.
- Ни одного вызова Janet из чужого потока. Потоки librdkafka живут своей жизнью, и VM для них не существует.
- Гарантии backend'а — декларация, которую router **читает** (ADR-0012): retry выключается под `:at-least-once`, outbox требует `:durable`. Объявленное обязано быть правдой.
- FFI без varargs. `rd_kafka_producev` — вариадическая функция, а вариадический вызов через `ffi/` не переносим: на darwin/aarch64 вариадические аргументы уходят на стек, и сигнатура, объявленная как фиксированная, кладёт их в регистры.
- Ни одной захардкоженной раскладки структуры, которую нельзя проверить или которую заголовок не фиксирует сам (урок ADR-0033).
- Контракт `:void.bus/backend` не меняется: восемь ключей и блок гарантий писались под streams с consumer groups (ADR-0012, уточнение 4) — пришло время проверить это утверждение, не трогая шов.

## Рассмотренные варианты

### Как события библиотеки попадают в Janet

1. **Event API + fd от библиотеки + `void/fdwait`.** У librdkafka есть вторая, бесколбэчная поверхность — очереди событий: `rd_kafka_queue_poll` с timeout 0 возвращает `rd_kafka_event_t` или NULL и не блокирует никогда, а `rd_kafka_queue_io_event_enable` просит библиотеку писать байт в **наш** fd при переходе очереди из пустой в непустую. Фибра паркуется на readiness этого fd через `void/fdwait` — ровно тот общий примитив, который SPEC §7 обещал: «librdkafka имеет свой poll-механизм, но паттерн тот же».
2. **Callbacks через native-трамплин.** Требует C-кода, дисциплины «колбэк только ставит флаг», и всё равно сводится к «разбуди Janet» — то есть к варианту 1, но с трамплином посередине.
3. **Поток на клиента (модель ADR-0033):** `ev/thread` крутит блокирующий `rd_kafka_consumer_poll`, ответы через threaded channels. Работало бы, но ADR-0033 выбрал потоки потому, что у libmysqlclient **нет** неблокирующего API — ждать нечего и негде. Здесь есть и API, и fd; N лишних OS-потоков и маршалинг каждого сообщения через границу VM — цена за то, чтобы не прочитать документацию до конца.
4. **Свой wire protocol на чистом Janet** (как `void/redis` для RESP). Протокол Kafka — это версионируемые API keys, ребалансировка групп, идемпотентный продюсер и сжатие четырьмя кодеками. Несопоставимо с задачей волны 5.

### Момент истины `publish!`

1. **Ждать delivery report:** `publish!` возвращается, когда брокер подтвердил запись (`acks=all` по умолчанию), и бросает, когда доставка не удалась. Фибра паркуется, loop работает.
2. **Fire-and-forget:** вернуться сразу после `rd_kafka_produceva`, ошибки считать статистикой. Быстрее на порядок — и `:durable true` становится ложью ровно в том месте, где на него опирается outbox: forwarder пометил бы строку отправленной, пока сообщение ещё лежит в очереди процесса, который можно убить.

## Решение

**События — вариант 1. `publish!` — вариант 1.** Пакет `kafka` содержит два plugin'а — `void/kafka` (клиент: producer-компонент и consumer-примитив) и `void/kafka-bus` (вклад `:kafka` в `:void.bus/backend`) — раскол `void/cache` — `void/cache-redis`, чтобы приложение, говорящее с Kafka напрямую, не composило шину, и наоборот.

### Насос событий: fd → fdwait → `queue_poll`

У каждого клиента (producer или consumer) — своя очередь событий, свой pipe(2) и одна фибра-насос:

    ждать readiness read-конца через fdwait → выпить pipe →
    (rd_kafka_queue_poll q 0) до NULL, раздавая события → снова ждать

Схема не теряет пробуждений по построению: NULL от `queue_poll` означает «очередь пуста», значит следующее событие — это переход «пустая → непустая», на котором библиотека пишет байт. `void/fdwait` level-triggered, гонки нет. Все вызовы librdkafka — только с loop-потока; её собственные потоки Janet не видят никогда.

pipe открывается через `ffi/` (pipe/read/close из libc): janet-стрим своего fd не отдаёт, а fd нужен обоим — библиотеке, чтобы писать, и `fdwait`, чтобы спать.

### Producer: `produceva` и подтверждение как возврат

Сообщение уходит через `rd_kafka_produceva` — не-вариадический близнец `producev`, принимающий **массив** `rd_kafka_vu_t`. Раскладку этой структуры фиксирует сам заголовок: хвост союза — `char _pad[64]` с комментарием «padding size for future-proofness», то есть vtype по 0, союз по 8, шаг 72 — это обещание ABI, а не наша догадка (разница с `MYSQL_BIND`, из-за которой ADR-0033 отказался от prepared statements).

`publish!` кладёт в сообщение opaque — порядковый u64-токен, — паркуется на канале и просыпается, когда насос выловит delivery report с этим токеном. Отчёт с ошибкой (таймаут доставки, слишком большое сообщение, нет такой партиции) — это `error` из `publish!`, у вызывающего кода. Ограничение по времени даёт сама библиотека: `message.timeout.ms` гарантирует, что отчёт придёт — тем или иным.

### Consumer: группы — кафковские, offset хранится после обработчика

`consume!` `{:group ...}` — это `group.id`: единица fan-out контракта шины и consumer group Kafka совпали без переходника, что ADR-0012 и обещал. Каждый `consume!` — свой `rd_kafka_t` консьюмера со своим насосом.

At-least-once собирается из двух настроек: `enable.auto.commit=true`, `enable.auto.offset.store=false`. Библиотека коммитит фоном **только то, что мы явно положили** в store, — а кладём мы offset после того, как `deliver` вернулся. Бросивший обработчик offset не сдвигает; сообщение уже у нас в руках, и backend передоставляет его сам — с паузой, счётчиком `:redelivery` в meta и головой партиции, ждущей своей очереди (то же head-of-line, что у курсора `void/bus-db`: порядок дороже прогресса). Ограничивает переигрывание poison-middleware, включённый по умолчанию; процесс, умерший между обработкой и коммитом, отдаст сообщение заново — направление отказа то же, что у forwarder'а outbox: дубликат, а не потеря.

### Гарантии, объявленные вслух

    :delivery :at-least-once   :ordering :none
    :durable  true             :shared   true

`:ordering :none` — самое честное слово из двух, которые есть в контракте: Kafka упорядочивает внутри партиции, а `:per-group` обещает порядок публикации группе целиком — через топики и партиции такого порядка нет. Приложение, которому нужен порядок по ключу, задаёт `:key` в meta сообщения — он становится ключом Kafka и выбирает партицию.

### На проводе: value — это payload, остальное — в headers

Value кафковского сообщения — тело через кодек шины и ничего больше; `:id` и meta едут в headers (`void-id`, `void-meta`). Консьюмер **не из void** читает payload, не зная о нас; консьюмер из void получает корреляцию и trace-контекст. Топик — keyword шины со слэшем, заменённым на точку (`:user/created` → `user.created`, обратно на приёме); символ вне алфавита Kafka — ошибка публикации, называющая топик. `[:kafka-bus :prefix]` отделяет приложения, делящие кластер.

### Границы блокировок — названы, а не спрятаны

Три места, где librdkafka хочет заблокировать, и что вместо этого:

- **flush при остановке** — цикл «`rd_kafka_outq_len` → парковка» под дедлайном, вместо `rd_kafka_flush`;
- **закрытие консьюмера** — `rd_kafka_consumer_close_queue` (асинхронная половина close) и парковка до `rd_kafka_consumer_closed`;
- **`rd_kafka_destroy`** джойнит потоки библиотеки и остаётся коротким блокирующим вызовом в `:stop` после осушенных очередей — та же сделка на выключении, что drain у prefork-мастера.

Проверка на старте — та же забота, что keeper-соединения драйверов БД («неверный брокер должен уронить boot, а не первый запрос»), но у Kafka нет момента «connect»: `rd_kafka_new` не ходит в сеть и не умеет не получиться. Ближайший честный аналог — DescribeCluster через тот же event API (admin-запрос, ответ — событие, парковка на fdwait). Символ появился в librdkafka 2.3; на библиотеке старше он объявлен optional (механика `load!` из ADR-0033), проверка пропускается и говорит об этом в лог.

## Последствия

Плюсы:

- Ни одного нового потока и ни одного native-модуля: библиотека сама даёт fd, `void/fdwait` уже умеет на нём спать. SPEC §7 закрыт в обе стороны — примитив действительно обобщился.
- `publish-tx!` — и значит, события о деньгах — работают через Kafka без оговорок: `:durable` подтверждён брокером на каждом сообщении.
- Монолит переезжает на Kafka сменой двух строк конфига (`[:bus :backend] :kafka` и брокеры) — обещание ADR-0012, теперь проверенное на самом дальнем backend'е.
- Payload на проводе читается чужими консьюмерами: headers наши, value — нет.

Минусы / цена:

- **`publish!` стоит round-trip до брокера.** Это цена честного `:durable`; путь «мне только сигнал» — это `:memory` backend или прямой producer `void/kafka` с fire-and-forget, выбранный осознанно.
- Раскладки `rd_kafka_vu_t` и `rd_kafka_message_t` читаются по смещениям. Обе — документированный публичный ABI (первая западдена заголовком «for future-proofness», вторая неизменна с 0.8), но это всё же смещения; интеграционная сюита гоняет round-trip на живом брокере.
- Ребалансировка отдана библиотеке целиком: между revoke и assign группа может получить дубликаты — это свойство at-least-once Kafka, а не наше, но читать об этом будут в нашем баг-трекере.
- `rd_kafka_destroy` в `:stop` блокирует на время джойна потоков библиотеки.

## Отступления от наброска SPEC

Два, оба в сторону меньшего API:

1. «callbacks → ev channels» из §5.11 не случились: event API делает то же без трамплинов и без каналов — см. выше.
2. Extension point `:void.kafka/handlers` не объявлен. Обработчик на топике с группой — это ровно `defhandler` шины при `[:bus :backend] :kafka`; вторая точка с той же семантикой была бы второй декларацией одного факта (аргумент ADR-0029/0031 — расходиться нечему, когда декларация одна). Прямой consumer `void/kafka` остаётся примитивом для приложений, читающих чужие топики мимо конверта шины.
