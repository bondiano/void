# ADR-0015: Свой HTTP-сервер; spork/http — референс и донор парсеров

- Статус: proposed
- Дата: 2026-08-25
- Связанные разделы SPEC: §5.1, §7 п.1, §8.2 (бюджеты B0–B1)
- Закрывает открытый вопрос №1 SPEC

## Контекст и постановка проблемы

`void/http` нужен production-сервер: keep-alive, лимиты, таймауты, graceful drain, chunked, SSE, буферные пулы под GC-бюджеты. SPEC требовал решить «обернуть или переписать spork/http» после чтения исходников. Исходники прочитаны (spork/http.janet, ~530 строк вместе с клиентом); аудит по критериям §7.1:

- **Keep-alive отсутствует**: `server-handler` обрабатывает один запрос и закрывает соединение (`defer (:close conn)`); цикла чтения запросов нет. Бюджет B0 (≥ 20k RPS) при connection-per-request недостижим.
- **Лимитов нет**: `read-header` читает до `\r\n\r\n` без max-header-size (memory DoS), `read-body` не знает max-body.
- **Таймаутов нет** ни на одну операцию (slowloris).
- **Graceful drain отсутствует** — тонкая обёртка над `net/server`.
- Chunked-чтение через `read-until` идёт по 1 байту за syscall; chunk extensions/trailers не обрабатываются (TODO в коде).
- **Пригодное к переиспользованию**: PEG-грамматики request/response/query-string/cookie (корректные: lowercase-имена заголовков, дубли — в массивы), таблица status-messages, `write-body` с авто-chunked — суммарно ~150 строк.

## Драйверы решения

- Перформанс-бюджеты §8.2 — контракт фреймворка; ключевые для них свойства (keep-alive, пулы буферов) должны контролироваться нами.
- Keep-alive, лимиты и таймауты не добавляются обёрткой — они меняют цикл соединения, т.е. ядро сервера.
- Минимизация собственного кода в опасной зоне (байтовый парсинг из сети) — наследовать проверенное, где возможно.
- Эволюция под нашу дорожную карту (SSE, drain, `:workers :auto`) без согласования с апстримом spork.

## Рассмотренные варианты

1. **Свой сервер; из spork/http забрать PEG-грамматики, status-таблицу и write-body; spork/http остаётся референсом поведения.**
2. **Обернуть spork/http** — фактически потребовало бы переписать `server-handler`, `read-header`, `read-body` (всё серверное ядро), оставив зависимость ради 30% кода; интерфейс (закрытие в defer, `:connection` в request) конфликтует с Ring-моделью и drain.
3. **Контрибьютить keep-alive/лимиты в апстрим spork** — цикл интеграции долгий, приоритеты апстрима — простота, не production-фичи; не исключается как параллельная деятельность, но блокировать волну 1 этим нельзя.
4. **C-сервер (ffi к libh2o/подобным)** — противоречит принципу «C только где Janet не может» (ADR-0011); парсер уже быстрый через PEG (C-движок).

## Решение

Вариант 1: **свой сервер в `void/http`**, спроектированный вокруг цикла соединения:

- fiber на соединение; цикл: read request (с таймаутом и max-header) → dispatch → write response → keep-alive решение по `Connection`/versionу; leftover-буфер сохраняется для следующего запроса (pipelining — читаем, отвечаем последовательно).
- Лимиты первым классом: max-header, max-body (route metadata `:void.http/max-body`, merge `:restrict`), таймауты (idle, read, `:void.http/timeout`), лимит соединений.
- Graceful drain: стоп accept → дождаться in-flight с таймаутом → close (интеграция с SIGTERM из lifecycle, §3.6).
- Переиспользуемые буферы per-connection (`buffer/clear`, пул) — под GC-бюджеты §8.2.
- Из spork/http наследуются: PEG-грамматики (request/response/query/cookie), status-messages, схема авто-chunked записи. Дальнейшие расхождения не синхронизируются — это форк идей, не кода-зависимость.
- SSE и chunked-стриминг ответа — часть контракта сервера с самого начала (нужны htmx/datastar и WS-соседям).
- Клиентская часть spork/http (`http/request`) может использоваться как есть до появления собственного клиента.

Валидация решения — бенчмарками B0/B1 (ADR-0014): свой сервер обязан пройти бюджеты, ради которых его пишем.

## Последствия

Плюсы:

- Keep-alive, лимиты, таймауты и drain — в дизайне цикла, а не прикручены; бюджеты B0–B1 достижимы.
- Самая рискованная часть (парсер) наследуется проверенной; свой код — управление соединением, где ошибки менее коварны, чем в парсинге.
- Контракт сервера эволюционирует с фреймворком без внешних согласований.

Минусы / цена:

- HTTP-сервер — поверхность для security-ошибок (request smuggling на границах content-length/chunked); нужны целевые тесты на smuggling-векторы и фаззинг парсера границ.
- Поддержка навсегда наша: RFC-краевые случаи (100-continue, trailers, обрывы) — наш бэклог.
- Старт волны 1 дороже на недели относительно «взять как есть» — но аудит показал, что «как есть» не проходит ни один критерий §7.1, так что реальная дельта меньше номинальной.
