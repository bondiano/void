# ADR-0025: `void/security` — CSRF по признаку кукиных полномочий, заголовки на краю, лимиты поверх контракта кэша

- Статус: accepted
- Дата: 2026-08-28
- Связанные разделы SPEC: §5.16, часть II §1.4 (фазы), §2.5 (`:void.security/csrf`, `:void.security/rate`)
- Связанные ADR: [0019](0019-pressure-load-shedding.md) (отказ раньше, чем стоимость), [0005](0005-route-metadata-otkrytyj-kontrakt.md), [0016](0016-request-lifecycle-imenovannye-stadii.md) (стадии), [0022](0022-kriptografiya-cherez-libcrypto.md) (примитивы и их цена), [0023](0023-auth-identity-i-strategii.md) (кто отмечает полномочие кукиным)

## Контекст и постановка проблемы

Четыре вещи, которые в Rails/Laravel/Spring включены по умолчанию и без которых серверный HTMX-фреймворк нельзя выпускать: CSRF, security-заголовки с CSP, rate limiting, CORS. Каждая из них выглядит тривиально и в каждой есть по одному решению, которое определяет, будет ли она работать в реальном приложении:

- **CSRF** ломает JSON-API, если включён «глобально по методу», и не защищает ничего, если выключается по желанию маршрута. При этом ключ `:void.security/csrf` заморожен в v1 со стратегией слияния `:restrict` — более частный слой может только **ужесточить**, то есть `false` на группе поверх `true` глобально невозможен by design.
- **Заголовки** должны стоять на **каждом** ответе, а 404, 405 и статика в void отвечаются **вне** цепочки маршрута (`make-handler`), то есть вне досягаемости middleware.
- **Rate limiting** без общего состояния бесполезен в prefork (ADR-0010) и во флоте; счётчик по IP, который верит `X-Forwarded-For`, подделывается заголовком.
- **CORS** должен отвечать на preflight там, где маршрута ещё нет.

## Драйверы решения

- Ни одного нового контракта хранилища: `:void/cache-store` уже описывает «строки с TTL и атомарным инкрементом», и у него уже есть memory- и redis-реализация.
- Безопасное по умолчанию: небезопасный дефолт, который «настраивается», — это дефолт, который в проде остался.
- Отказ должен стоить дёшево: 429 платится до разбора тела (довод ADR-0019).
- Ни `void/auth`, ни `void/authz` не должны быть обязательны: CSRF нужен приложению без логина.

## Рассмотренные варианты

**CSRF:**

1. Проверять по методу (POST/PUT/PATCH/DELETE) всегда. Отвергнут: ломает каждый JSON-API с Bearer-токеном, а `:restrict` не позволяет выключить это на группе — пришлось бы не включать вовсе.
2. Double-submit cookie без подписи. Отвергнут: субдомен, которому позволено ставить куки, обходит его.
3. **Проверять запросы, чьи полномочия принесены кукой.** Принято.

**Rate limiting:** свой контракт backend'а против переиспользования `:void/cache-store` — принято второе.

## Решение

### 1. CSRF применяется к тому, что вообще подвержено CSRF

Правило времени запроса, а не метаданных: **проверяем небезопасный метод, если запрос пришёл с кукой-полномочием** (сессионная кука есть, или identity получена стратегией, читающей куку). Запрос с `Authorization: Bearer` браузер сам к чужому сайту не приложит — CSRF там не существует, и проверять нечего.

Это снимает противоречие с `:restrict`: базовое поведение — свойство запроса, а метаданные умеют только **ужесточать** (`:void.security/csrf true` — «требовать токен на этом маршруте всегда, даже для API-клиента»), что ровно и означает семантика «true wins», замороженная в v1. Ключа «выключить» нет и не будет.

Токен приходит скрытым полем формы (слот `(dyn :void.html/csrf)` ждёт этого с волны 1), заголовком `x-csrf-token` для htmx (`(security/htmx-meta)` кладёт `<meta>` + `hx-headers` на `<body>`) и куки-дублем для JS-клиентов. Сравнение — за постоянное время, всегда.

### 2. Токен один, и он всегда подписан

Серверная сессия позволила бы обойтись синхронайзер-токеном — случайной строкой в сессии, без единого криптографического вызова. Так сделано не будет: тогда в пакете жили бы **два** токена — синхронайзер для форм и подписанный для stateless double-submit (API без сессии, где проверять негде, а неподписанный double-submit обходится через субдомен, которому позволено ставить куки). Два режима — это две кодовые дороги, два набора тестов и вопрос «а этот токен подписан?» на каждом ревью.

Поэтому токен один: `HMAC-SHA256` (`void/crypto`) над значением куки, которую ставит сам модуль, с меткой времени и сроком жизни внутри. Проверка не ходит в хранилище.

Привязка — именно кука, а не id сессии, хотя вторая была бы крепче: страницу с формой очень часто рендерит тот же запрос, который сессию и создаёт (форма и `Set-Cookie` уезжают вместе), так что в момент выпуска токена id сессии ещё не существует — и токен, привязанный к нему, был бы отвергнут ровно на том потоке, ради которого он выпущен. Остаточный риск — cookie tossing с поддомена; лечится он не подписью, а префиксом `__Host-`, который браузер не примет ни с поддомена, ни без `Secure` и `Path=/`. `[:security :csrf :cookie]` = `"__Host-void-csrf"` — рекомендация для любого деплоя с чужими поддоменами; дефолтом это не сделано только потому, что `__Host-` требует https, а `void dev` его не имеет.

Цена этого единообразия названа в ADR-0022: `void/security` **требует `void/crypto`**, то есть приложение с формами не запустится без libcrypto. Это принятый размен — один путь кода против одной внешней библиотеки, которая в этой волне и так становится обязательной для входа по паролю.

Секрет подписи — `[:security :signing-key]` (не `:secret`: значение вида `{:secret "NAME"}` — это ссылка на переменную окружения в конфиг-слое, ADR-0007, и литеральная строка под таким ключом читалась бы как имя переменной), обязательный в prod-профиле (его отсутствие — ошибка старта, не предупреждение) и эфемерный со `warn` в dev, чтобы `void new` работал из коробки. Ротация — список ключей: подписываем первым, проверяем любым.

### 3. Заголовки и CORS ставятся на краю, а не в цепочке маршрута

Middleware в void оборачивает **цепочку маршрута**; 404, 405 и статика собираются в `make-handler` вне её, а ответ, отрендеренный panic-guard'ом, не проходит обратный путь внутренних обёрток. Значит, security-заголовки как middleware отсутствовали бы ровно на тех ответах, где они особенно нужны (404 с отражённым путём, 500 со стектрейсом в dev).

Поэтому `void/http` получает **новую точку `:void.http/edge`** — обёртка вокруг всего обработчика, снаружи panic-guard: `{:name :phase :wrap}`. Это добавление контракта, а не его изменение (v1 замораживает существующие точки от мутаций, не запрещает новые). Оттуда работают заголовки (`x-content-type-options`, `referrer-policy`, `strict-transport-security`, `permissions-policy`, CSP) и CORS-preflight, который обязан отвечать и на путь, где маршрута нет.

CSP собирается из данных (`{:default-src [:self] :script-src [:self "https://unpkg.com"] :frame-ancestors [:none]}`), а не из строки: строка не проверяется, не сливается по слоям и не печатается объяснением. Директива с nonce требует, чтобы шаблон его вставил, — `(security/nonce)` доступен из hiccup; дефолтная политика nonce не использует, потому что молча сломанный inline-скрипт хуже отсутствующей директивы.

`report-only`-режим — переключатель конфига: единственный способ включить CSP на живом приложении, не сломав его.

### 4. Rate limiting стоит на контракте кэша, а не на своём

Лимитеру нужны «ключ → счётчик с TTL и атомарным инкрементом». Это в точности `:void/cache-store` (ADR волны 2), у которого уже есть memory-реализация, redis-реализация и честный ответ на вопрос «атомарен ли инкремент» (`store/atomic-incr?`). Своего контракта не будет: он был бы тем же самым, с двумя реализациями-близнецами.

`[:security :rate :store]` — `:memory` (встроенный в security, чтобы пакет работал в одиночку) или `:cache` (хранилище композиции; с `void/cache-redis` лимит становится общим для prefork-воркеров и для флота). Если стор не атомарен (memory при `:workers > 1`), это **предупреждение на старте** с указанием, что лимит теперь на воркер, — а не молчаливое умножение лимита на число процессов.

Алгоритм — скользящее окно на двух счётчиках (текущее окно + взвешенный хвост предыдущего): один инкремент и одно чтение на запрос, без всплеска ×2 на границе окна, который даёт фиксированное окно. Отказ стора — **fail-open** по умолчанию (`[:security :rate :on-error :allow|:deny]`): недоступный redis не должен превращать «защиту от перебора» в «отказ в обслуживании», и это ровно тот же выбор, что у `void/cache` («сбой стора деградирует в промах, а не в 500»).

Ответ — 429 через error-renderers, `Retry-After` и заголовки `RateLimit-*`; ключ — `:ip` (по умолчанию), `:subject` (identity из dyn-ключа `void/auth`, без импорта пакета) или символ приложения.

### 5. Две фазы лимитера, выбор — на сборке таблицы

Лимит по IP стоит в **фазе 200** — сразу после panic-guard и shedding (ADR-0019), до разбора тела, сессии и соединения с базой: перебор паролей не должен оплачивать сессию. Лимит по субъекту физически не может стоять там — identity ещё нет, — и стоит в **фазе 4400**, после auth (4000). Какой из двух обёрток обёрнут маршрут, решает предикат `:when` по метаданным на сборке таблицы, а не проверка на запросе.

### 6. Клиентский IP — вычисляемое значение, а не заголовок

`X-Forwarded-For` — это ввод пользователя, пока не доказано обратное. `[:security :trusted-proxies]` (список CIDR, по умолчанию **пустой**) задаёт, скольким хопам справа можно верить; `(security/client-ip req)` возвращает первый недоверенный адрес, и без конфигурации это просто peer сокета. Пустой список по умолчанию означает, что за прокси лимит сначала будет общим на прокси — заметная, чинимая одной строкой ошибка; обратный дефолт означал бы лимит, обходимый заголовком, чего никто не заметит.

## Последствия

Плюсы:

- CSRF, который не приходится выключать: правило совпадает с моделью угрозы, а не с методом запроса, и не воюет с `:restrict`.
- Заголовки на 404, 405, статике и 500 — потому что точка приложения выбрана по факту устройства обработчика, а не по удобству.
- Ни одного нового контракта хранилища; общий лимит во флоте появляется от добавления `void/cache-redis` в композицию.
- Пакет работает без `void/auth`, `void/authz`, `void/cache` и redis: каждый из них добавляет возможность (субъектный лимит вместо адресного, общий счётчик во флоте), ни один не обязателен. Обязателен ровно один — `void/crypto`.

Минусы и цена:

- Новая точка `:void.http/edge` в пакете волны 1 — рост контракта (добавление, не мутация), и её надо описать в CONTRACTS.md и заморозить вместе с остальным.
- CSRF теперь стоит libcrypto: приложение с одной формой и без логина всё равно требует OpenSSL 3 (ADR-0022). Это сознательный размен в пользу одного пути кода.
- Правило CSRF «по кукиным полномочиям» требует от `void/auth` честной отметки, какая стратегия читала куку; для приложения с самописной аутентификацией остаётся признак «в запросе есть сессия».
- fail-open лимитера — сознательный выбор в пользу доступности; приложению, которому нужен fail-closed, придётся сказать это конфигом.
- Пустой список доверенных прокси означает, что типовой деплой за nginx требует одной строки конфига, иначе лимит считается по адресу прокси.
