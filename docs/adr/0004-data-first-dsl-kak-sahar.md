# ADR-0004: Data first — DSL-макросы только как сахар над данными

- Статус: accepted
- Дата: 2026-08-25
- Связанные разделы SPEC: §2.1, Часть II (весь документ построен на этом принципе)

## Контекст и постановка проблемы

Lisp-фреймворки склонны к макро-DSL, где конфигурация «живёт» внутри макросов и недоступна как значение: её нельзя инспектировать, генерировать программно, диффать или сериализовать. Одновременно фреймворк обещает Spring-уровень интеграций — а интеграции требуют, чтобы plugins могли читать чужие декларации.

## Драйверы решения

- REPL-инспектируемость всего: routes, schemas, policies, manifests — `pp`, diff, запрос.
- Интеграция plugins между собой: OpenAPI читает routes и schemas, admin читает entity-декларации, obs читает route metadata — это возможно только если декларации — данные.
- Генерация деклараций кодом (например, codegen из `.proto`).
- Сериализуемость: lock-файлы, экспорт, кэши сборки.

## Рассмотренные варианты

1. **Данные первичны, макросы — сахар**: `defplugin`/`defroute`/`defschema` разворачиваются в plain structs/tables, помещаемые в registries.
2. **Макро-DSL первичен**: декларации существуют только как код; инспекция требует парсинга исходников.
3. **Внешние конфиг-файлы** (YAML/EDN-style): данные, но оторванные от кода — теряется compile-time проверка и REPL-цикл.

## Решение

Вариант 1: **всякая декларация — значение**. Routes, schemas, policies, components, plugin manifests, route metadata — structs/tables. DSL-макросы (`defplugin`, `defcomponent`, `defschema`, `GET`, `defentity`) — тонкий сахар, разворачивающийся в конструирование данных + регистрацию.

Проверочный критерий для каждого API: можно ли собрать ту же декларацию без макроса, из чистых данных, и получить идентичное поведение. Если нет — API спроектирован неверно.

## Последствия

Плюсы:

- Любой plugin может читать чужие декларации через registry — фундамент всех «бесплатных» проекций (OpenAPI, admin, MCP, ER-диаграммы).
- REPL-инструменты (`plugin/inspect`, `explain-route`, `config/explain`) реализуются тривиально.
- Тестируемость: декларации сравниваются как значения.

Минусы / цена:

- Каждому DSL нужен «двойной» дизайн: формат данных (публичный контракт) + макрос (сахар). Формат данных менять дороже, чем макрос.
- Данные не проверяются компилятором — вся валидация ложится на schema-контракты registries (см. ADR-0003).
