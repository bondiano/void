# ADR-0016: Request lifecycle — именованные стадии как публичный контракт

- Статус: accepted (реализован в v0.1)
- Дата: 2026-08-26
- Связанные разделы SPEC: §5.1, часть II §1.4 и §2.5
- Референс: [Fastify Lifecycle](https://fastify.dev/docs/latest/Reference/Lifecycle/)

## Контекст и постановка проблемы

`void/http` исполняет запрос через прекомпилированную цепочку фазовых middleware (константы 0–9000, SPEC ч. II §1.4). Модель мощная, но публичный контракт сформулирован в числах, а не в смысловых точках: автор plugin'а должен сам догадаться, что «после 2000 тело распарсено», а «после 6000 прошла валидация». Fastify показывает ценность именованного lifecycle: разработчик вешается на стадию по имени, точно зная, что на ней уже доступно; вся документация и обучение строятся вокруг одной диаграммы `onRequest → preParsing → preValidation → preHandler → preSerialization → onSend → onResponse`.

Кроме того, три точки в принципе не выразимы middleware-обёрткой:

- **после записи ответа в сокет** (`onResponse`) — единственное честное место для access-log и метрики полной длительности;
- **при ошибке** (`onError`) — до error-renderer'а, с доступом и к request, и к исключению;
- **при таймауте handler'а** (`onTimeout`) — сервер отменяет handler-task по `:void.http/timeout` (ADR-0015 п. 2), и об этом сейчас никто не может узнать.

## Драйверы решения

- Однозначный контракт «что доступно на какой стадии» — до заморозки контрактов v0.1 (стадии станут reserved-частью metadata-контракта).
- Никакого второго runtime-механизма: hot path остаётся одной прекомпилированной цепочкой (perf-бюджеты §8.2, прекомпиляция — ч. II §2.6).
- Fastify-паритет по выразительности: route-level hooks, короткое замыкание из hook'а, `:on-response`/`:on-error`/`:on-timeout`.
- Late binding: hooks — символы, живое редактирование в REPL (ADR-0002).

## Рассмотренные варианты

1. **Именованные стадии как тонкий слой над фазовой шкалой**: стадия = зарезервированный слот фазы, hooks компилируются в ту же цепочку при билде таблицы; плюс три внецепочечные точки в сервере/errors.
2. **Отдельная hook-система рядом с middleware** (как в Fastify, где hooks ≠ middleware) — два механизма исполнения, два порядка, двойная документация; на hot path — вторая диспетчеризация.
3. **Оставить только фазовые числа и документировать их** — не закрывает `:on-response`/`:on-error`/`:on-timeout`; «что когда доступно» остаётся конвенцией, а не контрактом.

## Решение

Вариант 1. Стадии v1 (замораживаются вместе с остальными контрактами к v0.1):

| Стадия | Слот | Сторона | Контракт стадии |
|---|---|---|---|
| `:on-request` | 1500 | запрос | routing свершился, `(request :void/route)` есть; request-id/log-context установлены (фаза 1000); тело — сырые байты |
| `:pre-parsing` | 1900 | запрос | последний шанс до body-кодеков (фаза 2000) |
| `:pre-validation` | 5900 | запрос | тело/сессия/auth есть; до schema-валидации (фаза 6000) |
| `:pre-handler` | 9900 | запрос | вся цепочка пройдена, последним перед handler'ом |
| `:pre-serialization` | 9800 | ответ | значение handler'а до рендера (hiccup/данные, до lazy-view рендера и кодеков) |
| `:on-send` | 500 | ответ | финальный response table перед записью: заголовки и тело в окончательном виде |
| `:on-response` | — | вне цепочки | после записи ответа в сокет; ничего не меняет |
| `:on-error` | — | вне цепочки | при исключении, до `:void.http/error-renderer` |
| `:on-timeout` | — | вне цепочки | при отмене handler-task по `:void.http/timeout` |

Направление следует из механики цепочки: наименьшая фаза — внешняя обёртка, поэтому запросные стадии идут сверху вниз, а ответные (`:pre-serialization`, `:on-send`) срабатывают на пути наружу — `:pre-serialization` (слот 9800, внутренняя) видит сырое значение handler'а раньше рендерящих middleware (9000+), `:on-send` (слот 500, внешняя) — последним перед сервером.

**Регистрация.** Глобально — новая точка `:void.http/hook`:

```janet
(contribute! :void.http/hook
  {:stage :on-request :name :tenant-resolve :fn 'my-app.tenant/resolve})
```

Per-route — metadata-ключ `:void.http/hooks` (merge `:concat` по каждой стадии, group-хуки раньше route-хуков):

```janet
(GET "/orders/:id" show {:void.http/hooks {:pre-handler ['my-app.orders/require-owner]}})
```

**Семантика.** Hook запросной стадии — `(fn [request] ...)`: nil/request — продолжить, response-map — короткое замыкание (остаток цепочки и handler пропускаются, ответные стадии отрабатывают). `:pre-serialization`/`:on-send` — `(fn [request response])` → response. `:on-response` — `(fn [request response])`, результат игнорируется. `:on-error` — `(fn [request err])`, может вернуть response вместо стандартного рендера. Hooks — символы (late binding); function-literal допустим в тестах.

**Компиляция.** На билде route table hooks каждой стадии сортируются детерминированно (plugin → name, как middleware) и вклеиваются в цепочку route тонкими wrapper'ами. Route, не имеющий hooks на стадии, не платит ничего — пустой слот не порождает wrapper. `:on-response` и `:on-timeout` вызывает сервер (и inject-путь — ADR-0017 — тем же кодом), `:on-error` — errors-механизм.

**App-level lifecycle** уже покрыт `void/core/hooks` (`:config-loaded`, `:before-start`, `:after-start`, `:before-stop`, `:after-stop`). Добавляются серверные хуки `:void.http/listening` (после bind), `:void.http/draining` (начало drain) и `:void.http/route-added` — на каждый route entry при билде таблицы (аналог Fastify `onRoute`: plugins валидируют и дополняют metadata, не дожидаясь запроса).

## Последствия

Плюсы:

- Один механизм исполнения; неиспользуемые стадии бесплатны; фазовые middleware остаются для тех, кому нужна настоящая обёртка «вокруг» (hook — точка, middleware — скобки).
- Документация lifecycle — одна диаграмма; контракт «что доступно» перестаёт быть фольклором.
- Access-log/метрики получают честное «до последнего байта» (`:on-response`); таймауты и ошибки становятся наблюдаемыми точками.
- Inject-тесты (ADR-0017) проходят ровно те же стадии — паритет socket/inject путей проверяется одним набором тестов.

Минусы / цена:

- Слоты и имена стадий — замороженный контракт: менять больно, поэтому фиксируем до v0.1 и обкатываем на access-log (ADR-0018) и pressure-middleware (ADR-0019).
- Появляется «два способа сделать похожее» — нужен короткий гайд «hook vs middleware» в docs plugin'а.
