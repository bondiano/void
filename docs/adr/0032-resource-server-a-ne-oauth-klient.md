# ADR-0032: OAuth в void — сначала **resource server**, а не клиент; аудитория обязательна

- Статус: accepted
- Дата: 2026-08-30
- Связанные разделы SPEC: §5.18 (`void/mcp`), §5.14 (`void/auth`), §5.16 (`void/security`), §5.20 (`void/oauth`, волна 5), часть II §2 (route metadata)
- Связанные ADR: [0010](0010-concurrency-ev-loop-prefork-tls-vne-yadra.md) (TLS вне процесса), [0022](0022-kriptografiya-cherez-libcrypto.md) (вся криптография — из libcrypto), [0023](0023-auth-identity-i-strategii.md) (identity как данные, стратегия как вклад), [0024](0024-authz-abac-kak-dannye.md) (идентичность читается из dyn, а не импортируется), [0025](0025-security-csrf-zagolovki-limity.md) (CSRF по кукиным полномочиям), [0027](0027-otlp-eksport-json-i-http-klient.md) (HTTP-клиент как часть ядра), [0030](0030-forma-razvertyvaniya-i-razdelyaemye-hranilisha.md) (хранилища за пределами процесса), [0031](0031-mcp-kak-proekciya-i-vorota-po-umolchaniyu.md) (MCP как проекция; ворота эндпоинта)

## Контекст и постановка проблемы

ADR-0031 оставил у MCP-эндпоинта один замок — общий bearer-токен из конфига — и назвал это открытым хвостом. Для одного оператора с одним агентом этого достаточно; для чего угодно больше — нет: общий секрет нельзя выдать конкретному агенту, нельзя отозвать у одного, не сменив у всех, и он ничего не говорит о том, **что** этому агенту позволено.

MCP отвечает на это своей спецификацией авторизации, и она короткая: MCP-сервер — это **OAuth 2.1 resource server**. Не клиент: он никого не логинит, ничего не редиректит и никаких refresh-токенов не хранит. Он делает три вещи — проверяет предъявленный access token, убеждается, что токен выпустили **для него**, и рассказывает клиенту, у какого authorization server токен брать.

Отсюда четыре вопроса:

1. **Чей это код.** `void/oauth` из волны 5 — это OAuth-*клиент* («войти через Google»): редиректы, code+PKCE, обмен кода на токен. Resource server — другая половина, и ждать волны 5 ради неё значит держать MCP-эндпоинт на общем секрете полгода.
2. **Как проверяется токен.** JWT проверяется локально по ключам издателя (и тогда нужен JWKS, то есть JWK → ключ, который откроет libcrypto); непрозрачный токен проверить локально нельзя вообще, для него есть introspection (RFC 7662). Что из этого обязательно?
3. **Что делает токен «нашим».** Это главный вопрос: без ответа на него токен, выданный чат-приложению, открывает **все** сервисы, доверяющие тому же издателю.
4. **Как об этом узнаёт `void/mcp-http`** — не превращаясь при этом в плагин, зависящий от `void/auth`.

## Драйверы решения

- Токен, выданный для другого сервиса, не должен открывать этот — иначе фреймворк раздаёт confused deputy по умолчанию.
- Отказ обязан говорить, **куда идти за токеном**: клиент, получивший голый 401, не может починить себя сам.
- Проверка токена не имеет права ходить в сеть на каждом запросе.
- Ни одна ошибка конфигурации, из-за которой сервер принимал бы лишнее, не должна быть умолчанием — только отказом на старте.
- Плагин MCP не должен знать, чем именно установлена идентичность; иначе каждая новая форма аутентификации требует правки в MCP.
- Ничего нового в криптографии (ADR-0022): всё, чего нет, — это кодировка.

## Рассмотренные варианты

**Чей это код.** (1) Ждать `void/oauth` волны 5 — отвергнуто: клиент и resource server пересекаются в одном месте (метаданные издателя) и решают разные задачи; связывать их значит откладывать вторую до первой. (2) Отдельный пакет `void/oauth-rs` — отвергнуто: он состоял бы из идентичности, стратегии и route metadata, то есть из `void/auth` целиком. (3) **`void/auth-oauth` — плагин в пакете `void/auth`** — принято: то же разделение, что `void/cache` — `void/cache-http`, приложение с сессиями и паролями не компонует ни строки этого.

**Как проверяется токен.** (1) Только introspection — отвергнуто: сетевой вызов на каждом запросе, и издатель становится частью горячего пути. (2) Только JWT — отвергнуто: непрозрачные токены есть у половины развёртываний, и «поменяйте формат токенов» — не ответ. (3) **Оба, и режим называется вслух** (`[:auth-oauth :mode]` `:jwt`/`:introspect`/`:auto`): JWS проверяется локально по JWKS, всё остальное уходит на introspection, если он настроен. Принято. JWKS кэшируется, неизвестный `kid` стоит **одного** перезапроса за кулдаун — иначе выдуманный `kid` превращается в запрос к издателю на каждый запрос к нам.

**JWK → ключ.** `void/crypto/sign` открывает ключи из PEM, JWKS публикует base64url-числа. (1) Байндинги `EVP_PKEY_fromdata` — отвергнуто: новые ffi-байндинги ради того, что уже есть. (2) **Кодировщик JWK → PEM** (`void/auth/jwk`, ~150 строк DER): это не криптография, а SubjectPublicKeyInfo из четырёх TLV и двух OID'ов из RFC. Проверяется единственным способом, который что-то доказывает, — сравнением байт в байт с PEM, который для тех же ключей написал OpenSSL.

**Что делает токен нашим.** (1) Проверять только подпись и срок — отвергнуто, и это ровно тот дефект, ради которого MCP написал свою секцию авторизации: у издателя, выпускающего токены для десяти сервисов, любой из них открывал бы остальные девять (RFC 9700 «confused deputy», RFC 8707 — параметр `resource`, которым клиент просит аудиторию). (2) Проверять `aud`, если он есть — отвергнуто: «если есть» означает «токен без аудитории подходит всем». (3) **`[:auth-oauth :audience]` обязателен и сверяется всегда**; композиция без него **не стартует**. Принято. То же для introspection: `active: true` значит «токен жив», а не «токен наш», поэтому `aud`/`iss`/`exp` проверяются и там.

**Алгоритмы.** Приняты только асимметричные: список — конфигурация, никогда не заголовок токена (это правило уже было в `void/auth/jwt`), а HS* в этом списке — **ошибка старта**, потому что ключ, которым resource server проверяет HMAC, это ключ, которым он может *выпускать* токены. Тогда он не resource server.

**Где кончается 401 и начинается 403.** Приняты обе границы RFC 6750: нет годной учётки — 401 и `WWW-Authenticate` с `resource_metadata` (RFC 9728), учётка годная и не даёт права — 403 `insufficient_scope` с перечислением нужных scope. Клиент повторяет первое и не повторяет второе; сервер, отвечающий 401 на оба, заставляет его повторять то, что не изменится.

**Как об этом узнаёт `void/mcp-http`.** (1) Ребро на `void/auth` — отвергнуто: тогда MCP по HTTP требует конкретной аутентификации, и это уже второе место, где решается, кто пользователь. (2) **Читать dyn-ключ `:void.auth/identity`** — принято, и это буквально то, ради чего ADR-0023 сделал ключ именованным контрактом, а ADR-0024 запретил `void/authz` импортировать `void/auth`. `[:mcp-http :auth] :identity` + `[:mcp-http :scopes]` работают с OAuth-токеном, с сессионной кукой и с чужой аутентификацией одинаково, а `void/mcp-http` не знает ни одной из них.

**Кто отвечает 401 на маршруте, где есть и `:bearer`, и `:oauth`.** Стратегия `:oauth` встала **раньше** `:bearer` в цепочке — не из-за учётных данных (обе читают один заголовок, и `:oauth` пропускает токен void на первом же взгляде), а из-за отказа: у API-токена void нет документа, на который можно показать, а у resource server он есть. Маршрут, которому нужен другой порядок, называет его сам — `:void.auth/strategies` для этого и существует.

## Решение

### 1. `void/auth-oauth` — resource server, и ничего кроме

Стратегия `:oauth` (вклад в `:void.auth/strategy`) читает `Authorization: Bearer`, пропускает API-токены void, проверяет остальное и возвращает identity: `sub` — субъект, а для machine-to-machine токена без `sub` субъект — `client_id`. Дальше это обычная идентичность void: её видит `void/authz`, её видит `void/security` (и не требует CSRF, потому что `:cookie false`), её видит приложение.

Компонент `:auth.oauth/keys` держит открытые ключи издателя: **лениво** (сервер, который не видел ни одного токена, не звонил издателю ни разу; издатель, который лежит, не мешает приложению стартовать), с TTL, с кулдауном на перезапрос и с освобождением заменённых ключей — это единственное место, где кончается время жизни ключа (ADR-0022 говорит, что финализатора у `ffi/` нет).

### 2. Аудитория, а не только подпись

`[:auth-oauth :audience]` — канонический URI этого сервера. Он сверяется с `aud` у JWT и у ответа introspection; его отсутствие — ошибка старта с текстом про confused deputy. Он же — источник URL документа метаданных, чтобы одно и то же не пришлось настраивать дважды.

### 3. Метаданные защищённого ресурса (RFC 9728)

`GET /.well-known/oauth-protected-resource` отдаёт `resource`, `authorization_servers`, `scopes_supported`, `bearer_methods_supported`. Путь фиксирован — его фиксирует RFC, и клиент, у которого есть только URL сервера, обязан найти документ, не спрашивая. Каждый отказ несёт `resource_metadata="…"` — это и есть ответ на «а где брать токен».

### 4. Scope как route metadata

`:void.auth/scopes` — ключ с merge `:concat`: группа и маршрут складываются, потому что маршрут внутри защищённой группы нуждается во всём, что нужно группе. Проверка — middleware в фазе **4500**, между аутентификацией (4000) и авторизацией (5000): scope это факт о выданном токене, а не решение о субъекте — решения принимает `void/authz` (ADR-0024), и здесь ему ничего не переопределяется.

### 5. `void/mcp-http` получил `[:mcp-http :auth]`

`:token` — общий секрет (как было), `:identity` — идентичность из dyn-ключа плюс `[:mcp-http :scopes]`, `:none` — ничего, и в `:prod` это **ошибка старта**, текст которой называет три выхода в порядке масштаба: OAuth-идентичность, общий токен, или собственный маршрут с `:void.authz/policy`. Композиция, просящая замок без ключа (`:auth :token` без токена, scope без `:identity`), тоже не стартует.

### 6. Чего здесь нет

Нет клиента: ни authorization code, ни PKCE, ни хранения refresh-токенов — это `void/oauth` волны 5, и он будет пользоваться теми же метаданными издателя. Нет динамической регистрации клиентов (RFC 7591) — её выполняет authorization server, а не ресурс. Нет собственного authorization server: выдавать токены — отдельный продукт, и void его не пишет. TLS по-прежнему снаружи (ADR-0010), а значит `https://` в `audience` — это то, чем сервер представляется, и терминируется он релеем рядом.

## Последствия

**Хорошо.** MCP-эндпоинт закрывается тем же способом, каким закрываются эндпоинты у всех остальных: токеном, выданным конкретному агенту, с конкретными scope, отзываемым у него одного. Отказ говорит клиенту, куда идти. Проверка JWT не ходит в сеть. Всё это — обычная идентичность void, поэтому `void/authz`, аудит через шину и `void/security` работают на MCP-запросе, ничего про MCP не зная. Побочно: у `void/auth` появился JWKS, которого не было, и `void/oauth` волны 5 начнётся не с нуля.

**Цена.** В пакете лежит DER-кодировщик — сто пятьдесят строк, которые придётся защищать от каждого следующего читателя (тест против OpenSSL делает это первым). Ключи издателя — C-указатели с ручным временем жизни, поэтому у них есть компонент. Стратегия `:oauth` встала перед `:bearer`, и это порядок, который приложение может захотеть переопределить — способ назван в самой стратегии. `void/mcp-http` читает форму scope (`scope` строкой и `scp` массивом) второй раз, отдельно от `void/auth-oauth`: пять строк ценой одного отсутствующего ребра между пакетами.

**Открыто.** Кэш JWKS — per-process по построению (это публичные ключи, перечитываемые из сети), и под `[:deploy :shape] :fleet` он ничего не нарушает; отдельного объявления в `:void.core/store` он не требует, потому что хранилищем в смысле ADR-0030 не является. Introspection не кэшируется вовсе — у ответа есть срок, но кэш ответов authorization server'а это уже политика, и её стоит настраивать, а не угадывать. Ротация ключей проверена только через «неизвестный `kid` → один перезапрос»; сценарий с двумя издателями одновременно не поддержан и не притворяется поддержанным.
