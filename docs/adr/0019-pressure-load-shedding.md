# ADR-0019: `void/pressure` — load shedding по образцу under-pressure

- Статус: proposed
- Дата: 2026-08-26
- Связанные разделы SPEC: §5.23 (новый), §8.2, §8.4
- Референс: [fastify/under-pressure](https://github.com/fastify/under-pressure)

## Контекст и постановка проблемы

Однопоточный ev-loop процесс под перегрузкой деградирует нелинейно: очередь accept растёт, loop-lag тянет за собой latency **всех** запросов, GC добивает, и процесс становится неотзывчивым для всех вместо «медленным для части». Fastify решает это плагином under-pressure: процесс сам сэмплирует event-loop delay / heap / rss и, перешагнув порог, отвечает 503 + `Retry-After` — быстро и дёшево, пока ещё может.

SPEC §8.4 называет loop-lag «главным health-индикатором», но мерить его планировал только `void/obs` (волна 3), а **реагировать** — никто: наблюдаемость без защиты. Reverse-proxy лимиты (ADR-0010: TLS/LB снаружи) не заменяют её — прокси не видит loop-lag и GC конкретного воркера.

## Драйверы решения

- Управляемая деградация: быстрый 503 части запросов вместо таймаутов у всех.
- Hot path не платит: проверка давления — одна атомарная операция на запрос.
- Prefork-схема (ADR-0010): у каждого воркера свой loop — давление и защита обязаны быть per-worker.
- Минимальное ядро (ADR-0006): shedding — policy, а не механизм HTTP, значит plugin.

## Рассмотренные варианты

1. **Отдельный plugin `void/pressure`** (выбран).
2. **Встроить в `void/http`** — против ADR-0006; сервер даёт механизмы (лимиты соединений, таймауты), политика перегрузки — надстройка.
3. **Ничего, положиться на reverse proxy** — прокси не видит внутренние сигналы процесса; см. выше.
4. **Ждать `void/obs`** — obs мерит и экспортирует, но shedding — не его ответственность; к тому же волна 3 далеко, а B2/B3-бенчи (волна 2) уже упрутся в поведение под перегрузкой.

## Решение

Plugin `void/pressure` (волна 2, зависит только от core + http):

- **Sampler-компонент**: fiber с интервалом `:sample-interval` (default 1 s) снимает:
  - **loop-lag** — дрейф `ev/sleep`: просили X, проснулись через X+lag (та же метрика, что §8.4);
  - **heap** — статистика janet GC;
  - **rss** — `getrusage` через ffi, где платформа даёт;
  - **custom-проверки** — extension point `:void.pressure/check` (many): `(fn [] {:ok bool :reason ...})` — пул БД исчерпан, очередь jobs растёт и т.п.
- **Пороги в конфиге**: `:max-loop-lag` (ms), `:max-heap-bytes`, `:max-rss-bytes`; любое превышение (или неуспешный check) → состояние `:under-pressure` (атомарный флаг + причины). Выход из состояния — гистерезис (порог восстановления ниже порога срабатывания), чтобы не мигать.
- **Middleware в раннем слоте (100)** — сразу после `:phase/panic-guard`, до parsing/session (отбрасываем раньше, чем потратились): под давлением → **503 + `Retry-After`** (config, default 10 s) через стандартный error-путь — problem+json при подключённом `void/rest`, обычный рендер иначе. На спокойном пути — одна проверка флага.
- **Исключения**: metadata-ключ `:void.pressure/exempt true` (merge `:replace`, декларируется через `:void.http/route-meta-key`) — `/health`, `/metrics`, drain-эндпоинты не режем.
- **Наблюдаемость**: contribution в `:void.core/health` (degraded + причины), `(pressure/status)` в REPL, события `:pressure/high` / `:pressure/recovered` в hooks-шину (алерты, автоскейл слушают); отвергнутые запросы логируются через `void/core/log` (ADR-0018) со счётчиком. Метрики заберёт obs в волне 3.
- **Prefork**: sampler живёт в каждом воркере (свой loop — своё давление); master агрегирует в свой health. SO_REUSEPORT сам делает остальное: перегруженный воркер отвечает мгновенным 503 и не копит очередь, kernel раскидывает новые соединения.

Пороги по умолчанию калибруются от бюджетов §8.2: в норме loop-lag p99 < 1 ms, порог срабатывания — на порядки выше (практика under-pressure: десятки–сотня ms); окончательные значения фиксируются по результатам B2/B3.

## Последствия

Плюсы:

- Деградация под перегрузкой становится контрактом, а не сюрпризом; B2/B3-бенчи получают осмысленное поведение на насыщении.
- Loop-lag появляется в системе на волну раньше obs — health и bench используют его сразу.
- Дешёвая интеграция: hooks-шина, health, error-renderer, metadata — всё уже существует.

Минусы / цена:

- Ещё один сэмплирующий fiber (дёшево, но в бюджете §8.2 учитывается).
- Пороги требуют калибровки на целевом железе; неверный `:max-loop-lag` либо молчит, либо режет здоровый трафик — поэтому гистерезис и события recovery обязательны с первой версии.
- 503 от приложения увидят внешние health-чекеры LB — документировать паттерн «`/health` exempt + LB routing по health».
