# ADR-0017: Тестирование через inject — полный стек без сокета

- Статус: proposed
- Дата: 2026-08-26
- Связанные разделы SPEC: §4, §5.1
- Референс: [Fastify Testing](https://fastify.dev/docs/latest/Guides/Testing/) / light-my-request

## Контекст и постановка проблемы

Fastify задал стандарт тестирования HTTP-приложений: `app.inject({method, url, payload})` прогоняет запрос через **весь** стек — routing, hooks, парсинг, валидацию, сериализацию — без единого сокета. Тесты быстрые (нет портов, таймаутов, flaky-биндингов в CI), детерминированные и проверяют ровно тот код, что работает в production.

У void уже есть зачаток — `(http/with-request {...})` (REPL-хелпер, ROADMAP 1.1). Но до inject-паритета не хватает:

- **HTTP-компонент всегда биндит сокет**: kernel (роутер + цепочки) и сервер — один компонент; тестовая система не может поднять «приложение без порта».
- Нет клиента с состоянием: cookie jar для сессионных сценариев (login → авторизованный запрос), базовые заголовки.
- Тело ответа может остаться lazy view (hiccup до рендера), chunked/SSE-ответы не наблюдаемы — `with-request` возвращает response до серверной сериализации, т.е. **не** те байты, что ушли бы в сокет.
- Нет сахара `:json`/`:form` и парсинга ответа.

## Драйверы решения

- Скорость и детерминизм тестов: никаких портов и сетевых таймаутов в CI.
- Fidelity: тест должен видеть те же байты и проходить те же lifecycle-стадии (ADR-0016), что и сокетный путь.
- Дешёвые сессионные сценарии (формы + CSRF + session — основной кейс HTMX-приложений волны 1).
- `void/test` уже умеет поднимать подмножество системы (`:only`) и подменять компоненты — inject должен на это лечь, а не дублировать.

## Рассмотренные варианты

1. **Реальный сервер на эфемерном порту + HTTP-клиент** — медленно, flaky (порты, таймауты), требует клиента, SSE/drain недетерминированы; тестируется транспорт, который и так покрыт e2e-тестами сервера.
2. **Звать handler-функции напрямую (unit)** — минует middleware, hooks, рендер и кодеки; уже возможно и остаётся для unit-уровня, но не отвечает на вопрос «работает ли endpoint».
3. **Inject: прогон через полный стек в памяти** (выбран).

## Решение

Вариант 3, тремя частями.

**1. Разделение компонентов в `void/http`**: `:http/kernel` (route cell, компиляция цепочек и hooks, итоговый handler — чистая часть, ноль I/O) и `:http/server` (`:deps [:http/kernel]` — сокет, keep-alive, drain, prefork-режим). Тестовая система поднимает `:only [:http/kernel]` — приложение «готово» (все contributions разрешены, hooks `:after-start` отработали), но порт не занят. Это же используют `with-request`/REPL.

**2. `test/client` + `test/inject` в `void/test`**:

```janet
(test/with-http [c {:plugins [my-app/plugin]}]      # старт (:only kernel) → клиент → stop в defer
  (def login (test/inject c {:method :post :uri "/login"
                             :form {:email "a@b.c" :password "pw"}}))
  (assert (= 303 (login :status)))                   # set-cookie ушёл в jar клиента
  (def resp (test/inject c {:uri "/orders" :json {:title "x"}}))
  (assert (= "x" (get-in (test/json resp) [:title]))))
```

- Клиент держит **cookie jar** (`set-cookie` ответов применяется к следующим запросам) и базовые заголовки — сессионные сценарии без ручного протаскивания.
- Сахар запроса: `:json x` (encode + content-type), `:form {...}` (urlencoded), `:headers`, `:body`; либо `:raw` — сырой байтовый запрос, прогоняемый через **тот же wire-парсер**, что и сервер (тесты лимитов, smuggling-векторов, malformed input).
- Хелперы ответа: `(test/json resp)`, `(test/text resp)`, `(test/sse-events resp)`.

**3. Fidelity-контракт inject-пути.** Запрос проходит: routing → lifecycle-стадии ADR-0016 → middleware → handler → рендер lazy views → body-кодеки → `:on-send`; затем ответ **сериализуется в память тем же wire-кодом** (`write-head`/`write-body`, chunked/SSE — накопленные фреймы/события), после чего вызывается `:on-response`. Результат — response table плюс `:raw` (финальные байты «как в сокет»). Единственное отличие от production-пути — транспорт; всё остальное — общий код, не эмуляция.

Fixtures/стабы — уже существующие `test/start!` `:only`/`:components` (стаб session-store, фейковый mail и т.д.); клиент их не дублирует, а принимает готовый boot: `(test/client boot &opt opts)`.

## Последствия

Плюсы:

- Тысячи запросов в секунду в тестах, ноль портов в CI; demo-приложения волны 1 тестируются целиком (формы, CSRF, session, HTMX-фрагменты).
- Общий wire-код гарантирует: то, что видит тест, — то, что уйдёт в сокет; расхождение socket/inject — баг по построению, а не по договорённости.
- `:raw`-режим даёт дешёвый фаззинг парсера (бэклог ADR-0015 про smuggling/края RFC).

Минусы / цена:

- Рефакторинг http-компонента на пару kernel/server (изменение манифеста и health; prefork остаётся в server).
- Сокетные edge-cases (partial reads, реальный drain, backpressure) inject не покрывает — они остаются за e2e-тестами сервера (уже есть с 1.1); граница обязанностей фиксируется в docs `void/test`.
