# ADR-0003: Plugin API — явный manifest + extension points вместо classpath-скана

- Статус: accepted
- Дата: 2026-08-25
- Связанные разделы SPEC: §2.4, §3.4, Часть II §1

## Контекст и постановка проблемы

«Batteries included» требует расширяемости уровня Spring auto-configuration: plugin должен уметь приносить компоненты, CLI-команды, middleware, health checks, метрики — без ручной проводки в каждом проекте. Spring решает это скана classpath и аннотациями — магия, которую невозможно инспектировать. Нужен эквивалент по мощности, но явный и данный.

## Драйверы решения

- Полная инспектируемость: `(plugin/inspect)` показывает «кто-куда-что» зарегистрировал.
- Fail fast: битые contributions, опечатки, конфликты — ошибки старта, не рантайма.
- Дистрибуция plugins как обычных janet-пакетов (`bundle/` + `jpm`), без спец-инфраструктуры.
- Эволюция контракта без breaking changes (см. `:void-api`).

## Рассмотренные варианты

1. **Явный manifest (`defplugin`) + extension points с контрактами** — проект перечисляет plugins явно, внутри plugin всё авторегистрируется.
2. **Classpath/каталог-скан** — авто-обнаружение по конвенции путей; магия, недетерминизм, не инспектируется.
3. **Ручная проводка** (Ring/Express-style) — каждый проект сам собирает middleware-стек и компоненты; максимум контроля, ноль «batteries».

## Решение

Вариант 1. Plugin = janet-пакет, экспортирующий **manifest** — замороженный struct (`pp`-able, диффабельный, сериализуемый) с `:void-api`, `:version`, `:requires` (semver), `:config-key`/`:config-schema`, `:when` (условная активация), `:components`, `:contributes`, `:extension-points`, `:on-load`.

**Extension point = именованный контракт**: schema вкладов + `:cardinality` (`:many`/`:single`/`:single-required`) + функция-свёртка `:reduce` + опциональный `:validate`.

Bootstrap — семь фаз до открытия портов: load → config → conditional → extension resolution → graph → start → ready. Гарантии фазы extension resolution:

- каждый вклад валидируется по schema точки, ошибка указывает plugin-источник;
- вклад в несуществующую точку → ошибка с did-you-mean;
- точка с вкладами, но без владельца в активном множестве → ошибка;
- нарушение cardinality → ошибка с перечислением кандидатов.

`plugin/dry-run` прогоняет фазы 1–5 без старта — полная валидация конфигурации системы в CI за миллисекунды. `void plugins lock` пишет lock-файл (plugin, version, contributions hash) для диффа окружений.

## Последствия

Плюсы:

- Spring-плагинистость без Spring-магии: добавил plugin в список — получил всё; удалил — не осталось следов (критерий готовности из SPEC).
- Все ошибки конфигурации — на старте, пачкой, с указанием источника.
- Manifest как данные → lock-файлы, диффы, генерация документации.

Минусы / цена:

- Явный `(use-plugins [...])` — на одну строчку больше, чем «просто положи jar в classpath».
- Дизайн extension point (schema + reduce) — плата за каждую новую точку расширения; дешёвые ad-hoc хуки запрещены.
- Механика семи фаз — самая сложная часть core; её нужно зафиксировать рано (это самый дорогой для изменения контракт).
