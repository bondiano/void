# ADR-0034: `void/oauth` — клиент code+PKCE; сессия вместо нового хранилища; identity отдаёт приложение

- Статус: accepted
- Дата: 2026-08-31
- Связанные разделы SPEC: §5.20 (`void/oauth`, волна 5), §5.14 (`void/auth`), §6 (волны)
- Связанные ADR: [0010](0010-concurrency-ev-loop-prefork-tls-vne-yadra.md) (TLS вне процесса), [0022](0022-kriptografiya-cherez-libcrypto.md) (криптография из libcrypto), [0023](0023-auth-identity-i-strategii.md) (identity как данные; фреймворк не знает, что такое пользователь), [0025](0025-security-csrf-zagolovki-limity.md) (подписанные токены `void/security`), [0027](0027-otlp-eksport-json-i-http-klient.md) (HTTP-клиент ядра), [0030](0030-forma-razvertyvaniya-i-razdelyaemye-hranilisha.md) (разделяемые хранилища под `:fleet`), [0032](0032-resource-server-a-ne-oauth-klient.md) (resource server; метаданные издателя, JWK → PEM)

## Контекст и постановка проблемы

ADR-0032 сделал первую половину OAuth — resource server: «мне предъявили токен, годен ли он». Вторая половина — клиент: «войти через провайдера» — редиректы браузера, authorization code + PKCE, обмен кода на токены, проверка id_token. ADR-0032 закончил словами, что клиент «начнётся не с нуля»: метаданные издателя (RFC 8414/OIDC discovery), JWKS-кольцо ключей и `void/auth/jwk` уже написаны и протестированы.

Пять вопросов, на которые клиент обязан ответить:

1. **Где живёт состояние между двумя запросами.** Между редиректом на authorization server и callback'ом проходят секунды, но это два разных HTTP-запроса — а под `[:deploy :shape] :fleet` возможно и два разных процесса. Где лежат `state`, PKCE-verifier и `nonce`?
2. **Как back-channel говорит с издателем без TLS.** ADR-0010: TLS в процессе нет, `https://` — ошибка разбора URL у `void/http/client`. Token endpoint любого публичного провайдера — https.
3. **Что происходит после проверки.** Токены обменяны, id_token проверен — но фреймворк не знает, что такое пользователь (ADR-0023). Кто превращает claims в identity и запись в таблице?
4. **Кто хранит refresh-токены.** Roadmap называет «хранение refresh» — но чьё это хранилище?
5. **Чей это пакет.** В пакете `void/auth` уже четыре плагина; клиент — это маршруты, конфигурация провайдеров и своя точка расширения.

## Драйверы решения

- Ни одного нового хранилища, если существующее уже даёт нужную гарантию (ADR-0030: session store под `:fleet` разделяем по построению).
- PKCE — не опция: OAuth 2.1 требует его для всех клиентов, включая конфиденциальные.
- `redirect_uri` никогда не выводится из `Host`-заголовка — это инъекция чужого хоста в параметр, который authorization server сверяет буквально (RFC 9700).
- Токен и claims — attacker-controlled вход: ни один из них не имеет права доехать до 500.
- Фреймворк не решает, кто пользователь: маппинг claims → identity — код приложения (ADR-0023).
- Ничего нового в криптографии: SHA-256, случайность и подписи уже есть (ADR-0022).

## Рассмотренные варианты

**Где живёт pending-состояние.** (1) Новый контракт хранилища — отвергнуто: контракт, компонент, `:shared?`-вопрос ADR-0030 и две реализации ради записи, живущей десять минут. (2) Подписанная/шифрованная кука (double-submit) — отвергнуто: verifier — секрет флоу, подпись его не прячет, значит нужно шифрование, которого в `void/crypto` нет и которое пришлось бы добавлять ради куки. (3) **Сессия** — принято: флоу начинается из браузера, session middleware уже стоит (фаза 3000), запись `{:state :verifier :nonce :next :at}` кладётся в `(req :session)` и читается callback'ом **один раз** (удаляется до любых проверок). Под `:fleet` session store уже обязан быть разделяемым (ADR-0030) — флоу переживает балансировщик по построению, и ни одной строчки про это писать не пришлось.

**Back-channel и TLS.** (1) Добавить TLS в клиент — отвергнуто: это ADR-0010, и он не пересматривается походя. (2) Молча позволить https и падать на первом обмене — отвергнуто: ошибка нашлась бы в проде на первом логине. (3) **Разделить каналы и сказать это на старте** — принято. Front-channel (authorization endpoint) — URL, на который редиректится **браузер**; браузер умеет TLS сам, поэтому `https://accounts.google.com/...` в `:authorization-endpoint` легален. Back-channel (metadata, token, JWKS, userinfo) зовёт `void/http/client`, поэтому https в любом из этих значений — **ошибка старта** с текстом про два выхода: внутренний издатель по http (Keycloak/Dex/Authentik в той же сети) или egress-релей рядом, терминирующий TLS наружу (тот же релей, что у `void/mail`). Https-`:issuer` при этом остаётся легальным как **строка сравнения** `iss` — но тогда back-channel-эндпоинты обязаны быть названы явно, и discovery не выполняется.

**Что происходит после проверки.** (1) `[:oauth :on-sign-in]` — функция в конфиге — отвергнуто: конфиг — данные, функции в нём не живут (ADR-0007). (2) Автосоздание пользователя в user store — отвергнуто: фреймворк не знает, что такое пользователь, и не решает, кому можно войти. (3) **Точка расширения `:void.oauth/sign-in`** (`:cardinality :single`) — принято: приложение отдаёт одну функцию `(fn [{:provider :claims :tokens :req}])`. Вернула identity — `void/oauth` зовёт `auth-http/login!` (ротация id сессии — фикс fixation достаётся бесплатно) и редиректит на `?next=` или `[:oauth :after-sign-in]`; вернула response — он уходит как есть (приложению виднее: онбординг, привязка аккаунта); вернула nil — 403, «приложение сказало нет» (домен не из списка). Маршруты смонтированы, а точка пуста — ошибка старта: флоу, у которого нет второй половины, не должен молча заканчиваться 500.

**Refresh-токены.** (1) Таблица пакета — отвергнуто: пакет не приносит миграций (та же поза, что `void/admin` §8 — админка не владеет таблицей). (2) **Токены — данные, отданные хуку**; их хранение — колонка приложения, у которого уже есть `void/db`. `oauth/refresh!` существует как функция (grant_type=refresh_token тем же token endpoint'ом), и ей всё равно, откуда взялся аргумент. Принято.

**Чей это пакет.** Пятый плагин в `auth/` — отвергнуто: у клиента свои маршруты, свой компонент, своя точка расширения и свой конфиг-ключ; ADR-0032 держал resource server в auth, потому что тот *состоял* из identity и стратегии — клиент из них не состоит, он ими **заканчивается**. **Отдельный пакет `oauth/`** с рёбрами `:void/core :void/crypto :void/http :void/auth` — принято: `void/auth` здесь ради модулей `jwk`/`jwt` (проверка id_token тем же кодом, что проверяет access token в ADR-0032) и ради `auth-http/login!`.

**Проверка id_token.** Тот же словарь, что ADR-0032: ключи издателя — JWKS через `jwk/signing-keys` + `sign/public-key`, кольцо с TTL и кулдауном на неизвестный `kid`, `alg` из конфигурации и никогда из токена, HS* в списке — **ошибка старта** (id_token, подписанный client_secret'ом, — симметричный ключ, который умеет выпускать). Сверяются `iss` (строка `:issuer`), `aud` (равен **client-id** — у клиента аудитория своя), `exp`/`nbf` с leeway, `nonce` (равен отправленному в этом флоу — replay id_token умирает здесь) и `azp`, когда он есть. `openid` в scope и отсутствующий id_token в ответе — отказ, а не пожатие плечами.

**Провайдер без OIDC.** GitHub-класс: id_token нет, профиль — нестандартный endpoint. (1) Каталог провайдеров в пакете — отвергнуто: каталог устаревает, а его записи — это чужие API. (2) **Claims из userinfo, когда он назван, иначе пустые** — принято: хук получает токены и достаёт профиль сам через `void/http/client`; у него есть всё, что есть у пакета.

## Решение

### 1. Плагин `void/oauth`, маршруты как у всех

`GET <mount>/:provider` строит authorize-URL (`response_type=code`, `client_id`, точный `redirect_uri`, `scope`, `state`, `code_challenge` S256, `nonce` при openid, `[:providers <p> :params]` сверху — `access_type=offline` живёт там), кладёт pending в сессию и отвечает 302. `GET <mount>/:provider/callback` — вторая половина: pending читается и удаляется одним движением, `state` сравнивается constant-time, возраст — против `[:oauth :max-age]`, `?error=` от издателя — отказ с кодом в логе и без кода в теле. Оба — обычные маршруты (`:void.auth/access :public`), поэтому `void routes`, `explain-route` и вся цепочка middleware работают, ничего не зная про OAuth. `?next=` принимается только локальным путём (`/…`, не `//…`) — open redirect через параметр не открывается.

### 2. Обмен кода — запрос как данные

`token-request` возвращает таблицу запроса (метод, URL, form, заголовки) — сюита утверждает, что уйдёт наружу, без сокета (форма `introspection-request` ADR-0032). Client credentials едут Basic'ом по умолчанию, `:post` — для издателя, который иначе не умеет; `code_verifier` едет всегда. Ответ обмена — JSON: `access_token`, `token_type`, `expires_in`, `refresh_token?`, `id_token?`, `scope?` — нормализуется в таблицу с keyword-ключами и отдаётся хуку вместе с сырым телом.

### 3. Redirect URI — из конфигурации, буквально

`[:oauth :base-url]` + mount + имя провайдера, либо `[:providers <p> :redirect-uri]` целиком. Ни того ни другого при смонтированных маршрутах — ошибка старта: URI, зарегистрированный у издателя, сверяется байтами, и выведенный из `Host` он был бы под контролем того, кто пишет заголовки (RFC 9700).

### 4. Компонент `:oauth/providers`

Кольцо на провайдера: метаданные издателя (кэш — эндпоинты не переезжают), ключи JWKS (лениво, TTL, кулдаун, освобождение при замене и на `:stop` — ADR-0022 про время жизни ключей). `void oauth check` печатает всю разрешённую картину — эндпоинты, redirect-uri, scope, алгоритмы — по каждому провайдеру, с той стороны конфига.

### 5. Чего здесь нет

Нет каталога провайдеров — провайдер это конфигурация. Нет implicit, hybrid и device flow — code+PKCE, один. Нет хранения токенов — см. выше. Нет собственного authorization server (ADR-0032 §6). Нет TLS (ADR-0010). Session-стратегии не добавилось: после `login!` работает та, что была, — вход через провайдера заканчивается обычной сессией void.

## Последствия

**Хорошо.** «Войти через провайдера» — конфигурация плюс одна функция приложения; всё, что защищает маршрут, защищает и эти два. Флоу переживает fleet без единого нового хранилища. Проверка id_token — тот же код, те же отказы и те же тесты, что у access token в ADR-0032. PKCE и точный redirect_uri — по построению, а не по чек-листу.

**Цена.** Публичный IdP требует egress-релей рядом — это честная цена ADR-0010, и она названа в ошибке старта. Пакет не помогает хранить refresh-токены — приложению, которому они нужны, придётся завести колонку. `:cardinality :single` у `:void.oauth/sign-in` означает один хук на композицию — диспетчеризация по провайдерам внутри него (он получает имя первым полем).

**Открыто.** `void/oauth-db` (хранилище связок subject ↔ provider ↔ tokens как opt-in плагин) — если три приложения подряд напишут одну и ту же таблицу. Logout у издателя (RP-initiated logout) не поддержан. Client credentials grant (machine-to-machine, без браузера) — функция на пять строк поверх того же `token-request`, когда попросят.
