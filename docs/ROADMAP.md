# ROADMAP: void

> Дорожная карта. Волны 0–5 (SPEC §6) закрыты; их историю хранят [CHANGELOG.md](../CHANGELOG.md) — проекция git-истории, — теги v0.1–v0.4 и [ADR 0001–0038](adr/README.md). Прежняя редакция этого документа с почеклисточной историей волн живёт в git (до 2026-09-01). Здесь — только то, что впереди.

**Правило зависимостей:** каждый plugin зависит только от `void/core` и plugins своей волны или более ранних. Волна закрывается по exit-критериям, а не по «код написан».

**Dogfooding:** вся разработка ведётся через netrepl внутри системы; каждый новый plugin строится на предыдущих.

## Волна 6 — паритет и первое приложение

Тема волны: закрыть то, обо что настоящее приложение спотыкается в первую неделю, но чего нет на фоне Laravel/Rails/Phoenix, — и собрать это приложение. Метрика — §9 дословно: время «идея → работающий деплой» и доля вертикали без выхода из стека. Каждый пакет — свой ADR; порядок внутри волны — по тому, что попросит приложение.

### 6.1 `void/storage` — файлы и загрузки *(L; [ADR-0039](adr/0039-hranilishe-fajlov-klyuch-kak-dannye.md))* ✅

Паритет: Laravel Storage / Rails ActiveStorage. Между multipart-парсингом и URL на странице теперь один шов, и он один и тот же для формы, admin и контроллера.

- [x] Контракт `:void/storage-store`: `put!`/`get`/`stream`/`delete!`/`url`; ключ и метаданные — данные
- [x] `:local`-store — диск (запись через tmp+rename), отдача через существующий static (etag/range) в `void/storage-http`
- [x] `:s3`-store — S3-совместимый API своим стеком: `http/client` + `void/tls` + SigV4 на `void/crypto`, проверенный на опубликованных векторах AWS
- [x] Signed/temporary URL — локально на ключах `void/security` (с ротацией), в bucket — SigV4 query auth
- [x] Шов с формами и admin: тип схемы `:file` + аннотации `:storage/*` → `input type=file` и `enctype` в `void/html`, виджет с превью и серверной проверкой в `void/storage-admin`
- [x] `:local`-store под `[:deploy :shape] :fleet` — та же проверка на старте, что у всех per-process хранилищ (ADR-0030)
- [x] `examples/shop`: картинка товара — одна строка в `defentity`, minio в `docker-compose.yml`

### 6.2 `void make auth` — auth-скаффолд *(M)* ✅

Паритет: phx.gen.auth / Laravel Breeze / Rails 8 authentication generator. Машинерия есть вся (`auth/password`, identity, strategies, `challenge!` + `mail-auth`, sessions) — но каждое приложение руками писало одни и те же страницы. Теперь пишет генератор, и reset с verify — один поток: `challenge!` + один redeem-роут, потому что доставщик строит один URL.

- [x] Генератор по образцу `make resource`: register/login/logout, reset и verify через `challenge!`; шаблоны — данные с проектными overrides (`templates/auth/<key>.janet`)
- [x] Сгенерированная сюита тестов через `test/inject` — со своим `:void.auth/deliver`, так что оба challenge проверяются без почтового ящика
- [x] Примеры не переписываются: скаффолд проверяется тем, что сам генерирует (`cli/test/make-auth-test.janet` гоняет сгенерированную сюиту на sqlite)

### 6.3 Jobs-дашборд *(S/M)* ✅

Паритет: Horizon / Sidekiq-web. `void/admin-jobs` был только раннером bulk-действий; теперь тот же plugin держит оба конца шва «админка × очередь» — зависимости у них одни и те же, а смотреть на очереди стало где. Не `defresource-admin`: очередь — не entity, у неё нет ни таблицы, ни pk, ни схемы, которую можно спроецировать, поэтому секция собрана из `:void.admin/page` поверх самого контракта.

- [x] Секция поверх `:void/jobs-backend` (восьми существующих функций хватило): карточки бэкенда и бэклога, таблица «очередь × состояние» со ссылками прямо в фильтр, листинг одного фильтра, одна запись целиком с её failures
- [x] Retry/discard для dead — обычные admin-действия под обычными политиками (`:admin.jobs/retry`, `:admin.jobs/discard`): сузить их — это `defpolicy` с этим именем и больше ничего, как у action'а ресурса
- [x] Ничего нового в контракте backend'а: `counts`, `list`, `fetch`, `retry!`, `remove!`, `clear!` — и границы оттуда же. Листинг по `:limit`, а не по страницам, потому что offset'а в контракте нет; bulk только по queue+state, потому что этой парой говорят `counts` и `clear!`; retry только для dead, потому что `revive!` не снимает claim и оживление записи, которую держит воркер, выполнит её дважды
- [x] `:void.admin/menu` научился `:path` (аддитивно — старые contribution'ы валидны): contribution — значение, замороженное на загрузке, а `[:admin :prefix]` — конфиг, так что plugin со своей страницей иначе не может назвать ссылку на себя

### 6.4 `void/notify` — единые нотификации *(M; [ADR-0040](adr/0040-notifikacii-odno-sobytie-neskolko-kanalov.md))* ✅

Паритет: Laravel Notifications; позиционирование §9 прямо называет «webhook/бот-хабы». Одно событие — один вызов; куда оно уйдёт, решает список плагинов. У канала не одна функция, а две — `project` там, где был запрос, `deliver` там, где сеть, — и ровно поэтому между ними помещается очередь, а повтор доставляет то же самое значение.

- [x] Точка `:void.notify/channel` по образцу `:void.mail/transport`; `:memory` и `:log` в ядре, mail-канал (`void/notify-mail`) из коробки — письмо строит `void/mail` и оно же его маршрутизирует через `mail/send-delivery`, так что `[:mail :queue]` продолжает значить то, что значило
- [x] `:webhook`-канал на `http/client`: тело — проекция уведомления, подпись `t=<unix>,v1=<hmac>` считается на доставке (schema Stripe), 4xx записывается, 5xx повторяется; telegram и прочие — приложением или пакетом по спросу
- [x] In-app канал: строка в таблице, которой владеет void (DDL данными — `(notify-store/tables)` в миграции), и htmx-колокольчик с четырьмя обычными маршрутами; получатель — личность из dyn, никогда не параметр
- [x] Отправка через `void/jobs` тем же приёмом, что `mail-jobs`, — ни одно место вызова не меняется; задача **на канал**, потому что упавший webhook не должен отправить письмо второй раз
- [x] В `:prod` композиция, у которой не осталось доставляющего канала, — ошибка старта: тот же отказ, что у `[:mail :transport]`

### 6.5 Assets: tailwind без node *(S)* ✅

Паритет: Phoenix (standalone esbuild/tailwind). Компиляция не стала стадией пайплайна: `assets/build!` получил `:steps` — thunk'и перед обходом, — и после них сгенерированного файла не существует. Стилевой файл лежит в asset root и фингерпринтится наравне с рукописным, а `html/asset` не отличает один от другого.

- [x] Standalone tailwind CLI: `locate` (`:bin` → кэш проекта → PATH; сеть — только по просьбе), `void assets install` через `http/client` + `:void/tls`, шаг `tailwind/step` в `assets/build!`, `--watch` как компонент `:html/tailwind` в `void dev`
- [x] Node в пути пользователя не появляется: ни npm, ни npx, ни `node_modules` — один статический бинарь в `.void/bin`, версия в имени файла
- [x] Отсутствие бинаря — фраза, а не тишина: ошибка называет платформу, все три места, где искали, и команду, которая это чинит; половина конфига (`:input` без `:output`) отклоняется на старте, а не на первой сборке
- [x] `void assets build` / `install` / `info` — три команды без `:needs`: сборка не открывает порт и не поднимает ни одного компонента

### 6.6 `examples/hub` — webhook/бот-хаб на чистой установке *(L)*

Приложение, которым закрывается волна: приём webhook'ов GitHub и доставка событий в telegram. Эту нишу §9 называет прямо («webhook/бот-хабы»), и она единственная, где исходящий канал — не украшение вертикали, а её половина.

Хаб живёт в `examples/`, но, в отличие от остальных примеров, **работает от установленного дерева, а не от module path checkout'а**: у него нет `test-support/paths.janet`, он импортирует `void/…` как посторонний. Это ставит его на существующую дорожку CI-джобы `install` («clean machine»), где сегодня проверяются только скаффолды, — и делает половину санитарного прохода волны 7 работой примера, а не отдельной задачей.

Слабое место выбора названо заранее: у бот-хаба нет аватарок, то есть 6.1 легко превратить в украшение. Настоящая работа для блоб-хранилища у него другая — **сырое тело входящей доставки**: сотни килобайт, которым нечего делать в строке БД, и первое, что просят при разборе инцидента.

- [x] Установочный шов: `scripts/install-tree.janet` — bundle в собственное дерево, `--export` печатает три переменные (`JANET_TREE` в том числе: `jpm` не читает `JANET_PATH` вовсе, и без этого сюита примера резолвит void из системного дерева, выглядя при этом одинаково). В графе — признак `:installed` и проекции `ci-installed` / `installed-deps`; `check` отказывает такому примеру, у которого завёлся `test-support/paths.janet`. Цена написана в README примера
- [x] Первый коммит — ровно то, что выдали `void new` и `void make auth`, без единой ручной правки; композиция, конфиг и `test/smoke-test.janet` (сюита, которая следует за `main.janet`, в отличие от сгенерированной) — следующим коммитом, и все три ручные правки записаны в README хаба
- [x] Приём: `X-Hub-Signature-256` через `crypto/hmac-sha256` и `crypto/equal?` (не `=`), идемпотентность по `X-GitHub-Delivery` (уникальный столбец, а не проверка в обработчике), сырое тело в `void/storage`, метаданные в БД, `202` до всякой маршрутизации; приём под `void/pressure`. Сюита гоняет настоящее тело доставки из файла — подпись над байтами проверяется байтами, которые никто не перекодировал, — и утверждает, что из хранилища выходит ровно то, что вошло. Строка в bench-таблице (§8.5) — при первом замере
- [x] Правила маршрутизации — данные (`{:when {…} :to [:telegram] :chat-id …}`), матчинг — чистая функция с таблицей примеров в тесте, который ничего не поднимает. Уведомление — **на каждое совпавшее правило**, а не на доставку: правило называет чат, а два чата одним адресом не бывают, и упавший канал одного правила не уносит соседнее
- [x] Telegram — вклад приложения в `:void.notify/channel`, ровно та пара из [ADR-0040](adr/0040-notifikacii-odno-sobytie-neskolko-kanalov.md): `:project` строит текст без сети, `:deliver` ходит через `http/client` + `void/tls`, `:permanent?` записывает 400/403 и повторяет 429 и 5xx; отправка через `void/notify-jobs`. Проверено против поддельного bot API — сервером `void/http` в том же процессе: единственный собеседник, который доказывает и то, что уходящие байты кто-то чужой смог бы прочитать, и то, что решение о повторе принимается по тому, что вернулось. Отдельная сюита утверждает очередь: после 202 есть **две задачи и ни одного сообщения** (два правила — два канала), после прогона очереди — сообщение, собранное из того значения, которое спроецировал запрос
- [x] Эксплуатация: jobs-дашборд 6.3 — главный экран (гостевая книга скаффолда удалена, `/` — редирект по имени маршрута `:admin.page/jobs`, а не по строке); доставки — одно объявление `defresource-admin` над той же сущностью, только чтение; сырое тело — виджет над `body-key`, `[:storage :serve :signed] true` и ссылка на пять минут, потому что ссылка **и есть** авторизация; кто оператор — список `[:hub :operators]`, а не колонка (регистрация открыта, и «вошёл — значит свой» здесь читается как «хаб читает кто угодно»). `void hub replay <delivery>` маршрутизирует заново и **не принимает** заново: подпись уже проверена, а идемпотентность по delivery id не даст второй строки; поднимает БД, хранилище и очередь — и ни одного порта
- [ ] Деплой: compose (web, воркер, БД, бакет), `[:deploy :shape]`, `void deploy check`, TLS на reverse proxy; живой трафик — webhook'и настоящих репозиториев в настоящий чат. sqlite и диск на старте, postgres и бакет — переключением переменных окружения, как в `examples/shop`
- [ ] Решения самого хаба — ADR-0041; всё, что потребовало выхода из стека или объяснения словами, возвращается в волну задачей
- [ ] Путь «идея → деплой» записан по шагам — артефакт §9, а не побочный текст
- [ ] По итогам — решение по пометке «эксперимент» у datastar (ADR-0037)

#### Вернулось из хаба

Задачи, которые приложение нашло собой; каждая — про генератор или про шов, а не про приложение (полный список с обоснованиями — в `examples/hub/README.md`):

- [ ] `void make auth` генерирует сюиту, поднимающую sqlite-драйвер, но не дописывает `janet-lang/sqlite3` в `project.janet` — сгенерированное падает на дереве, где есть только void. Либо генератор дописывает зависимость, либо называет её в том, что печатает
- [ ] Он же печатает десять плагинов и блок конфига и просит перенести это руками. Перенос одинаков в каждом приложении: решить, правит ли `make auth` `main.janet` и `config/` сам (как phx.gen.auth) — и если нет, сказать почему в тексте генератора
- [ ] `void new` кладёт в layout htmx с unpkg, `void make auth` требует `void/security`, чей дефолтный CSP сторонний скрипт запрещает: сгенерировать обе половины — получить страницу, чей скрипт браузер молча отклоняет. Либо скаффолд отдаёт htmx из своих assets (с 6.5 они фингерпринтятся), либо генератор называет строку политики
- [ ] Воркер не знает, что нужно задачам. Команда поднимает то, что перечислила в `:needs`, и `void jobs work` называет `:jobs/queue` — это правда про воркер и неправда про **задачи**: доставка в telegram это https, то есть `:tls/lib`, компонент, от которого очередь не зависит. Первая живая доставка пять раз упала на «no libssl open», пока `void/tls` стоял в композиции незапущенным. Хаб обошёлся своей командой (`void hub work` с лишней строкой в `:needs`), но правильное место, кажется, во фреймворке: `:needs` у самой задачи (`define-job!`) или у канала, и воркер поднимает объединение по тем очередям, которые обслуживает
- [ ] Стиль админки — инлайновый `<style>` в её собственном layout'е, и дефолтный CSP (`default-src 'self'`) его запрещает: композиция с `void/admin` тихо получает нестилизованный стол и строку в консоли. Приложение расплачивается `:style-src [:self :unsafe-inline]` — самой слабой половиной своей политики за чужую страницу. Либо стиль отдаётся как asset (с 6.5 они фингерпринтятся), либо `void/security` учится nonce и админка его берёт
- [ ] Потолок тела поднимается всему приложению ради одного маршрута: GitHub шлёт до 25 МиБ, а `:void.http/max-body` — `:restrict`, то есть маршрут умеет только понижать. Конфиг поднимает один раз, оба источника страниц возвращают вниз — обратное тому, что приложение имеет в виду. Решить, можно ли разрешить одному маршруту поднимать (у контракта метаданных для таких вопросов есть `:allow?`); хаб — первый честный потребитель
- [x] `jpm build` не линковал ни одно приложение с `void/html`: фингерпринт держал абстрактное значение в `def`, а сборка маршалит всё достижимое из точки входа. Починено (`82f98da`) — до 6.5 модуль не был достижим из CLI, поэтому поломка и жила незамеченной

## Отложенное с именем (по потребности, каждое — свой ADR)

Не обещания, а закладки с уже названными границами:

- gRPC streaming через HTTP/2 *(XL)* — SPEC §1 держит его в v2; ADR-0013 выбрал Connect именно потому, что unary покрывает нишу
- redis Cluster/Sentinel — «другой клиент»: MOVED/ASK-редиректы и слежение за топологией
- mTLS, ALPN, session resumption в `void/tls` — названные не-цели ADR-0038 §5; ALPN придёт вместе с HTTP/2, если придёт HTTP/2
- Full-text search — Postgres FTS + sqlite FTS5 за одним контрактом; аналог Scout по спросу
- Presence («кто онлайн» поверх ws rooms + bus) — по первому реальному потребителю
- Inbound email (аналог ActionMailbox) — если попросят бот-хабы §9
- Калибровка на референс-окружении — `scripts/bench-reference.sh` готов; вернётся, когда появится потребитель абсолютных чисел §8.2

## Definition of Done (для любого plugin)

1. Manifest проходит `plugin/dry-run`; удаление из `:plugins` не оставляет следов.
2. Config-schema + тесты на ошибочные конфиги; секреты не печатаются.
3. REPL-инспектируемость: `plugin/inspect` показывает все contributions.
4. Тесты: unit + интеграционный через `void/test`-fixtures; для middleware — строка в bench-таблице («B1 с моим middleware = −X%», §8.5).
5. Docs: README plugin'а + декларации metadata-ключей/extension points (авто-докгенерация).
6. Никаких блокирующих вызовов на ev loop (правило §8.5 п. 1).
