# ROADMAP: void

> Дорожная карта реализации по [SPEC.md](SPEC.md) и [ADR 0001–0019](adr/README.md). Волны — из SPEC §6, критерии готовности контрактов — из SPEC, часть II. Документ живой: статусы обновляются, порядок внутри волны может меняться, порядок волн — нет.

**Правило зависимостей:** каждый plugin зависит только от `void/core` и plugins своей волны или более ранних. Волна считается закрытой не по «код написан», а по exit-критериям.

**Сквозной принцип — dogfooding:** с волны 0 вся разработка ведётся через netrepl внутри системы; с волны 1 каждый следующий plugin строится на предыдущих (admin рендерится через html+htmx, jobs-ui — тоже, bench-приложения — обычные void-приложения).

### 2.2 Драйверы

- [x] `void/db-sqlite` *(S)* — обёртка janet sqlite3, референс-реализация контракта драйвера: pragma-набор на каждое новое соединение из `[:db-sqlite]` (WAL, `busy_timeout`, `foreign_keys` — sqlite по умолчанию FK не проверяет), RETURNING по детекту версии библиотеки (≥3.35, иначе перечитывание по `last_insert_rowid`), `BEGIN IMMEDIATE` по умолчанию (deferred-транзакция под пулом = классический SQLITE_BUSY при апгрейде блокировки) + savepoints, keeper-соединение компонента (кривой путь падает на старте, а не на первом запросе) — `db-sqlite/void/db-sqlite/driver.janet`
  - границы биндинга, зафиксированные тестами: prepared-пары нет (ядро уходит на фолбэк `:execute`), мульти-statement строка компилируется целиком до выполнения (DDL и зависимые statements — массивом строк в миграции), NULL-колонка отсутствует в строке результата, вызовы синхронные и блокируют ev-цикл (за асинхронность отвечает `void/db-postgres`)
  - URI-имена файлов выключены (`SQLITE_USE_URI` — compile-time опция, биндинг её не ставит), поэтому `file:...?mode=memory&cache=shared` не работает: путь берётся буквально и превращается в файл со странным именем. Отсюда два следствия — путь с префиксом `file:` драйвер отвергает с объяснением, а `:memory:` физически односоединенческая БД: драйвер отдаёт пулу одно и то же keeper-соединение, `[:db :pool :size]` > 1 с ней — ошибка старта с указанием, что править. Дефолтный путь поэтому файловый (`db/void.sqlite3`, родительский каталог создаётся)
- [x] `void/fdwait` *(S; ADR-0011)* — единственный нативный модуль монорепы (~60 строк C): «усыпи fiber до readiness чужого fd», ничего не читая и не записывая — того, что `ev/` выразить не может. Один watcher = одно направление (регистрация в loop идёт по флагам стрима, двунаправленный watcher на чтении вырождается в busy-spin; `:both` оставлен для send-петли, которой нужно дренировать вход), `dup(fd)` на watcher (два стрима на один fd = EEXIST в epoll; и закрытие watcher'а не трогает сокет владельца), level-triggered явно (kqueue по умолчанию EV_CLEAR — edge-triggered watcher навсегда засыпает на уже готовом fd). `pair` переиспользует watcher'ы между тысячами ожиданий на одном соединении, `refresh!` — на случай, когда fd меняется под ними (multi-host connect libpq). Тесты меряют главное: fiber просыпается от чужого fd, ev-цикл при этом свободен, 8 ожиданий идут конкурентно — `fdwait/src/fdwait.c`, `fdwait/void/fdwait/init.janet`
- [x] `void/db-postgres` *(M; ADR-0011)* — производственный вариант прототипа: libpq в non-blocking режиме на ev-цикле через `void/fdwait`, без thread pool. Три петли одной формы, все паркуются в fdwait, ни одна не спинит: `PQconnectStart`/`PQconnectPoll` (сокет может смениться на multi-host — `refresh!`), `PQflush` с ожиданием на `:both` (ждать только writable = дедлок с сервером, который перестал читать, потому что мы не дренируем его вывод), `PQisBusy`/`PQconsumeInput`/`PQgetResult` до NULL — всегда до NULL, иначе соединение остаётся посреди протокола. Что сверх контракта драйвера: `PQsendQueryParams`, prepared-пара, single-row streaming, pipeline mode (libpq 14+), LISTEN/NOTIFY, cancel (non-blocking poll-loop на libpq 17+, синхронный `PQcancel` — задокументированный фолбэк), TLS целиком на libpq (`sslmode` — обычный параметр соединения, кода TLS в плагине нет). Структурная ошибка вместо строки: SQLSTATE, constraint, column, table — `db-postgres/void/db-postgres/`
  - `:connect` отдаёт пулу **handle**, а не PGconn: void/db-пул не пингует и выбрасывает соединение только на упавшей транзакции, поэтому убитый бэкенд иначе раздавался бы вечно. Handle владеет conninfo и каталогом prepared-имён и переоткрывает соединение, найдя старое мёртвым — но только вне транзакции и только до отправки statement'а; `COMMIT` на мёртвом соединении — ошибка (он не закоммитил), `ROLLBACK` — успех (сессия уже откатилась, и это то, что пропускает исходную ошибку к вызывающему вместо ошибки отката поверх неё). Каталог сессии переживает замену, поэтому кэш sql→имя в пуле остаётся валидным, а имя, которого новая сессия не знает, готовится заново (26000)
  - конфиг: URL и keyword-строка сходятся в keywords (URI нельзя *дополнить* — libpq парсит одно или другое, поэтому `postgres://` разбирается здесь), явный ключ бьёт URL, серверные настройки (`:statement-timeout`, `:search-path`, `:settings`) едут в libpq'шном `options` как `-c name=value` — без лишнего round trip и уже для первого statement'а. Дефолты почти пусты: всё, что не названо, libpq берёт из окружения ровно как psql (PGHOST, ~/.pgpass, ~/.postgresql/root.crt)
  - LISTEN/NOTIFY — отдельное соединение вне пула (уведомление приходит в *сессию*, которая сделала LISTEN, а пул выдаёт разные), один fiber в fdwait, ноль стоимости в простое; подписки не выпускают SQL из чужого fiber'а, а будят слушающий через `conn/interrupt!` (watcher'ы снимаются, соединение не трогается), и он сверяет LISTEN'ы с желаемыми перед следующей парковкой. Без подписок соединение вообще не открывается. Доставка at-most-once — это Postgres, не драйвер
  - `[:db-postgres :prepared] false` снимает prepared-пару целиком — ровно то, что нужно transaction-pooling pgbouncer'у, где prepared-statement живёт в сессии, которую вам не вернут
  - границы, зафиксированные тестами: COPY не поддержан (другой путь протокола), результаты читаются в текстовом формате (binary — пересборка выходных функций Postgres по типу; numeric отдаётся строкой, потому что double теряет ровно то свойство, ради которого numeric существует), `PQconnectStart` резолвит имя хоста синхронно (единственный блокирующий шаг, который никто не уберёт — отсюда ленивое открытие в пуле), NOTICE/WARNING сервера libpq печатает в stderr сам (перехват требует C-колбэка, которого `ffi/` не даёт)
  - CI: сервис-контейнер postgres:16 + `VOID_TEST_PG`; `void/fdwait` и `void/db-postgres` в тестах, оба плагина — в `scripts/dry-run.janet` и `gen-contracts` (два драйвера на `:void/db-driver` = ровно та неоднозначность, которую ядро отказывается разрешать само, и гейт называет реализацию так же, как это сделал бы конфиг приложения)
- [x] `void/redis` *(M)* — RESP2/RESP3 в чистом Janet на ev-цикле: соединение — это `net/`-стрим и буфер, поэтому нативного кода и клиентской библиотеки нет вовсе, а N фиберов на N соединениях — это N параллельных команд в одном потоке (ADR-0010). Пакет `redis/`
  - **протокол** — та же развилка, что в `void/http/wire`: дешёвый сканер `resp/scan` находит границу кадра, PEG собирает значение. Сканер нужен потому, что RESP length-prefixed: блоб перешагивается арифметикой, а обрезанный кадр отвечает **сколько байт не хватает** (читатель просит их одним чтением, вместо квадратичного перечитывания буфера на каждый чанк), и потому что `nil` от `peg/match` слепляет два разных исхода — «кадр ещё не пришёл» и «это не RESP» (первое ждём, второе — ошибка, иначе не-redis на порту вешает фибер навсегда). PEG отвечает за значения, и оба агрегата — это ровно `lenprefix`, комбинатор под такой протокол: RESP2 и RESP3 в одной грамматике (map/set/push/attribute/verbatim/big number/double), ошибки и push-кадры — **значения**, потому что pipeline из трёх ответов, где упал один, должен вернуть остальные два
  - **кадрирование как инвариант**: ответы приходят в порядке команд, то есть соединение — очередь, а не пара запрос/ответ. Поэтому read-timeout помечает соединение сломанным (ответ всё ещё придёт — доверять такому соединению больше нельзя), а RESP3 push-кадры снимаются из потока в `receive-reply`: внеочередной кадр, доехавший до вызывающего, который считает ответы, сдвинул бы все последующие ответы на один
  - **пул** той же формы, что в `void/db` (FIFO-очередь ожидающих, дедлайн в дочерней задаче, а не `ev/with-deadline` на root task — класс багов ADR-0015), но **своим кодом**: кэш не должен требовать БД, пакеты независимы. Пул нужен не потому, что redis медленный, а потому, что ответы упорядочены: одно соединение выстраивает фиберы в очередь за самым медленным
  - **retry ровно одного класса отказа**: самая частая ошибка в проде — не «redis лежит», а «сокет закрыли, пока он лежал в idle» (серверный `timeout`, рестарт, прокси), и отличить такой сокет от живого до записи нельзя. Ретрай ограничен как только можно: только отказ *соединения* (не ответ-ошибка), только на соединении, побывавшем в idle, только один раз и никогда внутри `with-conn` — сессию нельзя молча подменить под MULTI. Честная оговорка задокументирована: команда, чей ответ потерян, могла выполниться, `[:redis :retry] false` выключает
  - **сахар и граница**: `get/set/del/expire/ttl/incr/hset/hgetall/lpush/blpop/sadd/zadd/zrange-by-score/scan/script/remember` — с префиксом ключей и кодеком значений; `command`/`call` — сырой слой без того и другого (обёртка, угадывающая, какие аргументы произвольной команды суть ключи, ошибается на первой же интересной — EVAL, ZADD, XREAD). `ttl` отвечает `:none`/`nil` вместо -1/-2, `hgetall` — таблицей, `scan` ходит SCAN'ом, а не KEYS (KEYS на проде — это инцидент)
  - **кодеки** — точка `:void.redis/codec`, `[:redis :codec]` выбирает: `:raw` по умолчанию (совместимость с тем, что пишут другие сервисы, и с redis-cli), `:jdn` (таблицы, keywords, вложенность — Janet-only), `:json`
  - **pub/sub** — отдельное соединение вне пула (подписанное соединение в RESP2 не принимает обычных команд, а пул отдаёт его следующему желающему), один фибер в чтении, соединение открывается первой подпиской. Два фибера трогают его безопасно, потому что с разных сторон: читатель только читает, `subscribe!` только пишет под локом; соединение открывает **только** читатель (иначе гонка: двое открывают по соединению и подписываются каждый на своё), а желаемый набор подписок сверяется при каждом переподключении. Доставка at-most-once — это redis, не драйвер, и так и написано
  - `void/redis-http` — companion-плагин (как `void/db-http` при `void/db`): вклад в `:void.http/session-store`, значение в jdn (сессия — таблица с keyword-ключами; JSON вернул бы строковые), TTL — это expiry redis'а, поэтому `:sweep` — честный no-op. Это же закрывает конфликт «сессии + `:workers :auto`» из ADR-0010
  - TLS нет: `rediss://` отвергается с объяснением (ADR-0010 — терминировать прокси или unix-сокетом), Cluster/Sentinel — другой клиент (MOVED/ASK-редирект и слежение за топологией) и отдельный ADR. Интерфейсы `:void/cache` и `:void/queue-backend` приедут с плагинами, которые их определяют (2.3/2.4) — примитивы для них тут все: TTL, атомарные счётчики, `SET NX`-локи, sorted sets под отложенные задачи, блокирующие pop'ы и Lua
  - CI: сервис-контейнер `redis:7` + `VOID_TEST_REDIS`; протокол, конфиг и кодеки тестируются без сервера, остальное — против настоящего (и не трогает чужие ключи: у каждого сюита свой префикс, `FLUSHDB` в тестах нет). Оба плагина — в `scripts/dry-run.janet` и `gen-contracts`, `:void.redis/codec` — в [CONTRACTS.md](CONTRACTS.md)

### 2.3 `void/cache` *(S)*

- [x] Интерфейс + memory impl (TTL, LRU); `(cache/wrap f ...)`; redis-backend — пакет `cache/`
  - **два интерфейса, а не один**: `:void/cache-store` — то, что *реализуют* (четыре функции над строками и значениями, остальное — задокументированные фолбэки, как у `:void/db-driver`), `:void/cache` — то, от чего *зависят* (префикс ключей, дефолтный TTL, single-flight, политика ошибок). Backend'ов два, оба `:provides :void/cache-store`, поэтому композиция с `void/cache-redis` требует `{:void/cache-store {:impl :cache/redis}}` — ровно та неоднозначность, которую ядро отказывается разрешать само, и та же строка, что нужна двум драйверам БД
  - **memory-store**: TTL + **точный** LRU (вытесняется реально давно не *использованный*, чтение считается использованием). Список давности — по **ключам**, а не по записям: интрузивный список из таблиц — это цикл, а `pp` на компоненте должен печататься (ADR-0001), две лишние hash-выборки на touch стоят дешевле этого. Протухание в двух местах, и оба нужны: лениво на чтении (там корректность) и фибером-подметальщиком (иначе значение, которое больше никто не прочитает, лежит в куче до вытеснения — а на незаполненном кэше это «никогда»); `[:cache :memory :sweep-interval] 0` выключает. Лимита в байтах нет: «сколько байт занимает это Janet-значение» не имеет ни дешёвого, ни точного ответа, поэтому лимит — в записях, и это честно написано вместо ключа, который врал бы
  - **упавший кэш деградирует в промах, а не в 500**: у кэша нет своих данных, терять нечего, поэтому `[:cache :on-error] :degrade` (по умолчанию) отвечает промахом, считает отказы и логирует не чаще раза в 10 секунд (авария, логирующая каждый запрос, — вторая авария поверх первой). `:raise` — для того, кто предпочитает знать
  - **single-flight**: холодный ключ на нагруженном роуте — это стадо: чем больше трафика, тем больше копий одного и того же расчёта. Первый фибер считает, остальные паркуются на канале и забирают результат — **включая ошибку** (стадо, которое после сбоя пересчитывает всё заново, — это то самое стадо). Внутрипроцессно; межпроцессный лок — другая фича с другим режимом отказа (умерший держатель), `[:cache :single-flight] false` выключает
  - **отсутствие — тоже значение, но только по просьбе**: промах у store'а — это nil, места для «закэширован nil» в протоколе нет, поэтому `:cache-nil` кладёт сентинел, а `fetch` возвращает `[found? value]` и различает их. На store'е, который не переживает keyword (redis с кодеком `:raw`, он объявляет `:values :bytes`), это ошибка с указанием, что настроить, — а не строка `":void.cache/nil"`, выданная кому-то как данные
  - **ключи**: написанные руками (строка, keyword, число) идут в store дословно — ключ, который вы написали, вы найдёте в keyspace; производные (аргументы `wrap`, составные) — через инъективный тегированный рендер с сортировкой пар словаря. Это и есть причина существования `void/cache/key`, а не вызова `%j`: Janet печатает ключи словаря в порядке хэша, стабильном ровно в пределах процесса, и разделённый кэш, где процессы ключуют по-разному, — это 0% попаданий без единого сообщения об ошибке. Анонимной функции `wrap` требует `:name` по той же причине
  - `void/cache-redis` — SET с PX, MGET, атомарный INCRBY (у store'а есть `atomic-incr?`, потому что фолбэк read-add-write точен только внутри процесса), кодек **свой** (`:jdn` по умолчанию, а не `[:redis :codec]`: `:raw` — правильный дефолт для клиента redis и невозможный для кэша, который держит таблицы; сессии выбрали так же и по той же причине). `clear` **обходит** свой префикс SCAN'ом и удаляет пачками — не атомарно и O(keyspace), но база общая, а `clear`, который был бы FLUSHDB, — это `clear`, который никто не рискнёт вызвать; префикс с glob-символом экранируется
  - `void/cache-http` — `:void.cache/response` `{:ttl :vary}` переезжает из reserved-таблицы CONTRACTS в declared. Слот 2500 — после парсинга, до сессии: попадание отдаётся, ни разу не открыв сессию (поэтому в нём физически не может быть Set-Cookie), но уже по разобранному пути и query. Это **разделяемый** кэш, и он ведёт себя как разделяемый: запрос с `Authorization` идёт мимо кэша целиком (RFC 9111 §3.5), ответ с `Set-Cookie`, с `cache-control: private|no-store` или со стриминговым телом не сохраняется — и каждый отказ логируется один раз на роут, а не молча. Кэшируются только 200; `:ttl 0` — способ отписаться от того, что поставила группа. Роут без ключа не получает обёртку вообще (`:when` вычисляется на построении таблицы), поэтому bench-строки по §8.5 п.4 здесь нет — вместо неё тест, который это пинит
  - CI: `cache/` в тестовых шагах, все три плагина — в `scripts/dry-run.janet` и `gen-contracts` (гейт называет реализацию `:void/cache-store` так же, как это сделал бы конфиг приложения); redis-suite — против сервиса-контейнера по `VOID_TEST_REDIS`, остальное тестируется без сервера

### 2.4 `void/jobs` *(M/L; ADR-0012)*

- [x] Persistence — интерфейс `:void/jobs-backend`: db (SKIP LOCKED polling), redis — пакет `jobs/`
  - **executor — фиберы `ev/`, а не spork/tasker**, и это единственное место, где реализация расходится с буквой ADR-0012. ADR называл tasker до чтения его исходников; tasker исполняет **подпроцессы** (задача — массив argv для `os/spawn`, записи — файлы `task.jdn` на диске). `defjob` устроен противоположно по необходимости: handler — внутрипроцессная функция через символ (ADR-0002), замкнутая на компоненты поднятой системы, и argv, выражающего «вызови эту функцию в этом процессе», не существует; дисковые записи tasker'а — ровно то, что заменяет backend-контракт. Требование ADR «исполнитель, не блокирующий цикл» на `ev/` — это фибер (ADR-0010). Уточнение записано в ADR-0012 и в шапке `void/jobs/worker`
  - **два интерфейса, как у db и cache**: `:void/jobs-backend` — то, что *реализуют* (восемь функций над записями; атомарен из них ровно один — `claim!`, и он и есть причина, по которой backend нужен вместо таблицы), `:void/jobs` — то, от чего *зависят*. Всё, что *решает* (сколько попыток, сколько ждать, что делает таймаут), живёт в runtime и одинаково под любым backend'ом — иначе контракт был бы не контрактом, а тремя разными очередями. Опциональные ключи (`reap!`, `touch!`, `lock!`/`unlock!`, `rate-take!`, `release-parent!`) имеют задокументированные фолбэки, а `capabilities` **выводит**, а не декларирует, какие из них настоящие: «rate limit — per process» оператор читает, а не обнаруживает
  - **три backend'а — одна conformance-сюита** (`test-support/conformance.janet`): таблица в куче, строки в БД и хеши в redis отвечают на одни и те же восемь вопросов, и сюита, которая гоняла бы только in-process backend, была бы сюитой, которая контракт ни разу не проверила
  - **у db-backend'а два пути claim'а, и оба под тестом**: на Postgres — один `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING`, на остальных — select + перепроверенный update в транзакции (проигранная гонка остаётся проигранной, а не вторым запуском). Портируемый путь идёт против sqlite, SKIP-LOCKED — против настоящего Postgres по `VOID_TEST_PG` (`test/db-postgres-test.janet`), и там же проверяется свойство, ради которого SKIP LOCKED и берут: N одновременных claim'ов получают N **разных** записей. Убери `FOR UPDATE SKIP LOCKED` — сюита падает на дубликате, это проверено мутацией
- [x] `defjob` (символы → hot reload), retries backoff+jitter, приоритеты, delayed, unique, DLQ
- [x] Flows (parent-child DAG), rate limiting per queue, concurrency per worker, group-ключи
  - четыре лимита — четыре разных механизма, потому что вопросы разные: concurrency воркера — это число фиберов; per-queue — счёт до claim'а; group — счёт до claim'а **и** `:skip-groups` в claim, чтобы запись не пришлось возвращать (это и есть fair scheduling: тенант с десятью тысячами задач не может занять все фиберы); rate limit — **после** claim'а, иначе лимитер тратил бы токен на каждый пустой опрос
  - таймаут — `ev/deadline` на своей задаче, никогда `ev/with-deadline` вокруг: последнее отменяет корневую задачу (тот же класс багов, что задокументирован в ADR-0015)
- [x] Repeatable: spork/cron, `defschedule`, single-instance через backend-lock
  - лок берётся на **слот** (`jobs:schedule:<name>:<slot>`), а не на имя: слот — это то, что должно случиться один раз
- [x] Lifecycle events в bus (появится в волне 3 — пока hooks)
  - `:void.jobs/event` на реестре хуков ядра; события (`:enqueued` `:started` `:completed` `:failed` `:dead` `:stalled`) — это шов, который в волне 3 забирает `void/bus`
- [x] CI: `jobs/` в тестовых шагах, все три плагина — в `scripts/dry-run.janet` и `gen-contracts` (гейт называет реализацию `:void/jobs-backend` так же, как это сделал бы конфиг приложения); `:void.jobs/backend` уезжает из reserved-таблицы CONTRACTS — backend оказался интерфейсом через `:provides`, как `:void/db-driver` и `:void/cache-store`, а не extension point

- [x] Проверка бюджетов ev-loop-lag/GC из §8.2
  - **измерять снаружи нечем**: клиент видит следствие loop-lag'а размазанным по каждому числу latency; сам лаг видит только процесс. Поэтому `void/bench/probe` — fiber внутри приложения, сэмплирующий тем же метром, что и `void/pressure` (одна реализация loop-lag на монорепо: та, что реагирует, и та, что бюджетирует). Runner снимает его через `/void/bench/probe` **вокруг fixed-rate прогонов** и только их: wrk на max throughput насыщает loop по построению, а «loop-lag p99 < 1 ms» — бюджет про целевую нагрузку, не про насыщение
  - **GC-бюджет едет на максимуме loop-lag**, и это не подмена: janet 1.41 не сообщает ни одной паузы, но stop-the-world сборка на однопоточном loop **и есть** loop lag не меньше собственной длины, так что `loop-lag max ≥ GC max pause` всегда. Проверка консервативна (максимум выше границы может быть и сборкой, и медленным хендлером) и не притворяется, что знает, чем именно. Вторая половина §8.2 («суммарно < 2% времени») такой границы не имеет — CPU хендлера изнутри неотличим от CPU сборщика — и остаётся неизмеренной, пока janet не начнёт считать сам
  - loop-lag p99 сравнивается и между коммитами (тот же абсолютный пол 0.1 ms: эти числа живут ниже миллисекунды, и 5% от 0.05 ms — это шум со знаком процента)
  - RSS печатается в отчёте, но **не гейт**: §8.2 называет «hello-app < 30 MB», а измеренное на ноутбуке b0 — 49 MiB. Прежде чем стать гейтом, эти цифры должны быть промерены на референс-окружении — ровно та же процедура, что B0/B1 прошли в v0.1
- [x] `b1-pressure` — строка §8.5 для middleware из 2.6: тот же B1 с `VOID_BENCH_PRESSURE=1`. Замер на M4 Max: −0.2% и +0.6% за два прогона, то есть внутри шума прогон-к-прогону — middleware на спокойном пути это один разыменованный var

### 2.6 `void/pressure` — load shedding *(S; ADR-0019)*

- [x] Принять ADR-0019 — accepted, с уточнениями по итогам реализации (см. ниже и хвост ADR)
- [x] Sampler-компонент: loop-lag (дрейф `ev/sleep`), rss; custom-проверки — point `:void.pressure/check`
  - **два plugin'а, а не один** (ADR говорил «core + http»): `void/pressure` — sampler, пороги, флаг, health, события, только core; `void/pressure-http` — middleware и metadata-ключ. Тот же шов, что между `void/cache` и `void/cache-http`, и по той же причине: воркер, который крутит jobs и не слушает порт, имеет право знать, что его loop опаздывает, не поднимая ради этого HTTP-ядро
  - **heap-метра нет, и это janet, а не пропуск**: `gccollect`/`gcinterval`/`gcsetinterval` — вся GC-поверхность 1.41, и ни одна не говорит, сколько байт на куче сейчас. Память меряется как RSS (`/proc/self/status`; на macOS mach `task_info(MACH_TASK_BASIC_INFO)` через `ffi/` — `getrusage` не подходит, `ru_maxrss` это high-water mark, с которого не восстановиться), `:max-heap-bytes` как ключ не существует. Сигнал без прибора репортится отсутствующим, и порог над ним не срабатывает никогда: «прибор сломан» не должно читаться как «всё хорошо»
- [x] Пороги `:max-loop-lag`/`:max-rss-bytes` → флаг `:under-pressure` с гистерезисом восстановления
  - гистерезис — не полировка, а сама фича: один и тот же порог в обе стороны превращает процесс на границе в процесс, который режет каждый второй запрос и восстанавливается между ними. Два барьера: срабатывание на `:max-loop-lag`, возврат — ниже `:recovery-ratio` × порог и `:recovery-samples` чистых замеров подряд. `:high`/`:recovered` — по одному на эпизод, а не на замер
  - у custom-проверок гистерезиса нет и быть не может: «пул исчерпан» — не число, у которого бывает 80% себя. Проверка, которая бросила, считается давлением — проба, чей отказ значит «продолжайте», не проба
- [x] Middleware в слоте 100: 503 + `Retry-After` через error-путь (problem+json при rest); metadata `:void.pressure/exempt` для `/health`/`/metrics`
  - **вызовом, а не броском**: в `void/http` добавлена публичная `render-error` — те же `:void.http/error-renderer` в том же порядке. Буквальное «бросить 503» стоило бы стектрейса на каждый отвергнутый запрос и попадало бы в panic-логирование (`status >= 500`) — тысячи строк лога поверх перегрузки, ровно когда платить нечем
  - exempt-маршрут не оборачивается вовсе: `:when` считается один раз на сборке таблицы, так что `/health` не может быть срезан и не стоит ничего. Паттерн для деплоя — `/health` exempt + routing LB по нему, иначе балансировщик выведет воркер ровно в тот момент, когда тот пытался остаться полезным
- [x] Contribution в `:void.core/health` (degraded + причины), `(pressure/status)`, события `:pressure/high|recovered` в hooks-шину
  - отвергнутые запросы логируются **раз за эпизод** (`[:pressure-http :log]`), а счётчик уезжает в событие `:recovered`: лог, который сам становится частью перегрузки, — не наблюдаемость
- [x] Prefork: sampler per-worker, ~~агрегация в master health~~ — агрегировать нечем и незачем
  - воркеры не делят ничего, кроме слушающего сокета (ADR-0010), канала до master'а нет. Вместо выдуманной агрегации master помечается `:mode :supervisor` и не сэмплирует вовсе: его loop простаивает по построению, и ноль с него был бы измерением ничьих запросов. Агрегация — это SO_REUSEPORT
- [x] Тест насыщения в CI (exit-критерий 4): реальный сервер, реально заблокированный loop, реальный сокет — 503 + `Retry-After`, exempt `/health` жив, после снятия нагрузки `:recovered`. Длительность удержания loop'а рандомизирована: фиксированная фазируется с интервалом sampler'а и даёт один и тот же замер вечно
- [x] Строка §8.5 для middleware: `b1-pressure` — тот же B1 на один plugin тяжелее (−0.2% / +0.6% за два прогона, внутри шума). Пороги там выключены (`:max-loop-lag 0`) при **работающем** sampler'е: вопрос §8.5 — что платит несрезанный запрос, а под max-throughput wrk loop насыщен по построению, и шедящий B1 мерил бы, как быстро void отвечает 503 (другое, куда более приятное число)
- [ ] Калибровка порогов по умолчанию на B2/B3 на референс-окружении — вместе с калибровкой абсолютных бюджетов B2/B3 (2.5)

- [x] ev/loop-lag гистограмма (главный health-индикатор, §8.4) тем же метром, которым реагирует `void/pressure` (`void/pressure/sample` — модуль, не плагин), с максимумом рядом как границей сверху на паузу GC; p99 «accept→handler» — гистограмма `void_http_queue_seconds` от `:arrived` (первые байты запроса в руках процесса), а не от accept: preconnect браузера иначе записал бы своё молчание в очередь процесса (ADR-0021 п. 6)

Инструментации db, redis, cache и jobs **живут в obs, а не в своих пакетах** — вклад в точку, которой нет в активном множестве, это ошибка старта, поэтому `void/db` не может контрибьютить в точку obs, не сломав каждое приложение без obs; obs идёт к ним публичным путём (экземпляр компонента + функция `stats` их модуля через `require`) и молча пропускает то, чего в композиции нет. http-client не инструментирован, потому что его в void ещё нет (закрыто в 4.1: `void/http/client` инструментирован единственным вкладом без `:needs` — модуль, а не компонент)
- [x] `/health` (зовёт проверки), `/ready` (флаг и состояния компонентов, никакого I/O — проба раз в секунду не должна ходить в базу), `/metrics` (опционально за bearer-токеном); маршруты несут `:void.obs/endpoint`, и `void/pressure-http` не сбрасывает их наравне со своим `:void.pressure/exempt`. Overhead — строка `b1-obs` в bench-suite (`void bench b1 b1-obs`, и в bench.yml на каждом прогоне). **Измерено на дев-машине** (M4 Max, macOS, генератор рядом с сервером — не референс-окружение): **−7…−10% throughput B1** при разбросе прогонов ±1.5 п.п., то есть на границе бюджета §8.2 и, возможно, за ней. Первая редакция стоила −15%; разницу дали спан по требованию (главное), метки метрик без строковых конверсий на запросе и in-flight счётчиком вместо записи в gauge. Вердикт по бюджету — за референс-окружением (выделенный runner, 1 vCPU), как и по абсолютным бюджетам B2/B3: это тот же открытый хвост калибровки

### 3.2 `void/auth` *(M)* → 3.3 `void/authz` *(M)* → 3.4 `void/security` *(S/M)*

- [x] crypto (`void/crypto`, ADR-0022) — предпосылка, которой у волны не было: у Janet 1.41 нет ни одного примитива кроме `os/cryptorand`. Все три пакета берут их из системной libcrypto через `ffi/` — ни одного нового нативного модуля и ни одной новой обязательной зависимости бандла: SHA-2/HMAC, scrypt/argon2id/PBKDF2, RS256/ES256 (значит, JWT умеет асимметрию сразу, а не «когда-нибудь с oauth»), `CRYPTO_memcmp`; случайность остаётся у ОС, потому что `RAND_bytes` пришлось бы пересеивать после fork, а void форкает (ADR-0010). Библиотека открывается компонентом `:crypto/lib` на `:start` — отсутствие это ошибка загрузки со списком путей, где искали, а не nil-вызов на первом логине; `[:crypto :require]` даёт приложению право **не стартовать** без алгоритма, на который оно рассчитывает (argon2id живёт в OpenSSL с 3.2, Ubuntu 24.04 LTS везёт 3.0 — поэтому дефолт scrypt, вопреки общей рекомендации OWASP). **KDF по умолчанию уходит в `ev/thread`**: на loop scrypt N=16384 стоит 25.3 мс, за которые тикер с интервалом 2 мс не провернулся **ни разу**, через поток — 36.9 мс и 17 оборотов loop; обе цифры заперты тестом, а не запиской. Списки кандидатов платформо-специфичны, и это не косметика: на macOS `(ffi/native "libcrypto.dylib")` и `/usr/lib/libcrypto.dylib` **убивают процесс** (SIGABRT из системного шима LibreSSL, мимо `protect`), поэтому там только явные пути — заперто тестом, чтобы «унификация списков» падала в CI, а не у пользователя. Векторы: FIPS 180-4 (SHA-2), RFC 4231 (HMAC), RFC 7914 (scrypt), RFC 6070 (PBKDF2), RFC 9106 (argon2id, с pepper и AD) — `crypto/`
- [x] auth (`void/auth` + `void/auth-http` + `void/auth-db`, ADR-0023) — **identity как данные**: `{:subject "user:42" :via :password :cookie true :claims {...}}`, и ничего от модели приложения; `current-user` в dyn-ключе `:void.auth/identity`, который `void/authz` читает **не импортируя пакет** (приём `void/pressure-http` с `:void.obs/endpoint`). Стратегии — точка `:void.auth/strategy` с тремя необязательными половинами (`:authenticate` — достать из запроса, `:verify` — проверить учётные данные, `:challenge` — как выглядит отказ): `:session`, `:bearer`, `:jwt` читают запрос, `:password`, `:magic-link`/`:otp` — нет, поэтому 25-миллисекундный KDF физически не попадает на горячий путь. Хэши — **PHC-строки** (`$scrypt$ln=14,r=8,p=1$...`): алгоритм и стоимость берутся *из строки*, а не из конфига, поэтому поднятие цены никого не разлогинивает, старые scrypt-хэши продолжают проверяться под argon2id, а `needs-rehash?` перевешивает их на успешном входе — единственный момент, когда пароль вообще существует. Неизвестный логин всё равно считает хэш (`dummy-verify`): 200 µs против 25 мс перечисляют базу пользователей надёжнее любой формы. API-токены — `vt_<id>.<secret>`, в хранилище SHA-256 от секрета (KDF на равномерных 256 битах стоила бы 25 мс на запросе и не добавила бы ни бита); JWT — HS256/384/512 + RS256/ES256, и **`alg` берётся из конфигурации, а не из токена**, поэтому `{"alg":"none"}` и подмена RS→HS отваливаются до проверки подписи (тест на каждую). Одноразовые коды одноразовы по построению: `:take` в контракте хранилища отдаёт и забывает, в БД — одной транзакцией. Хранилища — три контракта (`user-store` / `token-store` / `challenge-store`) с memory-реализациями в `void/auth` и БД-реализациями в `void/auth-db`, где таблица пользователей **остаётся приложению** (плагин её читает, не создаёт и не мигрирует), а две таблицы void'а приезжают DDL-данными в миграцию приложения. Enforcement — фаза 4000 и `:void.auth/access` (`:restrict`: группа, требующая логина, не ослабляется маршрутом внутри неё), ответ 401/302 идёт **через error-renderers**, а не через `error` — стектрейс на каждый неавторизованный запрос приходит ровно тогда, когда кто-то перебирает пароли. Вход **ротирует id сессии** (`session/rotate!`, аддитивная правка `void/http` волны 1) — session fixation другого лечения не имеет — `auth/`
- [x] authz (`void/authz` + `void/authz-http`, ADR-0024) — политика это **чистая функция под именем** (`defpolicy` — сахар над `register-policy!`), тело обычный Janet: «выразительнее» и «второй язык для отладки» — одно решение, принятое дважды (ADR-0004), а инспектируемость даёт реестр (`void authz policies`, `void authz routes`), а не форма тела. Чистота — контракт: политика не ходит в базу, всё с I/O приходит **атрибутом**, и атрибуты **вытягиваются, а не подкладываются** — `(authz/attr ctx :subject/brand-id)` зовёт провайдера при первом обращении и мемоизирует на решение (маршрут, чья политика смотрит на роль, не платит за запрос «какой у него бренд»; маршрут, которому бренд нужен, платит один раз на три политики). Встроенные фолбэки закрывают типовой случай без единого провайдера: `:subject/*` читает claims личности (плюс `:subject/id`/`:kind` из строки субъекта), `:resource/*` — ключ ресурса, `:env/*` — окружение. Решение — **значение** (`{:allow :policy :reason :attrs :us}`): `can?` его булева проекция, `ensure!` бросает 403, а `explain` печатает **ту же** оценку, а не вторую, которая рано или поздно разойдётся с первой; `:reason` уходит в decision log и в `void authz explain`, но никогда в тело ответа — объяснение это описание внутренних атрибутов. Enforcement — фаза 5000 и `:void.authz/policy` с `:concat`: политика группы **и** политика маршрута обе должны разрешить, «или» выражается одной политикой, а не формой метаданных; маршрут без политики не оборачивается вовсе (предикат `:when` считается на сборке таблицы). `[:authz :default :deny]` переворачивает умолчание, и это **ошибка старта** со списком незакрытых маршрутов, а не 403 во время запроса — забытая политика ловится там, где это бесплатно. RBAC — сахар: роли данные, `has-role?`/`permitted?` предикаты для тел политик, `role-policy` готовая политика; ни второго пути enforcement, ни второй подсистемы. Каждое решение проходит через хук `:void.authz/decision` (по умолчанию логируются только deny — allow'ов сотня на страницу со списком), и это шов, который в 3.6 забирает `void/bus`. **Зависимости от `void/auth` нет**: личность читается из dyn-ключа `:void.auth/identity`, и тест поднимает композицию с чужой аутентификацией, чтобы это было проверено, а не заявлено — `authz/`
- [x] security (`void/security`, ADR-0025) — **CSRF по кукиным полномочиям, а не по методу**: проверяется небезопасный запрос, чьё полномочие приехало кукой (сессионная кука или identity, которую построила читающая куку стратегия — `void/auth` честно помечает это на identity). Запрос с `Authorization: Bearer` браузер к чужому сайту не приложит, CSRF там не существует — поэтому JSON-API и HTML-формы уживаются в одном процессе, а `:void.security/csrf` остаётся `:restrict`-ключом, который умеет только ужесточать (ключа «выключить» нет и быть не может). Токен **один и всегда подписан** (`HMAC-SHA256`, `void/crypto`), привязан к куке, которую ставит сам модуль: к id сессии привязать нельзя, потому что страницу с формой обычно рендерит тот же запрос, который сессию и создаёт — токен был бы отвергнут на том самом потоке, ради которого выпущен; остаточный cookie-tossing лечится префиксом `__Host-`, и это записано, а не забыто. Поле формы приезжает через слот `(dyn :void.html/csrf)`, который `void/html` ждёт с волны 1, заголовок — через `security/htmx-meta` для htmx и fetch. **Заголовки и CORS ставятся на краю**: middleware оборачивает цепочку маршрута, а 404, 405, статика, отрендеренный panic-guard'ом 500 и preflight на путь без маршрута — всё это вне любой цепочки, поэтому `void/http` получил новую точку `:void.http/edge` (обёртка вокруг всего обработчика, снаружи panic-guard; аддитивное расширение контракта v1, в CONTRACTS.md). CSP собирается из данных — неизвестная директива это ошибка старта, а не молча проигнорированная браузером опечатка — с nonce на запрос только если политика его упоминает, и с `report-only` как способом внедрить CSP не сломав страницу. **Rate limiting стоит на контракте `:void/cache-store`**, а не на своём: memory-реализация встроена, `:cache` берёт хранилище композиции (с `void/cache-redis` счётчик становится общим для prefork-воркеров и флота, и неатомарный стор на `:workers > 1` предупреждает о себе на старте). Алгоритм — скользящее окно на двух счётчиках (один инкремент и одно чтение, без всплеска ×2 на границе), ответ 429 с `Retry-After` и `RateLimit-*`; отказ стора **fail-open** по умолчанию, потому что недоступный redis не должен превращать защиту от перебора в отказ в обслуживании. Две фазы лимитера (200 по адресу — до разбора тела и сессии; 4400 по субъекту — после auth), и какая обёртка достанется маршруту, решает предикат на сборке таблицы. **Клиентский IP вычисляется**, а не читается: `X-Forwarded-For` — ввод пользователя, пока `[:security :trusted-proxies]` не докажет обратное, список по умолчанию пуст (за прокси лимит сначала будет общим — заметно и чинится строкой; обратный дефолт обходился бы заголовком и не замечался никогда) — `security/`

### 3.5 `void/mail` *(S; ADR-0026)*

- [x] mail (`void/mail` + `void/mail-jobs` + `void/mail-auth`, ADR-0026) — **сообщение это таблица**, и остаётся ею до сокета: `{:to :subject :text :html}`, отправитель и префикс темы из `[:mail]`, `Date`/`Message-ID` на доставке; никакого builder'а (ADR-0004), поэтому письмо кладётся аргументом в задачу, сравнивается в тесте по полям и печатается в логе целиком. Конверт — не заголовки: `:bcc` это получатель в `RCPT TO`, и заголовка `Bcc` в письме нет вовсе, а `:envelope-from` отделён от `From`, потому что отлупы — свойство развёртывания. **Инъекция заголовка проверяется там, где заголовки пишутся, и до кодирования**: encoded word унёс бы `\r\n` безвредно, то есть молча принял бы тему, которой никто не писал. Адрес — данные (`{:name :email}`), **список адресов — список**: разобрать строку с запятыми правильно значит разобрать quoted display name, а парсер, ошибившийся однажды, дописывает получателя в уже отправленное письмо; не-ASCII в display name — RFC 2047, не-ASCII в самом адресе — отказ (это SMTPUTF8, которого клиент не объявляет). Тело — **обычное представление `void/html`** тем движком, который композиция уже выбрала, поэтому hiccup, temple и сторонний движок работают для писем, ничего о письмах не зная, а layout приезжает на сообщении (функция — не конфиг). У письма нет origin: `[:mail :base-url]`, `mail/url`/`mail/asset`, и **относительная ссылка — ошибка на рендеринге**, потому что она работает в каждом тесте и ни в одном входящем. Транспорт — **вклад в точку**, а не компонент (у него нет состояния, которое стоит стартовать, а «какой из» — имя в конфиге): `:memory` (outbox теста), `:file` (по `.eml` на письмо — открывается в почтовом клиенте), `:log`, `:smtp`; **в `:prod` транспорт, который никуда не отправляет, — ошибка старта**, тот же довод, по которому `void/security` не выдумывает ключ подписи в проде. **TLS нет** (ADR-0010): `smtps://` невозможен и STARTTLS не используется, развёртывание — релей на loopback (Postfix/msmtp/sidecar), как `rediss://` в 2.2, а **AUTH в открытую на не-loopback хост — отказ на старте** (чистая функция конфигурации), с двумя выходами в тексте ошибки. **Код ответа решает, будет ли ретрай**: 4xx летит исключением в политику очереди, 5xx возвращается отказом в квитанции — пять попыток доставить письмо в несуществующий ящик получают rate-limit от релея, а не доставляют письмо. `void/mail-jobs` ставит функцию на `mail/enqueue`, и **место вызова не меняется**; в очередь кладётся отрендеренное письмо (на воркере нет ни личности в dyn, ни локали, а на каждой попытке был бы новый `Message-ID`). `void/mail-auth` — вклад в `:void.auth/deliver`, пустовавший с 3.2, а вторая половина — `auth/challenge!` в `void/auth`: выпустить вызов и отдать доставщикам, и **вызов, который никто не доставил, — ошибка**, потому что альтернатива это страница входа, которая крутится вечно, не оставив следа ни в одном логе. Проволочный формат — чистая проекция (тесты сравнивают строки), разговор с сервером — сценарный SMTP-сервер на настоящем сокете: многострочный EHLO, отвергнутый получатель, dot-stuffing, 4xx против 5xx — `mail/`

### 3.6 `void/bus` *(M; ADR-0012)*

- [x] bus (`void/bus` + `void/bus-db` + `void/bus-jobs`, ADR-0012) — **сообщение это таблица на keyword-топике**: `{:id :topic :payload :meta}`, где `:meta` принадлежит фреймворку (`:published-at`, `:correlation-id`, `:causation-id`, `:traceparent`, `:redelivery`), а `:payload` — приложению, и ни одна запись void'а в него не течёт; поэтому схема payload'а (`bus/defevent`) остаётся утверждением о домене, а не о транспорте. Подписка — три формы и не больше: `:user/created`, `:user/*`, `:*` — четвёртая (glob, regex, иерархия произвольной глубины) это язык маршрутизации, который надо учить, отлаживать и ускорять, а двухчастный keyword Janet уже говорит «какая подсистема, какое событие». **Кодек работает на каждом backend'е, включая in-heap** — иначе обработчик, получающий `{:id 42}` под `:memory`, получал бы `{"id" 42}` под `:db`, форма payload'а зависела бы от развёртывания, и каждый тест был бы тестом формы, которой в проде нет; `:raw` — способ купить две аллокации обратно, прочитав этот абзац, и backend, хранящий байты, отказывает ему на старте. Роутер регистрирует **одну** подписку на группу и разводит сообщение по обработчикам сам: порядок в группе есть потому, что читатель один. Middleware — та же обёртка и **та же фазовая шкала, что в `void/http`**, с константами HTTP там, где смысл совпадает; слоты, которые запрос тратит на сессию, аутентификацию и авторизацию, сообщению не нужны (полномочие у него в `:meta` или его нет), и bus тратит их на poison/retry/dedup/throttle. **Retry и redelivery — одна забота на двух дистанциях**: под `:at-most-once` переигрывать обработчик больше некому и retry включён, под `:at-least-once` его включит backend, и делать оба значит превратить три попытки в девять — поэтому дефолт *выводится* из объявленной гарантии, а не задаётся. Trace продолжается из запроса в consumer, и **ребра на `void/obs` нет**: вклад в точку, которой нет в активном множестве, — ошибка старта, поэтому obs резолвится публично (`require` на `:start`, nil когда его не компоновали) — шов, которым сам obs инструментирует `void/db` — `bus/`
- [x] Backends — точка `:void.bus/backend` (фабрика, а не компонент: у jobs backend это *хранилище*, которых у приложения может быть два, а у bus — транспорт, который процесс говорит один, и его называют именем в конфиге, как транспорт почты). `:memory` — канал на группу поверх `ev/chan`, at-most-once, и сообщение, опубликованное когда никто не слушает, **исчезает**: лога, который можно догнать, здесь нет, а кольцо истории — буфер для `void bus tail`, из которого никогда ничего не переигрывается. `:db` (`void/bus-db`) — append-only лог и **курсор на consumer group**, а не очередь, у которой строки удаляются при чтении: fan-out это вся разница между шиной и очередью, и два сервиса должны увидеть `:order/paid` оба. Один читатель на группу держится **lease**, а не `FOR UPDATE SKIP LOCKED`: строку пришлось бы держать заблокированной всё время работы обработчика, то есть держать транзакцию открытой поверх произвольного кода приложения — ровно то, от чего `void/db` защищает (ADR-0009). Провалившаяся доставка **останавливает курсор группы**, потому что «в порядке» с пропуском того, что не доставилось, — это не порядок; счётчик попыток приезжает на сообщении как `:redelivery`, и poison-middleware — то, что в конце концов убирает его с дороги. Пробуждение на Postgres — `pg_notify` **на той же связи, что сделала вставку** (значит, приезжает на COMMIT и не приезжает на rollback), слушает `void/db-postgres` своим listener-компонентом, найденным публично; без него цикл опрашивает, и это потолок задержки, а не корректности. Обе ветки гоняют одну conformance-сюиту (`test-support/conformance.janet`) — `sqlite` всегда, `postgres` по `VOID_TEST_PG`, и второй раз с выключенным NOTIFY
- [x] **Transactional outbox** — `bus/publish-tx!` пишет сообщение **в ту транзакцию, внутри которой вызван** (`db/with-tx`), forwarder-компонент публикует то, что закоммитилось, и помечает строку. Порядок «опубликовать, потом пометить» выбран сознательно: он падает в **дубль**, а не в потерю, и дубль закрывается — в `:db` самим логом (`ON CONFLICT (id) DO NOTHING`: id сообщения *есть* сообщение), а для транспорта, который своего id не узнаёт, dedup-middleware. Подпись отличается от записанной в ADR (`(bus/publish-tx tx topic msg)`): у `void/db` транзакция **амбиентная** (dyn, ADR-0009), значения `tx` не существует — вызов вне `db/with-tx` это ошибка, называющая недостающую форму, а не молча не-транзакционная публикация (уточнение в ADR-0012)
- [x] CQRS-слой (`void/bus/cqrs`) — тонкий и без второго реестра обработчиков: `defevent` даёт имя, топик и схему (схема проверяется **на публикации**, там, где форму ещё может починить тот, кто её сломал), `defevent-handler` берёт топик и схему из объявления, так что форма записана один раз. `defcommand` — ровно один обработчик и ответ, и это **вызов в этом процессе**: команда с ответом поверх асинхронного транспорта требует топика ответа, ожидания по correlation и таймаута, то есть протокола request/response, а он у void уже есть (`void/http`, в волне 4 `void/grpc`); через границу процесса уходит *событие*, которое обработчик команды публикует. Второй обработчик на одну команду — ошибка **объявления**, а не гонка

### 3.7 `examples/shop` — вся волна 3 в одном приложении *(demo)*

- [x] Не exit-критерий, а ответ на вопрос «как выглядит приложение, собранное на void целиком»: витрина, корзина, оформление заказа, платежи, стол оператора и JSON-API в одном процессе — **тридцать плагинов void'а плюс собственный в композиции и ни одной строки приложения, которая знает хоть об одном из них**, кроме метаданных маршрута. Транзакция, идентичность, политика, CSRF, лимит частоты, кэш, метрики, трейс и сброс нагрузки — всё это `:void.db/txn`, `:void.auth/access`, `:void.authz/policy`, `:void.security/rate`, `:void.cache/response` в таблице маршрутов, а `main.janet` — единственный файл, называющий движок базы
- [x] Оформление заказа как **одна транзакция, у которой откат это ответ, а не ошибка**: остаток снимается условным UPDATE (`WHERE stock >= ?`), поэтому перепродать последнюю единицу нельзя без блокировки; цена перечитывается из каталога, поэтому корзина недельной давности не покупает прошлогоднюю цену; `bus/publish-tx!` и `jobs/enqueue` пишут в **ту же** транзакцию, поэтому не бывает чека без заказа и заказа, за который никто не выставит счёт. `db/rollback!` разворачивает стек, причина выставлена до разворота — и на странице оказывается «раскупили, пока вы думали», а не 500
- [x] Отказ платёжного шлюза и его молчание — **разные вещи**: отклонение это возвращённое значение, таймаут это ошибка; первое отменяет заказ сразу и возвращает остаток на полку (компенсация, потому что checkout его уже снял), второе void/jobs переигрывает с backoff'ом и отменяет на последней попытке. Обе ветки в сюите детерминированы (сумма, оканчивающаяся на 13 копеек, отклоняется всегда)
- [x] Атрибуты **вытягиваются**, и в этом приложении видно, зачем: роль сессионной личности — claim, скопированный `void/auth-db` со строки при входе, поэтому шапка и стол оператора решают без запроса; у API-токена claim'а нет, и провайдер атрибутов читает строку **тогда, когда политика спросила про роль**, — токен месячной давности не удерживает роль, отобранную вчера
- [x] **Ответ на вопрос «где чему лежать»**, потому что своей модульной системы у void нет и примеры обычно оставляют это на вкус: модуль — это директория `src/modules/<module>/`, а слой написан суффиксом файла — `*.model` (`defentity`, единственное место, называющее таблицу), `*.dto` (`defschema` и проекция к нему), `*.repository` (все запросы модуля и ничего про запрос, сессию и личность), `*.service` (правила: транзакции, инварианты, телеметрия, что публиковать — и ни строки SQL), `*.controller`/`*.api` (распаковать запрос, позвать сервис, выбрать представление и статус), плюс по адаптеру на заботу: `*.policy`, `*.jobs`, `*.events`, `*.mailer`, `*.session`, `*.telemetry`. Зависимости идут в одну сторону, и оба конца цепочки — то, ради чего разделение и делается: оформление заказа читается без существующего запроса, политики тестируются без базы, а JSON-API — сорок строк, а не второе приложение. Композиция модулей — **импорты в `src/app.janet`**: реестра, в который надо записаться, нет, `defentity`/`defroutes`/`defjob`/`defhandler`/`defpolicy` срабатывают на загрузке файла, поэтому «подключить модуль» и «удалить модуль» это одна строка
- [x] Docker: `Dockerfile` (две стадии — компилятор остаётся в первой) и `docker-compose.yml` с Postgres, redis, почтовым сервером с веб-ящиком, одноразовой миграцией, web и worker'ом, **где web и worker это один образ и один код, отличающиеся двумя переменными окружения**; `--profile obs` добавляет Prometheus и Grafana с готовым дашбордом. Схему очереди и лога сообщений создаёт миграция приложения из DDL, который плагины отдают данными (`[:jobs-db :auto-create]` и `[:bus-db :auto-create]` в `:prod` выключены: два процесса, стартующие одновременно, гонятся на `CREATE INDEX IF NOT EXISTS`)
- [x] Сюита — три файла: сквозной прогон через `test/inject` на обоих движках (каталог, корзина, оформление, джоба платежа, отсутствие товара, отклонённая карта, row-level авторизация, стол, `/metrics`, лимит частоты), JSON-сторона (пагинация, problem+json, кэш ответа, bearer, OpenAPI-документ) и политики как таблица случаев вообще без системы

### 4.1 Протокольная ветка

- [x] `void/proto` *(M)* — pure-Janet varint/wire-кодек (hot core можно в C позже), PEG-парсер `.proto` → schema-проекции → codegen; фундамент для grpc и OTLP
  - [x] Кодек совпадает с `protoc` **побайтно**, и это единственное утверждение, которое стоит делать о wire-формате: golden-векторы в `proto/test/codec-test.janet` напечатаны `protoc --encode`. Все шестнадцать скалярных типов, packed и unpacked repeated, map'ы, oneof, явное присутствие `optional` — и обратно тем же байтам
  - [x] Честность про 64 бита собрана в одну функцию (`wire/narrow`): int64, не помещающийся в double, возвращается `int/s64`, а не округляется — та же политика, которую `void/db-postgres` применяет к int8, и та же, которой proto3 JSON носит такое число строкой. IEEE 754 расписан руками, потому что Janet не умеет паковать float ни через `int/to-bytes`, ни через `marshal`; зато результат не зависит ни от порядка байт хоста, ни от нативного модуля, и сюита проверяет битовые шаблоны из стандарта, включая субнормальные
  - [x] Неизвестные поля **переживают** раунд-трип: байты полей, которых в дескрипторе нет, лежат в `:proto/unknown` и уезжают обратно на следующем encode. Прокси, sidecar и реплика постарше не должны быть причиной, по которой поле, добавленное соседом, исчезло — decode, роняющий их, превращает read-modify-write в потерю данных
  - [x] Каждое зарегистрированное сообщение — **зарегистрированная void-схема** под тем же именем: `void/proto/schema` *смотрит* на реестр дескрипторов (`descriptor/watch!`), поэтому сообщение из `.proto` немедленно видят `[:ref ...]`, `void schemas`, документ OpenAPI, валидация тела в `void/rest` и формы `void/admin` — и ни один из них не узнал, что такое protobuf. Это волна 1, окупающаяся дважды. Обратная проекция (`:proto` — строка, которую SPEC §3.3 зарезервировал под «protobuf descriptor») требует `:proto/field` у каждого поля: номер — это контракт совместимости, и придуманный из порядка ключей он сломал бы всех peer'ов на первом же переименовании
  - [x] proto3 и только proto3: `required`, `group`, `extensions` и `default =` отвергаются **по имени**, а не приближаются молча. Парсер читает настоящие файлы — `google/protobuf/api.proto` со всем импортом разбирается целиком, — а `google/protobuf/*.proto` резолвится из `./wkt`, а не с диска: Timestamp, Duration, девять обёрток, Empty и FieldMask со своими JSON-формами; `Any`, `Struct`, `Value` и `ListValue` названы отсутствующими с причиной
  - [x] `defproto` парсит файл **во время компиляции модуля** и запекает дескрипторы значениями: работающее приложение `.proto` не читает (§8.5, правило 3). Это и есть «codegen macros» из SPEC §5.7 — генерируется не класс, а данные
  - [x] Бенч-строчка, которую требует ADR-0013 (`proto/test/bench-test.janet`): печатает, а не гейтит — абсолютные числа на общем раннере не значат ничего (ADR-0014), а два коммита по ним сравнимы
- [x] `void/grpc` *(M; ADR-0013)* — Connect protocol поверх void/http (unary, HTTP/1.1), JSON+protobuf кодеки, `defservice` из `.proto`; route metadata работает на RPC-методах так же, как на HTTP
  - [x] **Метод — это маршрут**, и в этом всё содержание пакета: каждый зарегистрированный метод проецируется в общую таблицу — с именем, с метаданными, в `void routes` и в `explain-route`. Поэтому `:void.authz/policy` на RPC-методе проверяет то же middleware в той же фазе, что на странице, `:void.db/txn` открывает ту же транзакцию, `void/obs` считает RED по имени маршрута, `void/pressure` его шеддит, `void/security` стоит перед ним — и ни одна строчка этого не написана здесь. `grpc/test/policy-test.janet` проверяет и обратную сторону: под `[:authz :default :deny]` RPC-метод без политики **не даёт стартовать**
  - [x] Ничего не объявлено дважды: методы, их сообщения и `idempotency_level` приходят из `.proto` через реестр `void/proto`, а `defservice` добавляет ровно две вещи, которых файл сказать не может, — функцию и метаданные маршрута. Метод, объявленный в файле и никем не отвеченный, роняет **объявление**: `unimplemented`, который клиент находит в проде, — это дырка в контракте, и находит её не тот, кто может её закрыть
  - [x] GET для методов, объявивших `idempotency_level = NO_SIDE_EFFECTS`, — форма самого Connect и не украшение: GET понимает кэш, поэтому `:void.cache/response` работает на RPC-методе так же, как на странице (у GET-маршрута своё имя — суффикс `-get`, который в protobuf-идентификаторе невозможен)
  - [x] Ошибка — это шестнадцать кодов и **две** таблицы: код → HTTP-статус (это протокол) и HTTP-статус → код (это решение, поэтому оно записано в `codes.janet` построчно). 403 от `void/authz`, 429 от лимитера и 503 от `void/pressure` доезжают до сгенерированного клиента Connect-ошибкой, а не HTML-страницей: отдельный `:void.http/error-renderer` с приоритетом перед problem+json, потому что на RPC-маршруте клиент — это заглушка, читающая одну форму и не читающая другую
  - [x] Клиент — вторая половина того же протокола на `void/http/client`: ошибка **поднимается**, как её поднимает любой сгенерированный клиент, дедлайн едет `Connect-Timeout-Ms` и соблюдается обеими сторонами, а запрос, никуда не доехавший, становится `unavailable`/`deadline_exceeded`, а не транспортным шумом
  - [x] Стриминга нет честно: `.proto` со `stream` отвергается на `defservice`, где ошибку читает тот, кто может поменять файл или дождаться v2 (ADR-0013). Компрессии нет: у void нет компрессора, и запрос с `Content-Encoding: gzip` получает 415 с кодом `unimplemented` и заголовком `Accept-Encoding: identity`, а не отказ разбора, похожий на порчу данных
- [x] `void/obs` OTLP export (metrics + traces) — **сделано раньше `void/proto` и без него** (ADR-0027): OTLP/HTTP определяет и JSON-кодировку, а коллектор принимает её из коробки, так что protobuf оказался требованием традиции, а не спецификации. `[:obs-otlp :encoding]` — шов с одним легальным значением сегодня; `void/proto` добавит второе, и `encode` — единственная функция, которая об этом узнает
- [x] `[:obs-otlp :encoding] :protobuf` — второе значение того шва, и обещание ADR-0027 выполнено буквально: payload остался один (тот, что строит `./otlp` для JSON), бинарная кодировка — его вторая проекция (`void/obs/otlp-proto`: `from-json` через proto3 JSON mapping → `proto/encode`), и `encode` — единственная функция, узнавшая о второй ветке. Шесть `.proto` из opentelemetry-proto (v1.5.0: common, resource, trace, metrics + два collector-запроса) завендорены в дерево модуля и запечены `defproto`; единственное именованное расхождение OTLP/JSON с proto3-маппингом — trace/span id в hex, а не base64 — переписывается перед маппингом и нигде больше. Модуль грузится лениво: композиция на JSON-дефолте не парсит ни строчки, `:protobuf` проверяется на старте, а single-binary отдаёт модуль через `otlp/use-module!` (шов `db-sqlite`, docs/DEPLOY.md). Попутно `void/proto` научился hex в значениях enum (`SPAN_FLAGS_TRACE_FLAGS_MASK = 0x000000FF` — настоящий файл, который раньше не парсился) и резолвит относительные `:paths` `defproto` от файла-источника, а не от cwd процесса
  - [x] `void/http/client` — вторая половина HTTP-ядра, которой не было: голова ответа и чанки читаются теми же `wire`-парсерами, что пишет сервер; keep-alive на одно соединение с единственным авто-повтором (сокет, закрытый peer'ом, — запрос никого не достиг), таймаут отдельной задачей с `ev/deadline` (отмена фибры вызывающего — класс багов ADR-0015), `https://` — ошибка на разборе URL с текстом про релей рядом (ADR-0010)
  - [x] Клиент доведён до поверхности `gleam-lang/http` (ADR-0027): любой метод + сахар `head/options/delete/put/patch`, `:query` парами, `:cookies` именами и значениями, тело как `:body`/`:form`/`:multipart`, `url`/`resolve-url`, а на ответе — `header`/`header-values`/`cookies` (с атрибутами) и `redirect?`/`follow-target`. Редиректы — только по `:follow n`, с ответами вслух на два вопроса политики: метод (303 → GET, 301/302 превращают POST в GET, 307/308 сохраняют) и учётные данные (`Authorization`/`Cookie` снимаются при смене origin). Cookie jar по-прежнему нет — обе половины разобраны, хранение между запросами это сессия
  - [x] Недостающие половины форматов дописаны там, где живут их первые половины: `wire/url-decode`, `wire/cookie-header`, `wire/parse-set-cookie`, `multipart/content-disposition` (публично) и `multipart/encode` — сервер и клиент читают и пишут один формат одной реализацией. Заодно закрылась асимметрия: `ring/cookie-str` кодировал значение процентами, `wire/parse-cookies` не декодировал; теперь декодирует, не трогая `+` (куки носят base64)
  - [x] `void/obs-otlp` — третий плагин пакета obs: **вклад в `:void.obs/exporter`**, а не изменение трейсера, и на пути завершения спана это один ограниченный `ev/give`. Очередь 2048 / батч 512 / флаш 5 с (дефолты OpenTelemetry), метрики отдельным периодом 60 с; полная очередь роняет спан и считает его — телеметрия, тормозящая сервис, хуже отсутствия телеметрии. Повторяются только таймаут, 429 и 5xx, 4xx роняется сразу
  - [x] Метрики — **вторая проекция того же снапшота**, что рендерит `prometheus/render` (обещание ADR-0021, выполненное буквально): имена серий прометеевские, единица из суффикса имени, темпоральность cumulative со `startTimeUnixNano` от старта процесса, наносекунды строкой (uint64 не живёт в double). Метрика, ни разу не сработавшая, объявляется скрейперу и не отправляется никому
  - [x] Учётные данные и сеть: дефолт `http://127.0.0.1:4318`, `[:obs-otlp :headers]` с непетлевым эндпоинтом — **ошибка старта** (bearer-токен открытым текстом — тот же дефект, что SMTP AUTH в `void/mail`), непетлевой без них — предупреждение. `void obs otlp-check` спрашивает коллектор с той стороны конфига

### 4.2 `void/ws` *(M)*

- [x] RFC 6455: handshake, frames, ping/pong, close; per-connection fiber; channels/rooms, broadcast — **сокет это маршрут** (ADR-0028): `ws/accept` из обычного handler'а, поэтому рукопожатие уже прошло весь путь запроса, и `:void.authz/policy` на websocket-маршруте работает, не зная, что она на websocket-маршруте. Ядро отдаёт соединение одним ключом ответа (`ring/upgrade`) и не знает слова «websocket»; байты, пришедшие за головой, передаются вместе с сокетом. Нарушения протокола — это коды, которые велит сообщить RFC (1002/1007/1009), а не тексты; текст обязан быть UTF-8, и это проверяется
- [x] Метка `:void.ws/socket` обязательна: маршрут с ней и с `:void.http/timeout` **не стартует** — дедлайн отменил бы разговор через тридцать секунд, и в проде это выглядело бы как сетевая проблема
- [x] Две фибры на соединение (читает та, что была у запроса) и ограниченная очередь на запись: рассылка — это N постановок в очередь и возврат, переполнение закрывает соединение (`[:ws :overflow :drop]` — для потоков независимых фактов). Живость — один подметающий цикл на процесс, а не таймер на сокет
- [x] Комната = множество соединений под keyword; рассылка кодирует сообщение **один раз** на всех. Prefork: у каждого воркера свой реестр, fan-out между ними — подписчик `void/bus`, три строки в приложении (ADR-0010, ADR-0012)
- [x] `void/ws/client` — вторая сторона того же кадрирования, с pull-API (`receive`): без неё suite тестировал бы протокол против себя, а B4 нечем было бы нагружать
- [x] htmx ws-extension: hiccup-фрагменты по id — `void/ws-htmx`, отдельный плагин пакета (приложение с JSON-сокетами не тянет шаблонизатор); элемент без `id` — ошибка с текстом, а не молча не приехавший swap
- [x] Bench B4 (broadcast 1k conns) в CI — свой генератор вместо wrk, своя строка бюджета (доставка < 50 мс, 10k msg/s), ставка вещания с запасом над полом: гейт, запущенный ровно на своём бюджете, меряет округление на краях окна

### 4.3 `void/mcp` *(S/M)*

- [x] MCP server: JSON-RPC 2.0 (2025-06-18) поверх stdio (`void mcp serve` — строка это сообщение) и поверх **обычного маршрута** `POST /mcp` (`void/mcp-http`, отдельный плагин пакета). Батчи отвергаются с текстом: их убрали в 2025-06-18. Ошибка инструмента — это `isError`-результат (её читает модель), ошибка протокола — это ошибка JSON-RPC (её читает клиент)
- [x] Авто-экспозиция как **проекция, а не второй реестр** (ADR-0031): CLI-команды → tools (интерфейс команды — argv, и схема инструмента говорит это вслух), реестр схем → `void://schema/<Name>` (JSON Schema через *модуль* `void/openapi/jsonschema`; схема со ссылкой везёт цель с собой в `components/schemas`), `plugin/health` → `void://health`, экспозиция Prometheus → `void://metrics` (`void/mcp-obs`). Плюс две точки расширения — `:void.mcp/tool` и `:void.mcp/resource` — тот самый шов, который [ADR-0029](adr/0029-admin-kak-proekciya-deklaracij.md) обещает админке
- [x] **Ворота структурные, а не списочные**: инструментом становится команда, объявившая `:read-only? true` — новый необязательный ключ контракта `:void.core/cli` **в ядре**, потому что вопрос «меняет ли эта команда что-нибудь» задаёт не MCP, MCP оказался первым, кому нужен ответ. Молчание значит «неизвестно», и неизвестное не показывается никогда; allowlist `[:mcp :tools]` открывает остальное поимённо, `[:mcp :hide]` перевешивает оба, опечатка в любом из списков — **ошибка старта** со словарём в тексте. `void mcp tools` печатает обе половины: что экспонировано и что удержано — с причиной по каждой команде
- [x] stdout принадлежит протоколу: `:out` связывается буфером на время вызова, и напечатанное командой становится текстом ответа — команда не знает, что такое MCP, и не должна узнать. stdin читается **потоком** через ev-цикл: этот процесс — целое приложение, и воркер очередей в нём работает, пока агент думает. Компоненты поднимаются по требованию (`:needs` инструмента), а в уже обслуживающем процессе — нет: вызов из запроса не заводит пул к базе побочным эффектом
- [x] Ничего не хранится: `Mcp-Session-Id` не выдаётся, потока между запросами нет, поэтому `GET /mcp` — 405 с объяснением, а не транспорт 2024-11-05 (он приколотил бы сессию к процессу — ровно то, что запретил [ADR-0030](adr/0030-forma-razvertyvaniya-i-razdelyaemye-hranilisha.md)). SSE включается ровно там, где ему есть что везти: `tools/call` с `progressToken` отдаёт `notifications/progress` с тем, что команда напечатала с прошлого тика
- [x] Ворота HTTP: bearer-токен (сравнение без утечки префикса) и allowlist `Origin` (защита от DNS rebinding, которую требует спецификация; умолчание отсекает браузерную страницу, не мешая агенту), в `:prod` без токена — **ошибка старта**, называющая оба выхода. Конфига в ресурсах нет ни в каком виде
- [x] **Авторизация MCP закрыта по-настоящему** ([ADR-0032](adr/0032-resource-server-a-ne-oauth-klient.md)): `[:mcp-http :auth]` — `:token` (общий секрет, как было), `:identity` (идентичность из **dyn-ключа** `:void.auth/identity` плюс `[:mcp-http :scopes]`) или `:none`, и `:none` в `:prod` — ошибка старта, называющая три выхода. `void/mcp-http` не получил ребра на `void/auth`: он читает ключ по имени, поэтому OAuth-токен, сессионная кука и чужая аутентификация работают одинаково. Отказ несёт `WWW-Authenticate` с кодом RFC 6750 и `resource_metadata=` — тем самым указателем, по которому MCP-клиент узнаёт, у какого authorization server брать токен
- [x] Свёртка здоровья переехала в ядро (`plugin/health`) — у неё стало два читателя: `GET /health` (`void/obs-http`) и ресурс `void://health`; обе — проекции одного отчёта, а не две его версии
- [x] Dogfooding: `examples/shop` компонует `:void/mcp` + `:void/mcp-obs` и **без единой строки конфига** отдаёт агенту 30 инструментов и 17 ресурсов — все из плагинов, которые про MCP ничего не знают (после 4.4 их 45 и 23: та же композиция плюс `:void/admin-mcp`, и снова без строки конфига). `test/mcp-test.janet` проверяет обе половины списка: `jobs stats`/`bus tail`/`db status` есть, `db migrate`/`jobs work`/`mail send`/`shop seed` нет. HTTP-транспорт там намеренно не подключён: пример не раздаёт tool-эндпоинт на порту, который сам же велит открыть

### 4.4 `void/admin` *(M/L — killer feature)*

- [x] `defresource-admin`: schema + entity → CRUD через html+htmx. Декларация — **замороженное значение в реестре**, а не функция, строящая маршруты (ADR-0029 §1): из группы маршрутов нельзя прочитать «какие поля в списке» и «какая схема у формы», а именно это читает вторая проекция. Форма — это `schema/select` по сущности, то есть валидация формы и входная схема MCP-инструмента буквально одно значение. Список: фильтры (фасеты выведены из схемы), поиск, сортировка кликом, пагинация, правка ячейки на месте — и **состояние живёт в URL**, поэтому кнопка «назад» работает, а сервер не помнит между запросами ничего (§6, §10)
- [x] Каждое действие — **настоящий маршрут** `:admin.<ресурс>/<действие>` (§2, форма ADR-0028): `void routes` печатает админку построчно, `explain-route` объясняет её metadata, транзакция объявлена в `:void.db/txn`, CSRF приходит через слот, который `void/html` носит с волны 1. Ни одна защита, написанная для маршрута, не написана здесь второй раз. Форма без htmx доезжает до `PATCH`/`DELETE` через `?_method=`, переписываемый edge-обёрткой только под префиксом админки и **только из POST**
- [x] Widgets — контракт целиком, а не одна функция (§4): `:render` обязателен, `:display`/`:filter`/`:parse`/`:assets`/`:routes` отвечают на вопросы, которые иначе стали бы частными случаями ядра. Разрешение — **раз на поле при монтировании**, не раз на строку, и результат печатается (`void admin widgets`): на вопрос «почему поле нарисовано так» отвечает команда. Связь `belongs-to` рисует один виджет, выбирающий форму по размеру цели — три настройки Django здесь одно решение; автодополнение FK — первый пользователь `:routes`, а не частный случай ядра
- [x] Авторизация насквозь: **ворота закрыты по построению** — `:void.admin/access` отказывает, пока `[:admin :access]` не назовёт политику приложения, и текст отказа называет ключ, который его снимает (§3). Поверх — `:admin.<ресурс>/<действие>` по действию, разрешающая, существующая ради имени: сузить действие это `defpolicy`, и ни декларация, ни маршруты не меняются. Эшелонирование row-level: `:scope` сужает `query` **и** `count` одним выражением (пагинация считает то, что показывает), а каждое действие над одной строкой проходит политику с загруженной строкой в `:resource` — строка читается один раз, потому что загрузчик мемоизирует на запросе. Инлайн сторожат все три политики, и внешний ключ на родителя ставится из URL, а не из формы
- [x] Audit log — **админка не владеет таблицей** (§8): изменение объявляется core-хуком `:void.admin/changed`, историю отдаёт точка `:void.admin/history`, миграций пакет не приносит. `examples/blog` закрывает обе одной функцией над трейлом, который у него был с 3.6. Custom actions — страница подтверждения со **счётом на сервере** (число от клиента не значит ничего, `?all=1` пересчитывается по фильтру), тяжёлые уходят в `void/admin-jobs` (прогресс — состояние записи задачи, ради виджета контракт `:void/jobs-backend` не правился), а композиция с `:job`-действием и без этого плагина **не стартует**. Точки `/page`, `/dashboard-widget`, `/menu` монтируются такими же настоящими маршрутами с теми же воротами
- [x] **MCP-проекция**: `void/admin-mcp` читает тот же реестр и те же имена политик — `void/admin` не содержит ни строки про MCP, как и обещал шов 4.3. Ворота ADR-0031 применяются без исключений: `list`/`get`/декларация read-only и экспонированы, `create`/`update`/`delete` и объявленные действия — нет, пока оператор не назовёт их в `[:mcp :tools]`. Входная схема `create` — это `(desc :form-schema)`, то есть колонка, которую форма не даёт править человеку, отсутствует и у агента. `examples/blog` компонует обе проекции: у одного и того же автора страница и агент видят одни и те же строки, потому что `:scope` и политики одни (exit-критерий 1)
- [x] Второй стенд, и он про другое: `examples/shop` разложил декларации **по модулям** (`src/modules/*/*.admin.janet`) — бэк-офис это слой модуля, ровно как `*.api.janet`, а не модуль; директории `admin/` с контроллером, вью и тремя написанными руками маршрутами в примере больше нет. Что здесь показано сверх blog'а: действие как **доменный вызов** (`:ship` зовёт `orders.service/ship!`, и «отгружается только оплаченный» остаётся у записи, а не переезжает на кнопку), bulk через `void/admin-jobs` (`:archive` объявлен `:job`, подтверждение становится страницей прогресса, строки меняет воркер под личностью нажавшего), правка ячейки на месте, фильтр по enum'у, сужение действия одной `defpolicy` (стол не правит аккаунт, под которым вошёл — политика проверяется в `test/policy-test.janet` таблицей случаев, рядом с `:orders/own`), и `:mount false` для строк заказа и платежей — декларация без раздела, но с инструментами для агента
- [x] Композиция, которой раньше не было, нашла три вещи. `[:admin :route-meta]` — приложение с OpenAPI-документом обязано уметь сказать что-то про маршруты, которых оно **не объявляло**: документ это проекция таблицы маршрутов, metadata ставит только тот, кто маршрут объявил, и одна строка `{:void.openapi/hidden true}` убирает все 23 маршрута админки из публичного описания API (метаданные едут на группе, поэтому ключ, который ставит сама проекция, всё ещё выигрывает). `:enum` со строковыми членами не фильтровался вовсе — `coerce` искал keyword, а `[:enum "active" "archived"]` это обычная декларация (у shop'а статусы текстовые: два драйвера по-разному читают boolean-колонку). И маршрут FK-автодополнения нёс необъявленный ключ metadata `:void.admin/widget-route`, то есть **любая** админка, где `belongs-to` смотрит на ресурс с `:search`, не стартовала: ключ теперь объявлен там же, где остальные контракты
- [x] Один шов пришлось объявить в чужих контрактах, и симметрично: реестр наполняют модули приложения, то есть **позже**, чем замерзает манифест, — поэтому `:void.http/route-source` принимает в `:routes` функцию от boot, а `:void.mcp/tool`/`:void.mcp/resource` — `:expand`. Оба сформулированы как «источник, который является проекцией того, что разрешил bootstrap», и ни один существующий читатель не изменился (ADR-0029 §12)

### 4.5 `void/cli` — добить artisan

- [x] `void make resource Article title:string body:text votes:int? author:ref:Author` — четыре файла, и все четыре суть проекции одной декларации: `defentity` это схема **и** маппинг (ADR-0009), разметка формы и её валидация это `schema/select` по тому же узлу (ADR-0008), маршруты несут те самые имена, о которых потом спросит политика (ADR-0029), а миграция создаёт ровно те колонки, которые назвала сущность. Расходиться нечему — кроме миграции, единственного файла, который проекцией **не** является, и потому сгенерированная сюита читает её обратно как данные и сверяет колонку за колонкой. Базы эта сюита не требует вовсе: ошибка, которую генератор реально делает, — это поле, переименованное в одном месте и не переименованное в остальных, и ловится она без драйвера
- [x] Шаблоны — данные: кортеж `{:key :path :render}`, где `:render` чистая `(fn [spec] string)`; проект подменяет любую запись файлом `templates/resource/<key>.janet` с `render` (и, если файл должен лечь иначе, `path`). Второго языка шаблонов нет и не будет: `{{key}}` это дырка и ничего больше (`void/cli/template`, общий с `void new` — текст генерируемого файла читается в исходнике ровно так, как ляжет на диск), а проекту, которому нужно больше дырки, отдаётся вся запись — на Janet, на котором он всё равно будет править вывод
- [x] Ничего существующего не редактируется: `make` пишет новые файлы, отказывается затирать (`--force`, если всё-таки надо) и **печатает** строку, которую следует добавить в `:plugins`, вместо того чтобы лезть в main.janet. Генератор, переписывающий правленый руками код, — это генератор, который запускают один раз. `--dry-run` печатает то же самое в stdout, поэтому дружит с пейджером и диффом
- [x] Интерактив через rawterm — и у каждого вопроса одно определение и два фронта: на терминале сырой режим рисует промпт (умолчание по Enter, список по стрелкам), без терминала тот же вопрос читает строку и на EOF берёт умолчание. Скаффолдер, работающий только перед человеком, — это скаффолдер, который не запустить ни из CI, ни из Makefile; сырой режим снимается в `defer`, потому что упавший генератор не должен оставить шелл без эха
- [x] `void plugins lock` / `void plugins check` — композиция уже была значением (`plugin/bootstrap` даёт список плагинов, каждую точку расширения с contribution'ами **в порядке разрешения** и граф компонентов, всё до того, как что-нибудь открыло порт); не хватало того, кто это запишет. Теперь «почему в проде другой middleware-стек» — это дифф, а не расследование: `check` в CI стоит один dry-run (миллисекунды, ни сокета, ни базы) и валит сборку на появившемся плагине, уехавшей версии, переехавшем в цепочке contribution'е и форме развёртывания, отличной от той, в которой брали lock
- [x] Хеш покрывает композицию **как данные**, с каждой функцией, свёрнутой в её имя: у функции нет устойчивой идентичности между двумя процессами, и хешировать её значило бы получать новый хеш на каждом запуске. Вставленный, удалённый, переименованный или переставленный по фазе middleware хеш меняет; правка в теле middleware — нет. Граница названа в шапке самого lock-файла, потому что инструмент, ловящий изменившееся тело, — это тот, который и так смотрит в исходники. FNV-1a 64 по канонической записи (ключи отсортированы, одно написание на значение), а не криптография: отказ, которого здесь быть не должно, — это случайно совпавшие окружения, а редактирующий lock-файл злоумышленник уже внутри репозитория
- [x] `jpm quickbin` single-binary + [docs/DEPLOY.md](DEPLOY.md) — история, проверенная целиком, а не оценённая: 1.05 MB для скаффолда, 1.14 MB со своим CLI внутри, 2.4 MB с вкомпилированным sqlite; на цели ни janet, ни jpm, ни дерева модулей, из динамических зависимостей — `libSystem`. Два следствия marshal'а образа — верхний уровень выполняется на машине **сборки**, а `require` во время выполнения не находит ничего — превращены в четыре правила, и два из них уехали в сам скаффолд: профиль читается в `main`, а не в значении, и `void/dev` не входит в prod-композицию (свой netrepl он строит через `require`)
- [x] `cli/app-main`: бинарь с аргументами **это** `void` — `db migrate`, `routes`, `deploy check`, `plugins check`, `jobs work` против той композиции, которая внутри этого файла, и никакой другой. История развёртывания, в которой нельзя накатить миграцию, — не история. Работает потому, что boot-опции передаются значением: на цели нет main.janet, который `load-app` мог бы затребовать, и не нужен. Через него теперь входит не только скаффолд: `examples/shop` читает окружение в `main`, а не в значении, которое замёрзло бы на машине сборки (правило 1), и остаётся тем же `janet main.janet` для docker-compose. `void/dev` из его `:prod`-композиции при этом **не** выкидывается, и это решение, а не недосмотр: compose разворачивает из исходников, где netrepl стоит unix-сокет внутри контейнера и даёт `docker compose exec web void repl` — REPL в работающем веб-процессе; выкидывать его нужно ровно в single-binary, и это одна строка, показанная на `examples/guestbook`
- [x] `void/db-sqlite` получил шов `use-module!` — единственный его вызывающий это single-binary, у которого модуль уже влинкован, а дерева для `require` нет. Ленивый `require` остался умолчанием, потому что именно он держит janet-lang/sqlite3 вне зависимостей бандла (ADR-0020), и сообщение об ошибке теперь называет оба выхода

### 4.6 Fleet: ни одного in-memory хранилища за пределами одного процесса *(M; ADR-0030)*

Аудит волны 4 показал класс ошибок, который не ловился ничем. Разделяемые замены **есть почти для всего** (`void/redis-http`, `void/cache-redis`, `void/auth-db`, `void/jobs-db`/`-redis`, `void/bus-db`), и каждое in-memory хранилище честно говорило о себе в докстринге — но **все реальные проверки были навешаны на `[:http :workers]`, а это вертикаль**. Три реплики с `workers: 1` за балансировщиком проходили каждую проверку и ломались молча: сессии, rate limit, одноразовые коды и API-токены `void/auth`, `cache/forget`, memory-backend `void/jobs` и `void/bus`. Правильная форма проверки в репозитории уже была — в `void/security/secret` и `void/mail`, завязанная на **профиль**; и словарь для вопроса «я разделяемый?» уже был у `void/jobs` (`capabilities` → `:shared?`) и `void/bus` (`:guarantees {:shared}`). Не хватало того, кто спросит.

- [x] `[:deploy :shape]` — `:single` | `:fleet`; умолчание `:single` в `:dev`/`:test` и **`:fleet` в `:prod`** (безопасное значение по умолчанию, отказ от него — одна строка); `workers > 1` подразумевает `:fleet`, то есть сегодняшняя проверка стала частным случаем, а не всей проверкой. Слайс принадлежит `void/core`, который не плагин, поэтому валидируется прямо в `bootstrap` — как `[:log]` конфигурируется прямо в `start!`, — и форма едет на boot-значении, так что `plugin/dry-run` знает её, ничего не запуская
- [x] `:shared?` в контрактах, где его не было: `:void.http/session-store` (плюс `:replacement` в самой contribution), `:void/cache-store`, challenge- и token-store `void/auth`, лимитер `void/security`. Умолчание — `false`: хранилище, написанное без этого вопроса в голове, это хранилище в куче, и молчание значит именно это. **User-store `void/auth` намеренно не спрашивают** — он засевается из `[:auth :users]`, то есть построен из конфига и разделяем по построению
- [x] Одна точка расширения ядра — `:void.core/store` с функцией `:ask`, которую зовут **последним действием `plugin/start!`**, когда всё поднято (включая то, что плагин поднимает своим хуком `:after-start`, — лимитер `void/security`): спрашивают объект, который композиция подняла, а не имя, которое назвал конфиг
- [x] Под `:fleet` — **отказ на старте одной ошибкой со списком всех** per-process хранилищ композиции и заменой для каждого; форма — `authz-http/deny-by-default`, а не N отдельных падений. Выход назван в самом сообщении, включая тот, при котором прав конфиг: `[:deploy :shape] :single`
- [x] Закрыта единственная дыра в покрытии: session-store поверх `void/db` живёт в `void/db-http` — там же, где `:void.db/txn`, потому что это второй кусок `void/db`, которому нужен `void/http`. Часы `:realtime`, а не `:monotonic` (монотонные считают от своей точки в каждом процессе); просрочка подметается, потому что у базы нет TTL; запись — `UPDATE`, а при нуле строк `INSERT`, потому что `ON CONFLICT` в каждом диалекте свой
- [x] Сняты устаревшие проверки на `workers` в `void/http` (ошибка сессий) и `void/security` (предупреждение лимитера) — они стали проекцией одного ключа буквально
- [x] Оставлено per-process то, что per-process **правильно**, и сказано это в самой проверке третьим значением `:shared? :by-design` с обязательным `:why`, чтобы её не «чинили»: комнаты `void/ws` (ADR-0028, fan-out через шину), sampler `void/pressure` (RSS и loop-lag — факты процесса), реестр метрик `void/obs` (агрегирует Prometheus/коллектор)
- [x] `void deploy check` — готовность композиции к fleet печатается **до** деплоя: команда поднимает объединение `:needs` всех деклараций и ничего больше, поэтому порт не открывается и её можно запустить на машине, которая уже обслуживает; `void/dev` печатает тот же отчёт баннером
- [x] `examples/*` честны про развёртывание: `blog` говорит `{:deploy {:shape :single}}` и объясняет рядом с `[:cache]`, что `cache/forget` чистит **тот store, который резолвила композиция**, а этот в куче; `shop` говорит `:fleet` вслух и называет разделяемую реализацию для каждого своего хранилища
- [x] Тесты: композиция с in-memory хранилищами под `[:deploy :shape] :fleet` **не стартует**, с разделяемыми — стартует; сообщение называет все нарушения сразу (`core/test/deploy-test.janet`, `http/test/deploy-test.janet`); db-session-store против настоящего sqlite и против записанного SQL (`db-sqlite/test/session-test.janet`, `db/test/session-test.janet`); `void deploy check` поднимает только `:needs` (`cli/test/cli-test.janet`)

### Exit-критерии волны 4

1. ✅ Demo: back-office с admin (row-level scoping) + те же ресурсы доступны AI-агенту через MCP с теми же политиками — **два** стенда, и оба одной композицией. `examples/shop` компонует `:void/admin` + `:void/admin-jobs` + `:void/admin-mcp` поверх приложения, у которого уже были сущности, политики, трейл и очередь: `test/admin-test.janet` (по разу на движок) проходит ворота, список с поиском/фильтром/счётом, правку ячейки, объявленное действие, которое зовёт сервис и оставляет неоплаченный заказ в покое, bulk-как-задачу, сужение действия политикой, трейл, в который изменения приезжают через `:void.admin/changed`, и те же декларации, вызванные как MCP-инструменты — с личностью и без. `examples/blog` компонует `:void/admin` + `:void/mcp` + `:void/admin-mcp`, и `test/admin-test.janet` проверяет обе половины одной композицией: список автора сужен `:scope`, чужая строка не найдена (а не «403 с телом»), инлайн ставит внешний ключ из URL, bulk называет число до того, как тронет строки, изменения уезжают в трейл 3.6 через `:void.admin/changed` — и тот же реестр, прочитанный агентом, отдаёт те же строки под теми же политиками, а без идентичности не отдаёт ничего.
2. ✅ Connect-RPC сервис вызывается buf-клиентом — `grpc/test/interop-test.janet` поднимает сервер на эфемерном порту и зовёт его `buf curl --protocol connect` по тому же `.proto`: успех, `not_found`, `permission_denied` и запись, включая proto3-JSON'овую строку для int64 и имя enum'а. Это гейт там, где `buf` установлен, и громкий пропуск там, где нет (та же форма, что у интеграционных тестов `void/db-postgres` под `VOID_TEST_PG`) — в CI-образе buf'а пока нет, так что проверяет её тот, кто трогает протокол. gRPC и gRPC-Web не поддерживаются и не притворяются: они получают 415, а совместимость с ними — это transcoding-прокси, что ADR-0013 и выбрал.
3. B4 в CI. Тег v0.4, публичный README по позиционированию §9.

## Волна 5 — тяжёлый FFI и прочее

Вне критического пути; порядок по потребности.

- [ ] `void/kafka` *(L)* — ffi librdkafka (callbacks → ev channels), producer/consumer, point `:void.kafka/handlers`; kafka-backend для bus
- [x] `void/db-mysql` *(M)* — ffi libmysqlclient, блокирующие вызовы → `ev/thread` pool. Поток на соединение ([ADR-0033](adr/0033-mysql-potok-na-soedinenie-i-tekstovyj-protokol.md)): `MYSQL*` рождается и умирает в своей VM, ev loop говорит с ним через threaded channels, фибра паркуется на `ev/take` — во время `SELECT SLEEP(0.4)` тикер отрабатывает больше двадцати раз, а два таких запроса на двух соединениях занимают 0.4 с, а не 0.8 с (`test/driver-test.janet`). Диалект `:mysql` — в `void/db/builder`, так что миграция объявляет тип, а не написание; `RETURNING` нет, поэтому `:returning false` и `:insert-id`, и entity-слой ходит своей второй дорогой (`test/entity-test.janet`). Prepared statements сознательно нет: `MYSQL_BIND` — структура, хвостом которой MySQL и MariaDB разошлись, а параметры вместо этого рендерятся через `mysql_real_escape_string` самого соединения, со сканером плейсхолдеров и проверкой их числа (`test/types-test.janet`, без сервера). Цена названа вслух: пул размера N — это N OS-потоков.
- [ ] `void/oauth` *(M)* — OAuth2/OIDC **client** (authorization code + PKCE, обмен кода, хранение refresh): вторая половина, потому что первая — resource server — сделана в 4.3 ([ADR-0032](adr/0032-resource-server-a-ne-oauth-klient.md)) и уже читает метаданные издателя, которые понадобятся клиенту
- [ ] `void/i18n` *(S)* — словари-данные, locale в dyn, интеграция со schema-ошибками и шаблонами
- [ ] `void/datastar` *(эксперимент)* — SSE + full-page morph (идиома Biff)
- [ ] `void/tls` *(low priority)* — ffi openssl/bearssl; до тех пор TLS = reverse proxy (ADR-0010)
- [ ] gRPC streaming через HTTP/2 *(XL — отдельное решение, новый ADR)*

## Definition of Done (для любого plugin)

1. Manifest проходит `plugin/dry-run`; удаление из `:plugins` не оставляет следов.
2. Config-schema + тесты на ошибочные конфиги; секреты не печатаются.
3. REPL-инспектируемость: `plugin/inspect` показывает все contributions.
4. Тесты: unit + интеграционный через `void/test`-fixtures; для middleware — строка в bench-таблице («B1 с моим middleware = −X%», §8.5).
5. Docs: README plugin'а + декларации metadata-ключей/extension points (авто-докгенерация).
6. Никаких блокирующих вызовов на ev loop (правило §8.5 п. 1).
