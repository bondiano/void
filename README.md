# void

> *void — everything Janet keeps, one import away*

A batteries-included web framework for [Janet](https://janet-lang.org/): Laravel/Spring-level capabilities, Lisp-idiomatic architecture, REPL-driven development as a first-class mode. Everything is extensible through plugins in the spirit of Spring auto-configuration — but with data instead of annotations and classpath scanning.

> The name comes from Janet canon (*The Good Place*): Janet's boundless void, where everything is stored — "batteries included" as a character. Not affiliated with Void Linux.

## Status

**v0.4 — waves 0–4 closed; the public-announcement candidate.** The wave-1 vertical (`void new myapp && cd myapp && void dev` — a schema-validated HTMX app with hot reload, live handler redefinition, automatic route-table rebuilds and a netrepl into the running process) has since grown a data layer (v0.2: db / sqlite / postgres / redis / cache / jobs / load shedding), an enterprise layer (v0.3: observability / auth / authz / security / mail / a message bus with a transactional outbox), and wave 4 — the protocols and the killer features: protobuf as data and Connect-RPC where a method is a route, WebSocket as a route, the application as an MCP server, the back office as a projection of the schema layer, `[:deploy :shape]` (a composition that says `:fleet` refuses to boot on any in-process store), and a single-binary deploy that is also the CLI. The Plugin API and Route Metadata contracts have been **frozen** since v0.1 — the registry is [docs/CONTRACTS.md](docs/CONTRACTS.md) (generated from the declarations, drift-checked in CI), the deprecation procedure is in [CONTRIBUTING.md](CONTRIBUTING.md).

The full specification lives in [docs/SPEC.md](docs/SPEC.md), the wave plan and per-wave status in [docs/ROADMAP.md](docs/ROADMAP.md), performance budgets and the recorded baseline in [docs/BENCH-v0.1.md](docs/BENCH-v0.1.md), the deploy story in [docs/DEPLOY.md](docs/DEPLOY.md). All of it is also a website — [bondiano.github.io/void](https://bondiano.github.io/void/), generated from this repository by `scripts/gen-site.janet` (the documents rendered as pages, plus a config and CLI reference projected straight from the composition's declarations) and republished on every push. Absolute §8.2 budgets are reference numbers, not gates: CI runs the relative 5% regression gates instead (ADR-0014).

## Quick start

```sh
jpm install https://github.com/bondiano/void.git   # the whole framework, one bundle

void new guestbook
cd guestbook
jpm --local deps    # pin this void in ./jpm_tree (the binary prefers it)
void dev            # dev profile: file watcher + netrepl + the app
void routes         # the route table, `void routes --keys` with metadata
void repl           # repl into the running process

void make resource Product name:string price:int notes:text?
                    # entity + form + views + routes + migration + a suite
void make auth      # register/login/logout, password reset and address
                    # verification, over void/auth — plus their suite
void plugins lock   # writes void.lock; `void plugins check` fails CI on a drift
jpm --local build   # -> build/guestbook: one file, no janet on the target
```

Every line of that runs on a clean machine as a CI job, not as a
paragraph here (ADR-0020). Installing needs a C compiler — spork, which
`void/core` depends on, builds nine native modules of its own, and void
adds one (`void/fdwait`, ~60 lines).

The generated app — the same one as [`examples/guestbook`](examples/guestbook) — is a server-rendered HTMX guestbook: one map schema drives the form markup, the coercing validation (`form/check`) and the re-render-with-errors loop; the POST route answers htmx requests with the bare fragment (`:void.htmx/partial`). Out of the box every request carries a request-id bound to the log context and an access-log record lands through `void/core/log` on the `:on-response` lifecycle stage (ADR-0016/0018); tests drive the full stack in memory with `test/inject` — no sockets (ADR-0017).

## Where void fits

The combination is the niche: a single binary < 5 MB, RSS < 50 MB, a live REPL into the production process, and batteries included (db / jobs / auth / observability / admin / MCP). Spring is a gigabyte of JVM; Rails and Laravel are an interpreter plus a dependency tree; Go is fast but ships neither batteries nor a REPL; redbean is close in spirit and has no ecosystem. The sweet spot: server-rendered HTMX applications of small-to-medium complexity where the cost of deployment and ownership matters more than peak throughput — internal tools and admin panels, solo/indie SaaS on a VPS, webhook and bot hubs, embedded web UIs (Janet embeds in C hosts), edge and cheap hardware.

**Honest anti-cases:** teams of 5+ developers (hiring), >10k RPS per process (SPEC §8: prefork, or another language), CPU-heavy workloads, domains that require thick vendor SDKs.

What counts as success is deliberately not adoption: (1) the time from idea to a working deploy for one developer, (2) how much of the vertical fits without leaving the stack, (3) the stability of the two frozen contracts.

## Repository layout

Monorepo of scoped Janet packages. They install as **one** jpm bundle
named `void` and release one version per wave — jpm resolves a
dependency to a git repository with a `project.janet` in its root, and
has no notion of a subdirectory (ADR-0020). The edges between the
packages are declared once, as data, in
[`scripts/packages.janet`](scripts/packages.janet); the bundle's source
list, every test suite's module path, the CI steps and the dry-run gate
are projections of it.

| `db-mysql/` | `void/db-mysql` — MySQL and MariaDB over libmysqlclient, which is blocking all the way down: there is no non-blocking API to park on, so a connection lives on a **worker thread of its own** and the ev loop talks to it over a channel (ADR-0033) — a query parks the calling fiber and stops nobody else, and the suite says so with a ticker running through a `SELECT SLEEP`. Real isolation levels, savepoints, and insert ids in place of a `RETURNING` MySQL does not have. Prepared statements are deliberately absent: reaching `mysql_stmt_*` means hardcoding the layout of `MYSQL_BIND`, whose tail MySQL and MariaDB have diverged on, and a wrong struct layout is a segfault rather than an error — so parameters are rendered into the statement through the connection's own `mysql_real_escape_string`, behind a placeholder scanner that knows a `?` inside a literal, an identifier or any of MySQL's three comment forms is data. The one struct it does read is checked at connect with a probe, so an unfamiliar client library is a boot error naming itself. The price is named out loud: a pool of N is N OS threads | 5 |
| `redis/` | `void/redis` — RESP2/RESP3 in pure Janet on the ev loop (no native code, no client library): the wire format as a length-driven scanner plus a PEG, a fiber-aware pool, pipelining, value codecs behind `:void.redis/codec`, Lua scripts, and pub/sub on a connection of its own. `void/redis-http` (same package) contributes the `:redis` session store, which is what lets sessions and a fleet coexist | 2 |
| `cache/` | `void/cache` — the cache: the `:void/cache-store` contract and the `:void/cache` interface over it, an in-process store with TTLs and an exact LRU, read-through (`remember`) and memoization (`wrap`) with single-flight, and a store failure that degrades to a miss rather than to a 500. `void/cache-redis` (same package) puts it in redis; `void/cache-http` caches responses of routes marked `:void.cache/response` | 2 |
| `jobs/` | `void/jobs` — background jobs: the `:void/jobs-backend` contract (eight functions over records, exactly one of which has to be atomic) and the `:void/jobs` interface over it, an in-process backend, `defjob` with retries, backoff+jitter, priorities, delays, uniqueness and a dead letter queue, parent-child flows, per-queue rate limiting and concurrency with group keys for fair scheduling, and `defschedule` cron that fires once across a fleet. `void/jobs-db` (same package) keeps the queue in the database, claiming with `FOR UPDATE SKIP LOCKED` where there is one; `void/jobs-redis` keeps it in redis, claiming with a Lua script that promotes, skips capped groups and marks the job running in one round trip | 2 |
| `pressure/` | `void/pressure` — load shedding (ADR-0019): a fiber samples event-loop lag and RSS, thresholds with a recovery bar under them keep one boolean, and `:void.pressure/check` contributions cover what the runtime cannot measure. `void/pressure-http` (same package) turns that boolean into a fast 503 + `Retry-After` in phase 100 — before parsing, sessions or a pooled connection — while routes marked `:void.pressure/exempt` are never wrapped, so `/health` answers *while* the process refuses everything else. What it costs a request that is not being shed: nothing measurable — `janet main.janet b1 b1-pressure` in `bench/` puts the two rows side by side (SPEC §8.5) and the delta sits inside run-to-run noise | 2 |
| `auth/` | `void/auth` — authentication (ADR-0023): identity as **data** in a dyn (`{:subject "user:42" :via :password :claims {…}}` — void does not know what a user is), strategies as an extension point (`:session`, `:bearer` API tokens stored as digests, `:jwt` with the algorithm fixed by configuration rather than by the token, `:password`, magic links and one-time codes that are single-use by construction), password hashes as portable PHC strings that carry their own cost so raising it is a config change rather than a migration, and the user store as a contract. `void/auth-http` (same package) resolves the identity in phase 4000, rotates the session id on login (session fixation has no other fix) and enforces `:void.auth/access :required` as a 401 or a redirect through the error renderers; `void/auth-db` puts the stores in the database, with the two tables void owns shipped as DDL data for the application's own migration. `void/auth-oauth` (same package, ADR-0032) makes the application an **OAuth 2.1 resource server** — the half `void/oauth` will not have: an access token verified locally against the issuer's JWKS (fetched lazily, cached, one refetch per unknown `kid`) or through RFC 7662 introspection when it is opaque, `:void.auth/scopes` as route metadata (403 `insufficient_scope`, never a second 401), and the RFC 9728 metadata document that tells a client *which* authorization server to go to. `[:auth-oauth :audience]` is required and checked on every token: a token minted for another service must not open this one, which is the confused deputy MCP's authorization spec exists to prevent | 3 |
| `oauth/` | `void/oauth` — "sign in with a provider": the OAuth 2.1 / OIDC **client** (ADR-0034), the half ADR-0032 deliberately left out. Two routes and one hook. The start route writes a pending record into the **session** — under `[:deploy :shape] :fleet` the session store is already shared (ADR-0030), so the flow survives a load balancer without this package storing anything anywhere — and redirects with code + PKCE (S256, and no knob to turn it off: OAuth 2.1 requires it) to an exact, configured redirect URI, never one derived from a Host header (RFC 9700). The callback consumes that record in one motion, demands its state back in constant time, exchanges the code over `void/http/client`, and verifies the id_token against the issuer's JWKS with the same rules ADR-0032 applies to access tokens: `alg` from configuration and never from the token, HS* a boot error (a verifying key that could issue), `aud` equal to this client's id, and the nonce of *this* flow — a captured id_token replays never. Then the application's `:void.oauth/sign-in` decides, because the framework does not know what a user is (ADR-0023): an identity comes back and is signed in through `login!` (session-id rotation included), a response goes out as is, nil is a 403. Refresh tokens are handed to that hook as data — the column that keeps them is the application's, and `oauth/refresh!` works on whatever it stored. The boot check knows the two channels apart (ADR-0010): the authorization endpoint may always be https, the *browser* goes there; the token, JWKS, metadata and userinfo endpoints may be https once `:void/tls` is composed (ADR-0038) — without it they are a boot error naming the ways out (the plugin, an internal IdP over http, or an egress relay beside the process) | 5 |
| `authz/` | `void/authz` — ABAC (ADR-0024): a policy is a **pure function under a name** (`defpolicy`), so it is tested as a table of cases with no system running; attributes are **pulled** (`(authz/attr ctx :subject/brand-id)`) through providers only when a policy asks and are memoized for the decision, so a route whose policy reads a role never pays for the query that answers "which brand"; a decision is a **value** — `can?` is its boolean projection, `ensure!` raises it as a 403, and `explain` prints the same evaluation rather than a second one that could disagree. Roles are sugar over the same machinery, every decision passes through a core hook (`void/bus` turns it into an audit trail in 3.6), and the reason for a deny reaches the log and `void authz explain`, never the response body. `void/authz-http` (same package) enforces `:void.authz/policy` in phase 5000 — a group's policy and a route's both — and under `[:authz :default :deny]` a route with no policy fails the **boot**, not the request. Neither plugin depends on `void/auth`: the identity is read from a dyn key, so an application with its own authentication gets the same authorization | 3 |
| `security/` | `void/security` — the four things that are on by default elsewhere (ADR-0025). **CSRF** applies to requests whose credential rode on a **cookie**, not to every unsafe method — the rule follows the attack rather than the verb, which is what lets a JSON API and an HTML form live in one process while `:void.security/csrf` stays a `:restrict` key that can only be tightened; the token is signed, bound to a cookie this plugin sets, and spliced into every non-GET form through the slot `void/html` has been waiting with since wave 1. **Headers and CORS** are applied at the new `:void.http/edge` point, outside routing and outside the panic guard, because a 404, a static file, a rendered 500 and a preflight to a path with no route are all outside every middleware chain there is; the CSP is built from data (an unknown directive is a boot error, not a silently ignored typo) with an optional per-request nonce. **Rate limiting** stands on the `:void/cache-store` contract rather than a new one — a counter shared across a fleet is `void/cache-redis` in the composition — with a sliding window, `RateLimit-*` headers and a store failure that fails open. And the **client IP** is computed from trusted proxies rather than read from a header anybody can send | 3 |
| `crypto/` | `void/crypto` — every cryptographic primitive void has, from the system libcrypto through `ffi/` (ADR-0022): SHA-2 and HMAC, scrypt / argon2id / PBKDF2 derived **off the event loop** (a 25 ms scrypt on the loop is 25 ms of a worker answering nobody — the numbers are in the ADR and pinned by a test), RS256/ES256 signatures, `CRYPTO_memcmp` and OS randomness. Nothing is compiled and no jpm dependency pulls OpenSSL in: the library is opened at `:start` from a configured path, so a machine without it gets a boot error naming where it looked, and `[:crypto :require]` lets an application refuse to start without argon2id (which needs OpenSSL 3.2 — an LTS distribution may ship 3.0) | 3 |
| `tls/` | `void/tls` — outbound TLS from the system libssl through `ffi/` (ADR-0038), closing the bookmark ADR-0010 left: the reverse-proxy answer stays for inbound traffic, but for *outbound* connections "put a relay next to it" is a relay per external service, so this plugin takes that half over. SSL never sees a socket — a pair of memory BIOs and a pump between them and the janet stream, every `SSL_*` call returning immediately, the fiber parking exactly where it always parked — and what comes back is a table answering `:read`/`:write`/`:close` with a janet stream's own signatures, which is the whole integration contract: a consumer that switched `net/read` to a method call stops knowing what is underneath. Verification is the handshake, not an afterthought (`SSL_VERIFY_PEER` + `SSL_set1_host` before a byte moves; an IP peer through the verify params; SNI always; `:verify false` in `:prod` a boot error), and the consumers learn about TLS through a **seam, not an edge** (the `mail/enqueue` pose): composing `:void/tls` makes `https://` work in the http client, `rediss://` in redis, STARTTLS and `smtps` in mail, and https endpoints at the oauth and OTLP gates — while a composition without it keeps its old errors, now naming the plugin as the second way out. BIO and the X509 error strings are bound off `void/crypto`'s open libcrypto: one crypto stack in the process | 5 |
| `mail/` | `void/mail` — mail as data (ADR-0026): a message is a **table** all the way to the socket (so it can be a job's argument, a test's comparison and a log line), a body is an ordinary `void/html` view rendered by the engine the composition already selected (hiccup, temple or a third party's — a letter is written with the same components as a page), and a transport is a contribution to `:void.mail/transport` — `:memory`, `:file` (one `.eml`, openable in a mail client), `:log`, `:smtp`, or a provider's API from the application. `void/mail-jobs` (same package) is the whole of "send through a queue": it routes `mail/send` into `void/jobs` without a call site changing, queues the **rendered** letter so a retry sends the same one, and records a 5xx rejection rather than retrying it. `void/mail-auth` is the `:void.auth/deliver` contribution void/auth has been waiting for since 3.2 — `(auth/challenge! subject {:to email})` and the magic link is in an inbox. TLS is the relay's by default (ADR-0010) — and `[:mail :smtp :tls]` turns on STARTTLS or smtps once `:void/tls` is composed (ADR-0038); credentials that would go out in the clear are refused at boot either way, and in `:prod` a transport that keeps mail rather than sending it is a boot error | 3 |
| `bus/` | `void/bus` — messaging (ADR-0012), and the layer that is *not* `void/jobs`: a job is a piece of work with one owner, a message is a **fact** and who cares about it is not the publisher's business. A message is a plain table on a keyword topic, `defhandler` subscribes a function, and the chain around it runs on `void/http`'s phase scale — the panic guard, correlation and causation bound for the handler's extent, a trace that continues out of the request that published, retry, a poison topic, dedup, throttle and a payload schema. **Backends declare what they promise** (`:at-most-once` / `:at-least-once`, ordering, durability) and the runtime reads it rather than assuming: the retry middleware is on precisely when nobody else will re-run the handler. `void/bus-db` (same package) makes the message log a table — an append-only log, a cursor per consumer group, at-least-once and in order, woken by `LISTEN/NOTIFY` on Postgres and by polling everywhere else — and brings the **transactional outbox**: `bus/publish-tx!` writes the message in the caller's transaction, so a rollback takes it with it and a commit cannot lose it, which ADR-0012 makes the only sanctioned way to announce what a transaction wrote. `void/bus-jobs` puts the queue's own lifecycle on the bus | 3 |
| `kafka/` | `void/kafka` — Kafka through librdkafka (ADR-0035), and the integration is the interesting half: the library runs its own threads either way, so what matters is that none of them ever touches Janet. No callbacks — librdkafka's **event API** parks its news (delivery reports, fetched messages, its own log lines) on a queue, `rd_kafka_queue_io_event_enable` writes a byte into a pipe when the queue turns non-empty, and one fiber sleeps on that fd through `void/fdwait` — the exact generalization SPEC's appendix predicted for the shim, closing it from the second side. `produce!` is **confirmed by default**: the fiber parks until the broker's delivery report and a failed report is an error at the call site, which is what lets `void/kafka-bus` (same package) declare `:durable true` and hand the transactional outbox a transport it may trust. The bus backend maps a consumer group onto Kafka's own, moves the offset only **behind** the handler (at-least-once as two forced properties, not a promise), redelivers a nack in place with the counter the poison middleware reads, and puts the payload alone in the message value — id and meta ride in headers, so a consumer that never heard of void reads the topic and a foreign message on our topic is still a message. Order is declared `:none` out loud, because Kafka orders partitions and the contract's other word promises more; a `:key` in the meta buys the order Kafka actually sells | 5 |
| `ws/` | `void/ws` — WebSocket (RFC 6455, ADR-0028), and the point is what it is *not*: **a websocket is a route**. `ws/accept` is called from an ordinary handler, so the handshake has already been routed, has already loaded its session, and has already met `void/auth`, `void/authz` and `void/security` — no plugin needed a second code path for sockets, and the mark `:void.ws/socket` exists so a `:void.http/timeout` on such a route fails the **boot** rather than cancelling somebody's conversation. Below it: framing, ping/pong and a finished close handshake; a fiber per connection plus a writer draining a **bounded** outbound queue, so a broadcast cannot block on the slowest member of a room; one sweeper fiber for the whole process instead of a timer per socket; and rooms whose broadcast frames the message **once** for everybody (a server never masks, so the bytes are identical) — which is what makes B4 a queueing exercise rather than an encoding one. With prefork each worker has its own registry and that boundary is not hidden: a fan-out across workers is three lines of `void/bus`. `void/ws-htmx` (same package) is the server side of htmx's ws extension — a hiccup fragment marked for an out-of-band swap, rendered by the same engine a page uses. No `permessage-deflate`, and no TLS (ADR-0010): `wss://` terminates at the relay, like everything else | 4 |
| `proto/` | `void/proto` — protobuf in pure Janet (SPEC §5.7, ADR-0013), and the foundation ADR-0013 says to write first: the wire format, a codec over **descriptors as data** (no generated classes — a decoded message is an ordinary table, which every other layer of void already knows how to validate, log, queue and compare), the proto3 JSON mapping Connect's `application/json` needs, and a `.proto` parser on PEG that reads real files — `google/protobuf/api.proto` with its whole import graph — while `google/protobuf/*.proto` resolves out of the package rather than off disk. The encoder is **byte-identical to `protoc`**, and the suite says so with golden vectors `protoc --encode` printed. Two decisions carry the rest: a 64-bit integer that a double cannot hold comes back as an `int/s64` rather than rounded (the policy `void/db-postgres` already applies to `int8`), and **unknown fields survive a round trip** — a proxy or an older replica must not be the reason a field somebody added disappears. The payoff is SPEC §3.3 collecting: every registered message is a registered **void schema** under the same name, because the schema layer *watches* the descriptor registry — so `[:ref …]`, `void schemas`, the OpenAPI document, `void/rest`'s body validation and `void/admin`'s forms all work on a protobuf message without one of them learning what protobuf is. proto2 is refused by name (`required`, `group`, `extensions`, `default =`), not approximated | 4 |
| `grpc/` | `void/grpc` — Connect-RPC over the void/http kernel (SPEC §5.8, ADR-0013): gRPC compatibility **without HTTP/2**, which is the trade that makes this M rather than XL. The whole design is one sentence — **a method is a route**: every method a `.proto` declares is projected into the one route table, named `:shop.orders.OrderService/GetOrder`, so `:void.authz/policy` is checked by the same middleware in the same phase as on a page, `:void.db/txn` opens the same transaction, `void/obs` counts RED by route name, `void/pressure` sheds it and `void/security` stands in front of it — and none of that is re-implemented here. Under `[:authz :default :deny]` an RPC method with no policy fails the **boot**, like any other route. Nothing is declared twice either: the methods, their messages and their `idempotency_level` come from the file, and `defservice` adds the two things a `.proto` cannot say — the handler and the route metadata; a method the file declares and nothing answers fails the *declaration*, because an `unimplemented` discovered in production is a hole in a contract found by the one person who cannot fix it. An idempotent method also answers **GET**, which is Connect's own form and what puts `:void.cache/response` within reach of an RPC. Errors are the sixteen codes and two tables — code → status is the protocol, status → code is a judgement, so it is written down — and an error renderer ahead of problem+json means a 403 from `void/authz` reaches a generated stub as `permission_denied` rather than as an HTML page. The client is the same protocol on `void/http/client`. No streaming (a `.proto` with a `stream` is refused at `defservice`, where the person reading the error can change the file), no gRPC or gRPC-Web framing (the ecosystem's answer to a Connect server is a transcoding proxy, and ADR-0013 chose that), no compression | 4 |
| `mcp/` | `void/mcp` — the application as an **MCP server** (ADR-0031), and the whole of it is a projection: an agent's tools are the `:void.core/cli` commands the operators already run (`void jobs stats`, `void db status`) with the same arguments and the same output, its resources are the registered schemas as JSON Schema, the health report the core folds for `GET /health`, and — with `void/mcp-obs` — the same Prometheus exposition `/metrics` serves. Nothing is declared twice, so nothing can drift. **Read-only is structural, not a list somebody maintains**: a command is a tool because it declared `:read-only? true`, silence means "unknown" and unknown is never offered, and everything else waits to be named in `[:mcp :tools]` by an operator — a plugin added tomorrow exposes nothing. `void mcp serve` speaks JSON-RPC on stdin/stdout (a line is a message; a command's `print` becomes the tool's answer instead of corrupting the stream), and `void/mcp-http` (same package) is the other transport as an **ordinary route**: Streamable HTTP with no session to pin to a process, so it deploys as a fleet; SSE only when a client sent a progress token, carrying what the command has printed so far; `GET /mcp` is a 405 that says why; a bearer token or — with `void/auth-oauth` composed — an OAuth access token issued *for this server*, read from void/auth's dyn key so this plugin knows about neither; an Origin allowlist; and in `:prod` an endpoint with nothing in front of it does not boot | 4 |
| `admin/` | `void/admin` — the back office as **another projection of the schema layer** (ADR-0029), the way OpenAPI is. `defresource-admin` registers a *frozen value*, not a function that builds routes, and that one decision is what lets two projections read it: `void/admin` turns the registry into pages, `void/admin-mcp` (same package) turns the same registry into MCP tools with the same policy names, and the input schema of "create" for an agent **is** the schema the HTML form validates against — one value, so they cannot drift. Nothing is generated: a field added to `defentity` is in the list, the form and the tool on the next request. Every action is a real route named `:admin.<resource>/<action>`, so `void routes`, `explain-route`, `:void.db/txn` and CSRF work here without knowing the admin exists. **The gate is shut by construction**: `:void.admin/access` refuses until `[:admin :access]` names the application's policy, and the refusal says which key opens it; on top of it each action carries its own policy, which exists so that "only the owner may delete" is a `defpolicy` and nothing else. Row-level is two echelons: `:scope` narrows the query *and* the count with one expression, and every single-row action re-checks with the loaded row — so a bug in a scope is a 403, not somebody else's row. A bulk action is a confirmation **page** that counts the rows on the server (a number from the client means nothing), and a heavy one goes to `void/admin-jobs`, where progress is the job record's own state. Widgets are a six-function contract resolved once per field at mount and printed by `void admin widgets`. Below all of it are ordinary pages: htmx makes them responsive, never possible. And the package owns no table — a change announces itself on `:void.admin/changed`, and whoever wants a trail subscribes | 4 |
| `storage/` | `void/storage` — files and uploads (ADR-0039), the piece that used to be missing between the multipart parser of wave 1 and an `<img>` on a page. **A key is data**: `products/2026/09/4f2a1c.png` in an ordinary text column — not a URL that goes stale when the bucket moves, and not an attachment object with a table this package would have had to own. Five functions over keys and bytes (`put!`/`get`/`stream`/`delete!`/`url`) are the contract; the local store writes through a temp file and a rename, so a reader never sees half an upload, and serves through `void/storage-http` — one route into `static/file-response`, so an upload gets the *same* strong ETag, `304` and `Range` handling the stylesheet gets, out of one implementation. `void/storage-s3` speaks to a bucket with void's own stack and no SDK: `http/client` for the transport, `void/tls` for an https endpoint (ADR-0038), and SigV4 written as pure functions over `void/crypto` — which is why it is checked against AWS's published vectors in a unit test rather than against a 403 from somebody's bucket. Temporary URLs come two ways and that is deliberate: the local store signs with `void/security`'s keys (rotation included, ADR-0025), the bucket gets SigV4 query auth, because there the verifier is not us. And the seam that makes it a framework feature rather than a library: `:image [:file {:storage/accept [...] :storage/max-bytes ...}]` in a `defentity` is the whole declaration — `void/html` renders the file input and flips the form to `multipart/form-data`, `void/storage-admin` draws the thumbnail and *stores* what was submitted (refusing the wrong type on the server, with the reason on the field), and the column keeps the key. A disk is one machine's disk, so it answers `:shared? false` and `[:deploy :shape] :fleet` refuses to start on it, naming the bucket — the same check every other store meets (ADR-0030) | 6 |
| `obs/` | `void/obs` — observability (ADR-0021): a metric registry whose cardinality is capped by construction (counters, gauges, histograms; declared at module load, written on the hot path, refused past `:max-label-sets`) with the Prometheus text exposition as a pure projection of it, spans in a dyn with W3C `traceparent` in and out, an event-loop lag histogram (§8.4's health indicator, sampled with the meter `void/pressure` reacts to), log sampling that keeps a sampled trace whole, and auto-instrumentation of whatever data plugins are in the composition. `void/obs-http` (same package) adds RED per route from the route table — labelled by route name, never by path — the request's root span, a queue-time histogram, and `GET /metrics` `/health` `/ready`. A request's root span is built only when something will read it (an exporter, or a caller who sent a `traceparent`), which is how the ≤ 7% instrumentation budget of §8.2 is met: `janet main.janet b1 b1-obs` in `bench/` is the row that checks it | 3 |

`examples/` holds one example application per wave (they double as smoke tests in CI): `examples/demo` (the wave-0 toy plugin), `examples/guestbook` (the wave-1 HTMX guestbook), [`examples/blog`](examples/blog) (the wave-2 CRUD application — entities with relations, migrations as data, route-level transactions, explicit preloads, a cached index and a denormalized counter kept true by a background job — **carried into wave 3**: signing in on a session, a row-level policy that both the route and the template ask, CSRF the application never mentions, `[:authz :default :deny]`, under which a route without a policy fails the boot, and an audit trail that is one file — the handlers publish facts through the transactional outbox and `audit.janet` subscribes, so deleting it stops the trail and changes nothing else).

`examples/blog` is also where the wave-2 claim is checked rather than asserted: `main.janet` is the only file that names a database driver, and its suite runs twice — once on sqlite, once on Postgres — over the same list of assertions, with no branch on the dialect in any of them.
It is also where wave 4's admin is dogfooded, and the shape of that is the claim: `examples/blog/admin.janet` is *four declarations, one policy and one function* — no handlers, no templates, no routes. The pages it produces are a projection of the entities wave 2 wrote; an author's list is scoped to their own articles, so the count on the page counts what the page shows; comments are edited inline on the article and the foreign key comes from the URL rather than the form; and every change is announced on `:void.admin/changed`, which that one function turns into a bus message — so the admin's edits land in the audit trail wave 3.6 built, next to the edits the application's own routes make, with no migration anywhere. The same composition also loads `void/admin-mcp`, and `test/admin-test.janet` asserts both halves at once: the same author, through a page and through an agent's tool, sees the same rows under the same policies — and an agent with no identity sees none.

[`examples/shop`](examples/shop) is the one that puts the whole framework in one process, and the one to read if you want to know what an application built on void actually looks like: a storefront and a checkout that takes money (stock decremented by a conditional UPDATE, prices re-read from the catalog, and the order, the fact that it happened and the payment job all committing in one transaction), a payment gateway whose declines and timeouts are deliberately different kinds of answer, a back office with no pages in it — six `defresource-admin` declarations living in the modules they are about, projected into routes for a person and into MCP tools for an agent out of the same value — a JSON API that is a second *view* rather than a second application (query and response schemas, bearer-only credentials, response caching, and `/openapi.json` as a projection of all of it), five application metrics next to void/obs' own, and an audit trail that is one deletable module. It is also the example that answers "where does this code go": `src/modules/<module>/` with a model, DTOs, a repository, a service, a controller and its adapters, and a README section spelling out what each layer may and may not do. It also ships a [`Dockerfile`](examples/shop/Dockerfile) and a [`docker-compose.yml`](examples/shop/docker-compose.yml): `docker compose up --build` brings up Postgres, redis, a mail server with a web inbox, a one-shot migration, a web tier and a worker — **the same image running the same code, differing by two environment variables** — and `--profile obs` adds Prometheus and a provisioned Grafana dashboard.

The scaffolding half of the CLI landed in wave 4.5, and with it the deploy story: `void make resource` writes four files that are four projections of one declaration (so the generated suite checks that they still agree, without needing a database); `void make auth` (wave 6.2) does the same one layer up — the machinery for signing in has been there since wave 3, and what every application still wrote by hand were the five pages, so the generator writes those: an entity `void/auth-db` reads, a sign-up form projected off it, register/login/logout, and a password reset and an address verification that are *one* flow, because `challenge!` mints both and a deliverer builds one URL. What checks it is not a rewritten example but the suite it generates itself, booted on a real database; `void plugins lock` writes the composition down — every extension point with its contributions *in resolution order* — so that "why is the middleware stack different in production" is a `void plugins check` diff rather than an investigation; and `jpm --local build` produces a single binary that is also the CLI, so `./myapp db migrate` works on a target with no janet and no source tree. The measured sizes, the four rules an application follows to be buildable, and what the binary deliberately does not contain are in [docs/DEPLOY.md](docs/DEPLOY.md).

Wave 5's main chain is closed: `void/db-mysql` (ADR-0033), `void/oauth` (ADR-0034), `void/kafka` (ADR-0035), `void/i18n` (ADR-0036), the experimental `void/datastar` (ADR-0037) — and `void/tls` (ADR-0038), which retires the last "void speaks no TLS" caveat for outbound connections while inbound TLS stays at the reverse proxy (ADR-0010). Wave 6 (see [docs/ROADMAP.md](docs/ROADMAP.md)) is about parity with what a real application reaches for in its first week — file storage and uploads (ADR-0039) and the `void make auth` scaffold are in; a jobs dashboard in the admin, unified notifications and tailwind without node are next — and about building that application; the v0.5 tag and the public announcement wait for it. The datastar experiment keeps its mark until a first application outside `examples/` (the decision is recorded in ADR-0037), and gRPC streaming over HTTP/2 stays deferred with an ADR of its own, waiting for a reason.

## Development

Requires [Janet](https://janet-lang.org/) ≥ 1.41, jpm and a C compiler.

```sh
janet scripts/bootstrap.janet   # external deps + build void/fdwait
cd core && jpm test             # any package; the module path is wired
                                # from the graph, nothing is installed
```

Contributors never install void to use it — `scripts/void` is the CLI
running straight off the checkout, so an edit in `core/` is live in the
next command:

```sh
scripts/void new myapp
cd myapp && ../scripts/void routes
```

`void/db-postgres` needs a Postgres to test against:

```sh
cd db-postgres && jpm test    # config/types run everywhere; the rest
                              # skips without a server

VOID_TEST_PG="postgres://void:void@127.0.0.1:5432/void_test" jpm test
```

`void/db-mysql` asks the same way:

```sh
cd db-mysql && jpm test       # config/types run everywhere; the rest
                              # skips without a server

VOID_TEST_MYSQL="mysql://void:void@127.0.0.1:3306/void_test" jpm test
```

`void/kafka` too — the layouts and the config run everywhere, the
delivery-report machinery runs wherever librdkafka is installed
(`brew install librdkafka`, `apt install librdkafka1`) with no cluster
at all, and the full backend suite wants one broker:

```sh
cd kafka && jpm test

VOID_TEST_KAFKA="127.0.0.1:9092" jpm test
```

libpq itself is opened at runtime through `ffi/` (`brew install libpq`,
`apt install libpq5`) — nothing links against it, and a machine without
it is told so at boot rather than at install time. libmysqlclient is
opened the same way (`brew install mysql-client` or
`mariadb-connector-c`, `apt install libmysqlclient21` or `libmariadb3`);
MariaDB Connector/C exports the same API and is a first-class answer
rather than a fallback. `janet-lang/sqlite3`
is the same deal for `void/db-sqlite`: the bundle leaves the binding out
on purpose, and the driver resolves it on first use, so an application
that never lists `:void/db-sqlite` in its `:plugins` never needs it.
